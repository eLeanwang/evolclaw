#### P0-1: 回复发送路径自相矛盾

**位置**: architecture.md §2.4 vs prompts/main-base.md

**问题描述**:
- architecture.md: 代码层解析 `response.replies` 后循环执行 `ec msg send`
- prompts/main-base.md: 主会话在 turn 内自己调用 `ec msg send`

两条路径同时存在 → **每条回复发送两遍**。

**根本原因**: 
架构设计按"裸 API 调用"思路，假设主会话只返回文本由代码层发送。但 Claude Code 是 agentic 基座，turn 内可执行工具调用、分步回复，不能用"turn 结束后统一发送"模型。

**影响**:
- 重复发言
- 与现有 proactive 模式不一致
- 附加能力(发文件/@人)必走 CLI，出现两套发送路径并存

**用户澄清** (2026-07-03):
✅ **同意删掉代码层 sendReplies，统一为主会话 turn 内自发 CLI**

**核心发现**:
- 本 agent 通过 `ec group send` / `ec msg send` 发送的消息会从 AUN 网络广播回来，但在 `aun.ts:1490-1494` 被 own message 过滤（`senderAid === this._aid`），**不会进入辅助队列**
- 因此辅助会话看不到本 agent 的回复，**必须通过 feedback.replies 传递**

**修复方案**:
1. 删除 architecture.md §2.4 的 `sendReplies()` 方法
2. 删除 `FeedbackStore` 组件和 `main-feedback.jsonl` 文件（多余，feedback 直接通过方法调用传递）
3. 简化 `MainFeedback` 结构：
   ```typescript
   interface MainFeedback {
     summary: string;   // 主会话输出的自然语言总结（<200字）
     replies: string[]; // 从工具调用历史提取的回复内容
   }
   ```
4. 代码层从主会话的工具调用历史中提取所有 `ec group send` / `ec msg send` 的消息正文 → `replies`
5. 代码层从主会话的最后输出中提取自然语言总结 → `summary`
6. 组装成 `MainFeedback` 后直接调用 `auxiliarySession.processFeedback(feedback)`
7. 更新 main-base.md 提示词：主会话在 turn 内自己发送，turn 结束输出自然语言总结（不是 JSON）
8. ~~增加兜底检查~~（用户明确：不需要，agent 有不回复的自主权）

#### P0-2: 单聊场景设计缺失

**位置**: 全文档

**问题描述**:
用户要求支持"单聊和群聊"，但整套设计针对群聊：
- `delay + 0-60s 随机` 是纯群聊竞争回避，单聊里让 owner 等 3-63 秒不可接受
- `hold`("与本 agent 无关") 在一对一里几乎无语义
- plugin-analysis.md:301 写 `applicableScenes = ['group', 'private']`，但所有判断标准(auxiliary-base.md)都是群聊话术

**影响**:
单聊下延迟过高、体验差，与现有"private 场景自主模式"的用户预期不符。

**用户澄清** (2026-07-03):
单聊双会话模式与群聊基本一致，只有以下差异：

**修复方案**:
单聊与群聊使用相同的双会话机制，但有以下差异：

1. **辅助会话输出类型**：
   - 群聊：`hold / delay / transfer`
   - 单聊：`delay / transfer`（无 hold，一对一都相关）

2. **延迟投递不加随机数**：
   - 群聊：`delayMs + 0-60秒随机`（避免多 agent 竞争）
   - 单聊：仅 `delayMs`（无竞争，无需随机）

3. **触发条件差异**：
   - 防抖时间：两者相同（3秒，可配置 0-6 秒）
   - 最早消息强制触发：两者相同（15 秒）
   - **队列满强制触发**：群聊 50 条，单聊 **15 条**
   - **主会话空闲触发**：单聊特有（主会话变空闲时立即触发投递）

4. **辅助会话提示词**：
   - 按 `chatType` 使用不同 fragment（复用 ECK 的 `when` 条件）
   - 单聊版提示词删除 hold 相关描述和示例

5. **主会话空闲监听**（单聊特有）：
   ```typescript
   mainSession.on('statusChange', (oldStatus, newStatus) => {
     if (oldStatus === 'processing' && newStatus === 'idle') {
       const undelivered = auxiliaryQueue.getAllUndelivered();
       if (undelivered.length > 0) {
         auxiliarySession.process(undelivered, 'main-idle');
       }
     }
   });
   ```

#### P0-3: HOLD 消息永不清理，队列无界增长

**位置**: auxiliary-base.md:65, architecture.md

**问题描述**:
auxiliary-base.md 明确"挂起的消息不会丢弃，仍在辅助队列中"。每次触发都把**全部未投递消息**送给辅助会话判断。

活跃群里闲聊占大头 → HOLD 堆积 → 每次辅助调用 token 线性增长 → 队列满 50 条触发器被闲聊持续打满。

**用户澄清** (2026-07-03):

**核心机制**：
1. **HOLD 是"暂时挂起"，不是"永久不投递"**
2. **辅助队列消息的唯一出口**：转移到主队列（没有其他清理机制）
3. **队列满强制投递**：
   - 群聊：50 条或 10k 字节
   - 单聊：15 条或 10k 字节
   - 触发时：所有消息（HOLD/DELAY/PENDING）按时间顺序全部投递到主队列，排队投递（不打断）
4. **已处理消息不重复输入**：辅助会话处理过的消息（标记 `processedByAuxiliary = true`）不会再次作为输入，只有新消息会输入

**结论**：
- ✅ 有兜底机制（队列满强制投递）
- ✅ 已处理消息不重复输入（token 不会线性增长）
- ✅ HOLD 消息最终会投递到主队列

**P0-3 不是真正的问题**，现有设计已有合理的兜底机制。

#### P0-4: 与现有群聊 mention 静默机制未明确集成关系

**位置**: 缺失

**问题描述**:
现有系统群聊默认 mention 模式，未@的消息在 aun.ts 适配器层被过滤(见项目 memory)。

双会话模式的价值在于辅助会话**看到全量群消息**判断相关性。两者叠加时谁生效？文档完全未提。

**影响**:
- 若 mention 过滤先生效 → 辅助会话只能看到@消息，相关性判断能力废掉
- 若双会话先生效 → 需要明确旁路 mention 过滤的机制

**用户澄清** (2026-07-03):

**当前实现**（`aun.ts:1606-1616`）：
```typescript
const enforceMention = dispatchMode === 'mention' || isCommandMsg;
const isMentioned = mentionedSelf || mentionedAll;

if (enforceMention && !isMentioned) {

2. **双会话模式下，没有"提及模式"的概念**
3. **所有群消息都应该进入辅助队列**（无论是否被 @）
4. **`isMentioned` 标记保留**，在系统提示词渲染时使用（被 @ 的消息相关性更高）

**修复方案**:
1. 删除 `aun.ts:1612-1616` 的 mention 过滤逻辑
2. 保留 `isMentioned` 标记（传递给辅助会话）
3. 所有群消息进入辅助队列，由辅助会话判断相关性（hold / delay / transfer）
4. 系统提示词渲染时，如果 `isMentioned=true`，可以增加相关性提示（如"本消息 @ 了你"）

**新逻辑**：

```

#### P0-5: 打断机制按"无副作用文本生成"设计，Claude Code 下不成立

**位置**: README.md:265-298, architecture.md:515-519

**问题描述**:
设计假设"停止主会话是免费的，消息 A 已在上下文可继续参考"。

但 Claude Code 的 turn 是带工具调用的 agentic 过程：
1. 打断时可能已执行副作用——**已发送半截回复**、改文件、跑命令
2. 打断后重新处理批次，可能对同一问题再答一遍(重复发言高危路径)
3. 中断在 tool_use 与 tool_result 之间留下不完整会话状态
4. "A 已在上下文"只在 turn 至少启动过后成立

**影响**:
- 重复发言
- 资源泄漏(半完成的操作)
- 会话状态不一致

**用户澄清** (2026-07-03):

**现有实现**（单聊打断机制）：
- 每条新消息都调用 `agent.interrupt(sessionId)`
- `agent.interrupt()` 调用 SDK 的 `sdkStream.interrupt()` 方法
- **硬打断**：中止当前 API 请求（abort）
- **副作用无法撤回**：已发送的回复、已执行的命令无法撤回

**双会话模式的打断机制**：
- **单聊和群聊的打断操作是一样的**：都是调用 `agent.interrupt(sessionId)`
- **打断触发条件**由辅助会话判断（不是"每条消息都打断"）：
  - 辅助会话输出 `interrupt: true`
  - 主会话正在处理（`isProcessing()`）
  - 当前批次 < 50 条
- **副作用说明**：
  - 已发送的回复无法撤回（通过 `ec group send` / `ec msg send`）
  - 已执行的工具调用无法撤回（修改文件、执行命令等）
  - 这是打断机制的固有特性

**结论**：
- ✅ 双会话模式已有清晰的打断逻辑
- ✅ 副作用是机制固有特性，不是设计问题
- ✅ 辅助会话判断打断，避免了"每条消息都打断"的问题
- ✅ 主会话的反馈（包含已发送的回复）会传递给辅助会话

**P0-5 不是真正的问题**，现有机制已合理，只需在文档中说明副作用。

#### P0-6: 打断后被中断的批次会丢

**位置**: architecture.md:423-427, 515-519

**问题描述**:
- `extractBatch` 用 `splice` 把消息移出队列
- `interrupt()` 不回灌 `currentBatch`
- 重新提取的新批次是 [B, C, D]

消息 A 只存在于"上下文"里，既不在主队列、不在新批次，在辅助队列已标记 TRANSFERRED 且永不出现在 feedback 的 processedMessageIds 里 → **既不会被处理也不会被清理**。

**影响**:
消息永久丢失，无声无息。

**用户澄清** (2026-07-03):

**消息 A 在哪里**：
- ✅ 在主会话的上下文中
- ✅ 主会话处理新批次 [B, C, D, E] 时，A 仍然在上下文中可以参考
- ✅ 主会话实际上是在处理 [A, B, C, D, E]（A 在上下文，BCDE 在新批次）

**不是问题**，但需要增强打断机制：

### 辅助会话输出增强

**新增字段**：
```typescript
interface AuxiliaryDecision {
  action: 'hold' | 'delay' | 'transfer';
  delayMs?: number;
  interrupt?: boolean;
  interruptReason?: string;  // 打断原因（interrupt=true 时必填）
  previousMessageStrategy?: 'ignore' | 'defer' | 'continue';  // 被打断消息处理策略（interrupt=true 时必填）
  reason: string;
}
```

**`previousMessageStrategy` 三种策略**：
- `ignore`：忽略被打断的消息，只处理新消息
- `defer`：先处理新消息，完成后再处理被打断的消息
- `continue`：继续处理被打断的消息，但考虑新消息的内容

### 辅助会话输出格式

**两部分输出**：
1. **思考过程**（<200字）
2. **JSON 判断结果**

**示例**：
```
【思考过程】
Owner 提了一个关于报错的紧急问题，主会话正忙着处理闲聊消息，需要打断。新问题优先，但闲聊消息不重要可以忽略。

【判断结果】
{
  "action": "transfer",
  "interrupt": true,
  "interruptReason": "Owner 提出紧急问题",
  "previousMessageStrategy": "ignore",
  "reason": "紧急问题优先处理，闲聊可忽略"
}
```

### Schema 插入方式

- **Schema 作为辅助会话系统提示词的一部分**（`.md` 文件）
- 通过 ECK 的模板渲染机制注入
- 兼容所有 base agent（Claude Code、Codex、Gemini CLI 等）
- 不是硬编码在代码中

### 输出验证和重试

```typescript
// 解析辅助会话输出
const response = await auxiliarySession.process(batch);

// 提取 JSON 部分
const jsonMatch = response.match(/\{[\s\S]*\}/);
if (!jsonMatch) {
  await auxiliarySession.retry('未找到 JSON 格式的判断结果，请重新输出');
  return;
}

// 验证 schema
const decision = validateSchema(JSON.parse(jsonMatch[0]));
if (!decision.valid) {
  await auxiliarySession.retry(`输出格式不符合 schema：${decision.errors}`);
  return;
}
```

### 主会话系统提示词注入

**打断发生时，注入打断信息**：

**ignore 策略**：
```
【打断通知】
原因：紧急问题需要立即处理。
处理建议：忽略之前的消息，只处理新消息。
```

**defer 策略**：
```
【打断通知】
原因：紧急问题需要立即处理。
处理建议：先处理新消息，完成后再处理之前的消息。
```

**continue 策略**：
```
【打断通知】
原因：用户补充了重要信息。
处理建议：继续处理之前的消息，但考虑新消息的内容。
```

**要点**：
- 只插入打断原因和处理建议的文字描述
- 不枚举被打断的具体消息
- 不浪费 token

**结论**：
- ✅ 消息 A 没有丢失（在主会话上下文中）
- ✅ 通过打断信息指导主会话如何处理
- ✅ Schema 通过提示词注入，兼容所有 base agent

#### P0-7: 主会话调用失败 = 静默丢消息

**位置**: message-flow.md:582-604

**问题描述**:
失败后直接 `completeBatch` + feedback 写"处理失败" + 辅助队列**照样移除**这些消息。

owner 的问题无声无息消失，没有重试、没有告警、没有对端通知。

**影响**:
消息丢失，严重损害可靠性。

**用户澄清** (2026-07-03):

**当前单聊的错误处理机制**（response-engine.ts:1448-1565）：
1. 重试 3 次（退避时间：5秒、10秒、30秒）
2. 每次重试前通知用户："API 不可用，X秒后重试 Y/3"
3. 重试期间检查中断（新消息到达可以打断重试）
4. 重试失败后：
   - 记录健康状态（`recordError`）
   - 抛出错误
   - 消息从队列移除，继续处理下一条
   - **用户没有收到任何回复**（消息"丢失"）

**双会话模式的错误处理机制**：

### 1. 调用失败的主要处理行为

**与单聊一致**：
- 重试 3 次（5秒、10秒、30秒退避）
- 每次重试前通知用户
- 重试期间检查中断

### 2. 最终失败后消息回退

**消息回退到来源队列**：
- **辅助会话处理失败** → 消息回退到**辅助队列**
- **主会话处理失败** → 消息回退到**主队列**

**消息标记错误**：
```typescript
interface QueuedMessage {
  message: Message;
  state: MessageState;
  hasError: boolean;           // 是否处理失败
  lastErrorTime?: number;      // 上次失败时间
  errorCount?: number;         // 失败次数
}
```

### 3. 消息重新处理

**重新提取批次**：
- 处理成功 → 消息从队列移除
- 处理失败 → 消息回退并标记 `hasError: true`
- 继续提取后续消息进行处理

### 4. 消息提取规则（关键）

**提取规则取决于"上次处理结果"**：

#### 上次处理成功

可以提取带 `hasError` 标记的消息（重试失败的消息）：

```
初始队列：[A, B, C, D]
提取批次：[A, B]
处理结果：失败
↓
A、B 回退到队列，标记 hasError: true
队列：[A(error), B(error), C, D]
↓
下次提取：[C, D]（跳过带 error 的消息）
处理结果：成功
↓
C、D 从队列移除
队列：[A(error), B(error)]
↓
再下次提取：[A(error), B(error)]（上次成功，可以重试错误消息）
```

#### 上次处理失败

跳过带 `hasError` 标记的消息，只提取正常消息：

```
队列：[A(error), B(error), C, D]
上次提取：[C, D]
处理结果：失败
↓
C、D 回退到队列，标记 hasError: true
队列：[A(error), B(error), C(error), D(error)]
↓
下次提取：无法提取（所有消息都标记 error，且上次失败）

等待新消息到达：E
队列：[A(error), B(error), C(error), D(error), E]
↓
下次提取：[E]（跳过所有带 error 的消息）
```

#### 批次边界规则

**遇到错误消息时截止**（避免错误消息与正常消息混在同一批次）：

```
队列：[A, B(error), C, D]
提取时：
- 如果 B 是第一条 → 提取 [B(error)]
- 如果 B 前面有消息 → 提取 [A]，B(error) 留给下个批次
```

**规则**：同一批次中，遇到第一个带 `hasError` 标记的消息时截止（除非它是批次的第一条）。

### 5. 消息渲染规则

**提示词中标注错误消息**：

```
【消息 #A】
来自：Owner
时间：2026-07-03 10:00
状态：⚠️ 处理失败（上次尝试：2026-07-03 10:05，失败 1 次）
内容：帮我修复这个 bug
```

**要点**：
- 明确标注"处理失败"
- 显示上次尝试时间
- 显示失败次数
- 提醒 base agent 这是需要重新处理的消息

### 6. 通知用户

**最终失败后向对端发送通知**：

```
抱歉，我遇到了技术问题（API 暂时不可用），你的消息暂时无法处理。我会在问题解决后继续处理。
```

**要点**：
- 不让用户的消息"无声无息消失"
- 告知用户会继续尝试
- 保持用户信心

**结论**：
- ✅ 复用单聊的重试机制（3 次退避重试）
- ✅ 消息回退到来源队列，标记错误
- ✅ 智能提取规则：上次成功可重试错误消息，上次失败跳过错误消息
- ✅ 批次边界规则：错误消息不与正常消息混在同一批次
- ✅ 提示词标注：明确告知 base agent 这是失败消息
- ✅ 用户通知：告知技术问题，会继续尝试

### 7. 辅助会话失败降级策略（补充）

**问题场景**：
1. **消息卡在辅助队列**：群里有人发了消息，被辅助会话 HOLD 了，然后再也没有其他消息进来 → 主会话漏掉处理这个消息的机会
2. **辅助会话模型挂了**：如果辅助会话模型不可用，但主会话模型可用 → 整个群聊卡住

**兜底机制**：

#### (1) HOLD 超时投递

```typescript
interface QueuedMessage {
  message: Message;
  state: MessageState;
  hasError: boolean;
  holdSince?: number;  // 新增：首次 HOLD 的时间
}
```

**规则**：
- HOLD 超过 **1 小时** → 自动投递到主队列（不打断）
- 检查时机：每次辅助会话处理时检查

#### (2) 辅助会话失败降级

**错误状态标记**：
```typescript
interface AuxiliarySession {
  errorState: {
    isInError: boolean;           // 是否处于错误状态
    consecutiveFailures: number;  // 连续失败次数
    lastSuccessTime?: number;     // 上次成功时间
  };
}
```

**降级策略**：
```
辅助会话调用失败
↓
第一次失败：退避重试 3 次（5秒、10秒、30秒）
↓
重试失败：
  - 默认决策：delay (medium, 2分钟)
  - 延迟投递到主队列
  - 标记辅助会话为"错误状态"
  - 投递说明中注明失败原因
↓
后续调用：
  - 先尝试调用辅助会话
  - 失败 → 延迟 2 分钟投递（不重试）
  - 成功 → 清除错误状态标记
↓
下次失败：
  - 重新重试 3 次（错误状态已清除）
```

**延迟投递的优势**：
- ✅ **批量处理**：2 分钟内的消息累积后一次处理
- ✅ **降低 token 消耗**：不会每条消息单独调用主会话
- ✅ **响应可接受**：延迟 2 分钟不会太久
- ✅ **系统鲁棒**：辅助会话挂了主会话仍能工作

**投递说明示例**：
```markdown
【批次投递说明】
投递原因：辅助会话模型调用失败，延迟 2 分钟后批量投递（5 条消息）

注意：由于辅助会话暂时不可用，这些消息没有经过相关性判断，可能包含与你无关的消息。请自行判断是否需要响应。
```

**与单聊的区别**：
- 单聊不需要此降级策略（单聊消息都相关）
- 群聊降级后可能投递无关消息，需要主会话自行判断

**P0-7 最终结论**：
- ✅ 双会话模式有完整的错误处理机制
- ✅ HOLD 超时投递（1 小时）
- ✅ 辅助会话失败降级（延迟 2 分钟批量投递）
- ✅ 消息可达性有保障（不会因辅助会话失败而丢失）

#### P1-2: 竞争回避在慢 agent 下失效

**位置**: README.md:6.2, message-flow.md:3.2

**问题描述**:
这是核心机制的博弈漏洞。场景：

```
T0    问题到达(未@)
T+8s  Agent2 delay到期 → transfer → 主会话开始处理(耗时2分钟)
T+15s Agent1 delay到期 → 群里还没有任何回复 → 也 transfer
T+31s Agent3 同理 → transfer
→ 三个 agent 全回复
```

随机数错开的是**判断时刻**，但"已有人回复"的证据要等对方主会话**跑完**才出现在群里。主会话越慢，碰撞窗口越大。

**影响**:
在慢 agent 场景(正是本方案要解决的场景)下，多 agent 竞争回避失效。

**用户澄清** (2026-07-03):

### 解决方案

#### 1. 增大延迟随机时间范围

**当前**：
- 群聊 `delayMs` 加 0-60 秒随机数

**改进**：
- **默认 2 分钟**（可配置：1-3 分钟）
- 更大的随机范围减少碰撞窗口

#### 2. 延迟等级机制（新增）

**辅助会话输出增加 `delayLevel` 字段**：
```typescript
interface AuxiliaryDecision {
  action: 'hold' | 'delay' | 'transfer';
  delayMs?: number;
  delayLevel?: 'short' | 'medium' | 'long';  // 延迟等级（action=delay 时）
  // ... 其他字段
}
```

**延迟等级映射**：
- `short`：1 分钟 + 随机数
- `medium`：2 分钟 + 随机数（默认）
- `long`：3 分钟 + 随机数

**辅助会话自主评估**：
- 根据问题的**相关性**和**紧急性**判断延迟等级
- 例如：
  - 高相关性、紧急问题 → `short`
  - 中等相关性 → `medium`（默认）
  - 低相关性、不紧急 → `long`

#### 3. 新消息到达时重新判断

**现有机制**：
- 群里有新消息 → 辅助会话重新判断
- 可能将 `delay` 改为 `transfer`（如果有人回复了）
- 或将 `delay` 改为 `hold`（问题已解决）

#### 4. 不需要的机制

- ❌ 不需要认领协议（增加复杂度）
- ❌ 不需要监控指标（现在）

**结论**：
- ✅ 增大延迟随机间范围（默认 2 分钟）
- ✅ 延迟等级机制（辅助会话自主评估）
- ✅ 新消息到达时重新判断（已有）
- ✅ 主会话自主决定是否回复（已有）

#### P1-3: interrupt 在队列 >50 时完全失效

**位置**: message-flow.md:291-318, plugin-analysis.md:434-438

**问题描述**:
紧急消息 D 被"追加到队列末尾"再重新提取前 50 条。若积压 60 条，D 根本不在新批次里。

两份文档描述矛盾：
- message-flow: 追加到末尾
- plugin-analysis: 清空主队列 + priority 999

**影响**:
紧急打断在队列积压时失效。

**用户澄清** (2026-07-03):

### 解决方案：打断时一次性提取所有消息

**场景**：
```
主队列：[A, B, C, ... 共60条消息]
主会话正在处理前 50 条
新消息 D 到达，辅助会话判断：interrupt: true
```

**当前设计的问题**：
- 打断后追加 D 到队列末尾
- 重新提取批次时只取前 50 条
- D 排在第 61 位，不在新批次中

**正确的做法**：
```
1. 打断主会话
2. D 追加到主队列
3. 一次性提取**所有消息**（有限制，见下方）
4. 主会话处理所有消息
```

**提取限制**：
- 最多提取最新的 **100 条消息**
- 且总大小不超过 **20k 字节**
- 更早或超出大小的消息留在队列中继续排队

**要点**：
- **只有在打断场景下**才一次性提取所有消息（带限制）
- **正常场景**仍然按批次（< 50 条）提取
- 这样保证紧急消息 D 一定在当前批次中
- 打断场景说明消息紧急且重要，需要立即处理
- 限制 100 条/20k 字节防止单次批次过大

**结论**：
- ✅ 打断时提取所有队列消息（最多 100 条，20k 字节内）
- ✅ 正常场景保持批次限制（< 50 条）

#### P1-4: feedback-ack 调一次 LLM 纯属浪费

**位置**: architecture.md:259-276

**问题描述**:
反馈处理先调模型拿固定格式 `{ack: "已更新上下文"}`，再由代码层做真正的事。这次模型调用**没有任何决策输出**。

**影响**:
不必要的 API 调用成本和延迟。

**用户澄清** (2026-07-03):

### 解决方案：MainFeedback 插入辅助队列，被动触发

**当前设计的问题**：
```
1. 主会话处理完批次
2. 生成 MainFeedback（summary + replies）
3. 调用 AuxiliarySession.processFeedback(feedback)  ← 调用 LLM
4. 辅助会话输出：{type: 'feedback-ack', ack: '已知悉'}  ← 固定格式，无决策价值
5. 代码层：无操作（仅确认收到）
```

**正确的做法**：
```
1. 主会话处理完批次
2. 生成 MainFeedback（summary + replies）
3. 代码层：直接插入到辅助队列，标记为"主会话反馈"
4. 辅助队列中只有反馈消息 → 不触发提取
5. 等待新 AUN 消息到达
6. 提取批次时：反馈消息 + 新 AUN 消息一起提取
7. 辅助会话处理：可以看到主会话的反馈 + 新消息
```

**场景示例**：
```
时间线：
T0: 消息 [A, B, C, D] 提取给主会话
T1: 主会话处理完，生成 feedback
    → feedback 插入辅助队列
    → 辅助队列：[feedback]（不触发处理）

T2: 新消息 E 到达
    → E 插入辅助队列
    → 辅助队列：[feedback, E]
    → 触发提取：[feedback, E]
    → 辅助会话处理：可以看到之前的反馈
```

**要点**：
- **省去了一次 LLM 调用**（不再调用 processFeedback）
- **feedback 仍然被记录**在辅助会话上下文中（通过队列机制）
- **被动触发**：只有新消息到达时才处理反馈
- **自然可见**：辅助会话下次判断时可以参考之前的反馈

**结论**：
- ✅ MainFeedback 插入辅助队列，标记为"主会话反馈"
- ✅ 不主动调用 LLM 处理反馈
- ✅ 等待新消息到达时一起提取处理

### 双会话模式的持久化方案

**目录结构**：
```
$AGENT_DIR/relations/<channel>#<peerId>/_threads/<threadId>/_queues/
├── main-queue.json          # 主队列
└── auxiliary-queue.json     # 辅助队列
```

**例子**：
```

├── main/
│   └── _queues/
│       ├── main-queue.json
│       └── auxiliary-queue.json

    └── _queues/
        ├── main-queue.json
        └── auxiliary-queue.json
```

**设计优点**：
1. **话题隔离清晰**：`_threads/<threadId>/` 是话题级数据的根目录
2. **数据分类合理**：`_queues/` 只是话题级数据的一部分
3. **扩展性好**：未来可以在话题级增加其他数据（context.json、summary.md 等）
4. **避免写入冲突**：主队列和辅助队列分别写入不同文件
5. **错误隔离**：一个队列文件损坏不影响另一个

1. 启动时设置所有话题的"需要重载"标志
2. 操作队列时检查标志，如果需要则从文件加载
3. 加载后清除标志，避免重复加载
4. 队列变化时写入文件

- ✅ 单会话模式已有持久化（全局 message-queue.json）
- ✅ 双会话模式需要新的持久化机制（按话题级分离存储）
- ✅ 方案：`$AGENT_DIR/relations/<channel>#<peerId>/_threads/<threadId>/_queues/`

#### P2-3: delay 拆成两种语义

**位置**: auxiliary-base.md

**问题描述**:
`delay` 混淆两个目的：
- **等用户补充**（分段输入）
- **礼让他人**（竞争回避）

前者绝不应加 0-60s 随机（用户等 63 秒体验极差），后者才需要。

**用户澄清** (2026-07-03):

### 当前设计已经足够细分

**6 个层级**：
1. **挂起（hold）** - 下次消息来了再决定
2. **延迟投递 - long** - 3 分钟 + 随机
3. **延迟投递 - medium** - 2 分钟 + 随机（默认）
4. **延迟投递 - short** - 1 分钟 + 随机
5. **立即投递 - 追加（transfer）** - 不打断
6. **立即投递 - 打断（transfer + interrupt）** - 打断主会话

### 语义已经通过层级表达

- **等待时间太长** → 选择 `transfer`（立即投递），而不是 `delay`
- **很紧急** → 选择 `transfer + interrupt`（打断投递）
- **需要观察** → 选择 `delay`，通过 `delayLevel` 选择等待长度
- **与我无关** → 选择 `hold`

### reason 字段的作用

- 辅助会话在 `reason` 中说明**为什么做这个决策**
- **不需要额外的 `delayType` 字段**
- 例如：
  - `{ action: 'delay', delayLevel: 'short', reason: '等待用户补充细节' }`
  - `{ action: 'delay', delayLevel: 'medium', reason: '观察其他 agent 是否响应' }`
  - `{ action: 'transfer', reason: '问题明确，立即处理' }`

**P2-3 不是问题**：
- ✅ 6 个层级已经提供足够的选择空间
- ✅ `reason` 字段说明决策原因
- ✅ 不需要 `delayType` 字段

## 四、设计建议

### 4.1 单聊走轻量直通模式

单聊下辅助会话净贡献 ≈ 防抖 + 打断判断。

**建议**:
单聊默认：**代码防抖 → 直接 transfer**，辅助 LLM 仅在主会话 busy 时被调用决定"追加还是打断"。

**收益**:
单聊延迟回到 3-5 秒量级，符合"private 场景自主模式"用户预期。

**用户澄清** (2026-07-04):
> 减少规则才是优雅的方式，自主性是我们整个设计体系中很重要的一个原则。

**结论**：不采纳此建议
- ✅ 单聊和群聊使用统一的双会话机制
- ✅ 保持辅助会话的自主判断能力
- ✅ 通过"主会话空闲触发"机制降低单聊延迟

---

### 4.2 长时间处理的消息先确认

**用户建议** (2026-07-04):
> 不需要认领协议，但可以在系统提示词中建议：需要多轮工具调用、长时间处理的消息应该先给出一个确认信息。

**实施方案**：
在主会话系统提示词中增加"先确认再处理"建议：

```markdown
### 需要长时间处理的消息

如果判断某条消息需要**多轮工具调用或长时间处理**（如代码分析、日志排查、复杂调试），**建议先发送一条确认消息**，再开始处理。

**好处**：
- 让对端知道你正在处理（避免重复提问或其他 agent 介入）
- 在多 agent 群聊中"认领"这个问题
- 即使后续处理被打断，对端也知道你已经开始

**适用场景**：
- 需要调用多个工具（>3 次）
- 预计处理时间 > 30 秒
- 问题复杂，需要分步分析
```

**收益**：
- ✅ 避免多 agent 同时处理同一问题
- ✅ 提升用户体验（知道有人在处理）
- ✅ 不增加协议复杂度（仅提示词建议）

---

### 4.3 确定性排序替代随机数(备选方案)

不引入新消息类型的最小方案：各 agent 本地计算 `rank = hash(msgId + selfAid)` 在群成员 agent 列表中的序。

rank 0 立即答，rank k 等 `k × T` 后仅在无人回复时答。

**收益**:
无碰撞、无需通信、完全去中心化，严格优于随机数。
