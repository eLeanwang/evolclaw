## 一、为什么需要 Context-Mode？

### 1.1 问题背景

在群聊场景下，AI Agent 面临的挑战：

```
挑战 1: 消息量大
  - 群聊消息频繁
  - 大量无关消息浪费 token
  - 难以聚焦重要信息

挑战 2: 上下文复杂
  - 多人同时对话
  - 话题交叉和切换
  - 需要理解"谁在和谁说什么"

挑战 3: 参与时机难判断
  - 什么时候应该参与？
  - 什么时候应该静默？
  - 如何避免过度或不足？

挑战 4: 成本控制
  - 每次调用主力模型成本高
  - 需要在成本和质量间平衡
```

### 1.2 传统方案的局限

**方案 A: 全量处理**
```
每条消息都用主力模型处理
  ↓
优点: 不会漏掉任何消息
缺点: 成本极高，大量无效处理
```

**方案 B: 简单过滤**
```
关键词匹配 + 简单规则
  ↓
优点: 成本低
缺点: 灵活性差，容易误判
```

**方案 C: 固定模式匹配**
```
预设 N 种模式，逐个匹配
  ↓
优点: 相对明确
缺点: 僵化，无法处理未知情况，失去 LLM 优势
```

## 二、Context-Mode 的解决方案

### 2.1 核心思想

```
不是"匹配模式"，而是"理解上下文"

不是"查表决策"，而是"推导策略"

不是"固定规则"，而是"灵活判断"
```

### 2.2 架构设计

```
┌─────────────────────────────────────────────────────┐
│                   群聊消息流                         │
└─────────────────┬───────────────────────────────────┘
                  ↓
         ┌────────────────────┐
         │  辅助会话           │
         │  (便宜模型)         │
         │                    │
         │  职责:             │
         │  1. 理解交互特征   │
         │  2. 判断参与意愿   │
         │  3. 评估重要性     │
         │  4. 决定折叠       │
         └────────┬───────────┘
                  ↓
          消息标注 + 折叠决策
                  ↓
    ┌─────────────┴─────────────┐
    ↓                           ↓
  折叠                     进入主队列
  (低重要性)                (需要处理)
    ↓                           ↓
  压缩存储              ┌────────────────┐
                       │  主会话         │
                       │  (主力模型)     │
                       │                │
                       │  职责:         │
                       │  1. 执行策略   │
                       │  2. 实际响应   │
                       │  3. 深度处理   │
                       └────────────────┘
```

### 2.3 关键机制

#### 机制 1: 交互理解

```
不是问"这是哪种形态？"
而是问"这个交互有什么特征？"

通过 5 个核心维度 + 10 个状态属性
完整描述交互的上下文
```

#### 机制 2: 参与决策

```
不是固定规则"if X then Y"
而是基于特征推导"考虑 A/B/C 因素，判断是否参与"

保留灵活性：相同特征可能有不同决策
```

#### 机制 3: 消息折叠

```
低重要性消息折叠
主会话只看摘要
需要时按需展开

节省 60%+ token
```

#### 机制 4: 交互存储

```
交互作为一等公民
持久化到关系级目录
支持检索和引用

知识沉淀，可追溯
```

## 三、系统组成

### 3.1 核心概念

#### 交互 (Interaction)

```
群聊中的最小意义单元

特征：
  - 有明确的起点和（潜在的）终点
  - 有一组参与者
  - 有一个主题或目标
  - 包含一系列相关消息
```

#### 核心维度 (Dimensions)

```
5 个维度定义交互的本质：

1. 参与者结构 - 谁在和谁交流
2. 交互意图 - 想要达成什么
3. 时间模式 - 如何在时间上展开
4. 结构化程度 - 是否有预定流程
5. 上下文依赖性 - 与历史的关系
```

#### 状态属性 (Attributes)

```
10 个属性描述交互的当前状态：

动态属性：
  - 紧急程度
  - 情绪基调
  - 信息完整性
  - 参与活跃度
  - 共识程度（讨论类）
  - 进展阶段（协作类）

上下文属性：
  - 话题专业性
  - 发起者权限
  - AI 相关性
  - 外部依赖
```

### 3.2 双会话机制

#### 辅助会话 (Auxiliary Session)

```
使用便宜模型（如 DeepSeek V3 / Haiku）

职责：
  1. 交互理解 - 识别维度和属性
  2. 参与决策 - 判断是否需要主会话处理
  3. 重要性评分 - 0-10 分
  4. 折叠决策 - 判断是否折叠
  5. 交互追踪 - 追踪交互演进

输出：
  - 消息标注（维度、属性、重要性、策略建议）
  - 折叠决策
```

#### 主会话 (Main Session)

```
使用主力模型（如 Claude Opus / GPT-4）

职责：
  1. 读取辅助会话的标注
  2. 验证和调整决策（可覆盖）
  3. 执行响应策略
  4. 深度处理复杂任务
  5. 反馈结果给辅助会话

输入：
  - 折叠后的消息流（摘要+重要消息）
  - 辅助会话的标注
```

### 3.3 提示词体系

```
prompts/
├── auxiliary/
│   ├── base.md                      # 基础角色和职责
│   ├── interaction-understanding.md # 交互理解指南
│   ├── participation-decision.md    # 参与决策框架
│   └── folding-decision.md          # 折叠决策标准
└── main/
    ├── base.md                      # 基础角色和职责
    ├── strategy-execution.md        # 策略执行指南
    └── context-assembly.md          # 上下文组装规则
```

**关键**：
- 提供方法论和框架
- 提供常见模式作为参考（非强制）
- 保留 AI 的判断空间

## 四、工作流程

### 4.1 消息处理流程

```
[步骤 1] 消息到达
  ↓
  新消息进入辅助队列

[步骤 2] 辅助会话处理
  ↓
  加载提示词:
    - auxiliary/base.md
    - auxiliary/interaction-understanding.md
    - auxiliary/participation-decision.md
  ↓
  理解交互:
    - 识别或创建交互
    - 评估维度和属性
  ↓
  参与决策:
    - 判断 AI 是否应该参与
    - 确定参与意愿
  ↓
  评估重要性:
    - 打分 0-10
  ↓
  折叠决策:
    - 重要性 ≤ 3 → 折叠
  ↓
  写入标注

[步骤 3] 消息分流
  ↓
  if 需要主会话处理:
    进入主队列（按优先级）
  else:
    折叠存储

[步骤 4] 主会话处理
  ↓
  加载提示词:
    - main/base.md
    - main/strategy-execution.md
  ↓
  读取上下文:
    - 折叠的消息（仅摘要）
    - 重要消息（完整内容）
    - 辅助会话标注
  ↓
  执行策略:
    - 根据标注推导策略
    - 可覆盖辅助会话的建议
  ↓
  实际响应

[步骤 5] 反馈
  ↓
  通知辅助会话处理结果
  更新交互状态
```

### 4.2 辅助会话的判断示例

**场景**: 用户发送 "@AI 这个报错怎么解决？"

```
辅助会话思考过程：

1. 理解交互
   维度:
     - 参与者结构: 单人→群
     - 交互意图: 信息获取
     - 时间模式: 实时同步
     - 结构化程度: 自由对话
     - 上下文依赖性: 独立
   
   属性:
     - 紧急程度: 正常
     - 情绪基调: [中性]
     - 信息完整性: 完整（问题描述清晰）
     - AI 相关性: 必须 AI（明确 @AI）
     - 话题专业性: 技术

2. 参与决策
   - 被 @AI → 强制参与
   - 问题清晰 → 无需等待
   - 技术问题 → 属于职责范围
   
   决策: 必须参与

3. 重要性评分
   - @AI: +3
   - 技术问题: +2
   - 信息完整: +1
   
   评分: 8/10

4. 折叠决策
   - 重要性 8 > 3
   
   决策: 不折叠

5. 策略建议
   - 信息完整 → 直接回答
   - 无需等待或引导
   
   建议策略: 直接回答（S2）

输出标注:
{
  "interactionId": "int-123",
  "dimensions": {...},
  "attributes": {...},
  "participationIntent": "我的职责",
  "importance": 8,
  "folded": false,
  "actionStrategy": "S2-直接回答",
  "reason": "用户明确 @AI 求助，问题清晰完整"
}
```

## 五、核心优势

### 5.1 灵活性

```
✅ 可处理未知情况
   即使没有预设模式，也能基于维度推导策略

✅ 相同情况可以有不同策略
   考虑更多上下文因素，不是固定映射

✅ 支动态扩展
   新增维度/属性不需要重写规则
```

### 5.2 成本优化

```
✅ 双会话降低成本
   辅助会话用便宜模型，节省 70%+ API 成本

✅ 消息折叠
   低重要性消息折叠，主会话 token 减少 60%+

✅ 智能过滤
   无关消息不进入主队列，避免浪费
```

### 5.3 知识沉淀

```
✅ 交互存储
   交互作为一等公民持久化

✅ 可检索可引用
   支持按话题、时间、维度检索

✅ 经验积累
   常见模式可以沉淀为参考库
```

### 5.4 可观测性

```
✅ 决策可追溯
   每个决策都有明确的理由

✅ 可调试可优化
   可以分析辅助会话的判断质量

✅ 可人工干预
   用户可以强制唤醒或调整策略
```

## 六、与固定模式的对比

| 维度 | Context-Mode（本方案） | 固定模式方案 |
|------|----------------------|-------------|
| **决策方式** | 理解上下文 → 推导策略 | 匹配模式 → 查表 |
| **灵活性** | 高（可处理未知情况） | 低（只能处理预设） |
| **模型利用** | 充分发挥 LLM 理解能力 | 仅用于文本生成 |
| **维护成本** | 低（方法论稳定） | 高（模式库易过时） |
| **扩展性** | 强（新增维度即可） | 弱（需要枚举新模式） |
| **确定性** | 较低（灵活的代价） | 高（固定映射） |
| **适用场景** | 复杂多变的群聊 | 简单确定的场景 |
