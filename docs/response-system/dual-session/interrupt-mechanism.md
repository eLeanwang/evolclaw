## 一、为什么需要打断

主会话使用慢模型（如 Opus），处理一个批次可能耗时数分钟。这期间若有**紧急消息**到达（如"生产环境崩了"），不能让它排队等慢批次跑完。打断机制让辅助会话能中止主会话当前处理、立即转入紧急消息。

打断是**例外路径**，不是常态。绝大多数消息通过 `append`（追加到主队列末尾）正常排队。

---

## 二、触发条件

打断发生**当且仅当**同时满足以下全部条件：

1. `interruptEnabled === true`（配置开关，默认 true）
2. 辅助会话判断需要打断，输出 `interrupt: true`
3. 主会话正在处理：`status === 'processing'`
4. 当前被打断的批次未满：`currentBatchSize < 50`

任一不满足 → 退化为 `append`（消息追加到主队列末尾，不打断）。

> **条件 4 与"打断时全量提取"（见 §5）的关系**：条件 4 判断的是**被打断的那个旧批次**大小——旧批次已满（≥50）说明主会话已在处理一大批，再打断收益低、成本高，故不打断。而 §5 的 100 条/20k 上限是**打断成立后重新提取新批次**时用的特殊上限。两者作用于不同对象，不矛盾。

---

## 三、硬 abort 语义（P0-5）

打断是**硬打断**：调用 base agent 的 `agent.interrupt(sessionId)`，其内部调用 SDK 的 `sdkStream.interrupt()`，**中止当前正在进行的 API 请求（abort）**。

关键后果——**旧批次的处理续体被中止，不会继续往下跑**：

- 主会话 `process(batch)` 此刻正 `await callModel(batch)`；
- abort 使该 await **抛错中止**，`process()` 不会执行到后续的 `extractSummary` / `processFeedback` / `completeBatch`；
- 因此**旧批次不会产生反馈、不会 completeBatch、不会清空新批次的 processing 状态**。

这是 §7 串行化成立的前提：正因为 abort 让旧续体整体中止，才不存在"旧续体与新批次并发写同一状态"的竞态。

> **实现注意**：`interrupt()` 只把 `status` 设为 idle 是**不够**的——单设状态不会中断正在进行的 `await callModel`。必须真正调用 abort。若某处伪代码只写了 `status = 'idle'`，视为对本文的失真简写，实现须补齐硬 abort。

---

## 四、被打断批次的去向（P0-6）

设主会话正在处理批次 A，被打断，新消息为 B、C、D。

**A 不回灌**：
- `interrupt()` **不**把 A 回灌主队列，**不**回灌 `currentBatch`；
- A 只存在于**主会话的上下文**中（模型已读过这些消息）；
- 新批次 = 主队列剩余消息 + 新消息，**只含 B/C/D**，不含 A。

**主会话事实上在处理全集**：
- 虽然新批次是 [B, C, D]，但 A 仍在上下文中可被参考；
- 主会话实际处理的是 **[A(上下文) + B, C, D(新批次)]**；
- 如何对待 A，由 `previousMessageStrategy` 通过提示词指导（见 §6）。

**A 不会丢也不会重复清理**：
- A 在辅助队列已标记 TRANSFERRED，不会重新进入辅助判断；
- A 靠主会话在同一 turn 内从上下文自行处理，不依赖队列层重投。

---

## 五、打断时的特殊提取（P1-3）

**普通场景**：批次按 ≤50 条提取（`extractBatch`）。

**打断场景**：一次性提取**主队列全部消息**，上限放宽为：
- 最多最新 **100 条**；
- 且总大小 ≤ **20k 字节**；
- 超出的更早/超大消息留在队列继续排队。

**原因**：若打断后仍只提取前 50 条，而队列已积压 60 条，则排在末尾的紧急消息 D 落在第 61 位、不在新批次里，打断形同失效。打断场景本就意味着消息紧急且重要，需保证紧急消息一定在当前批次中，故放宽上限。100 条/20k 的限制防止单批次过大。

---

## 六、被打断消息的处理策略（P0-6）

辅助会话在 `interrupt: true` 时必须给出 `previousMessageStrategy`，三选一：

| 策略 | 语义 |
|------|------|
| `ignore` | 忽略被打断的消息，只处理新消息 |
| `defer` | 先处理新消息，完成后再处理被打断的消息 |
| `continue` | 继续处理被打断的消息，但考虑新消息的内容 |

**关键定性——这三种策略都是提示词层的处理建议，不是队列层机制**：

- 打断发生时，主会话系统提示词注入一段【打断通知】，只含**打断原因 + 处理建议的文字描述**，不枚举被打断的具体消息、不浪费 token；
- 特别地，**`defer` 没有队列层的"稍后重投"机制**——它不把旧消息重新入队、不设置延迟重投。`defer` 完全依赖主会话在**同一个 turn 内**，处理完新消息后，自行从上下文把旧消息捞回来处理；
- 因此三种策略在代码层是**同一条路径**（都不回灌队列），差异仅在注入的建议文字。

【打断通知】示例（defer）：
```
【打断通知】
原因：紧急问题需要立即处理。
处理建议：先处理新消息，完成后再处理之前的消息。
```

## 七、副作用不可撤回（P0-5）

打断**无法撤回**已经发生的副作用：
- 已发送的回复（哪怕只发了半截）无法收回；
- 已执行的工具调用（改文件、跑命令）无法回滚。

这是硬打断的**固有特性，不是设计缺陷**。应对方式是**在决策层规避，而非在代码层做幂等/事务兜底**：
- 辅助会话**谨慎决定是否打断**（打断是例外路径，紧急才用）；
- 主会话在执行破坏性操作前，先确认消息未过期；发送回复前，检查是否有更新的消息。

---

## 八、并发与时序（P1-6）

打断机制**不引入并发写状态的竞态**，因为整个双会话是队列串行化的：

1. **所有触发都经过队列**：AUN 消息、主会话反馈都追加到辅助队列尾部，不直接触发处理；
2. **辅助会话串行处理**：一次一个批次，处理完再取下一批，不会有两个 LLM 调用同时进行；
3. **状态更新顺序明确**：辅助处理完 → 更新队列状态 → 投递主队列 → 主会话处理完 → 生成反馈 → 追加辅助队列；
4. **打断不破坏串行化**：§3 的硬 abort 使旧续体整体中止，不会与新批次并发写 `status` / `processing` / feedback。

因此不需要 generation id、epoch 标记或幂等反馈这类额外的代码层并发保护——串行化 + 硬 abort 已覆盖。

## 九、完整时序示例

```
T0:  正常消息 A 投递主队列，主会话开始处理 A（预计 5 分钟）
T2:  紧急消息 D 到达辅助队列，命中紧急关键词，立即触发辅助会话
T2.5 辅助判断：transfer + interrupt=true, previousMessageStrategy=ignore
       → mainQueue.interrupt([D])
T2.6 打断守卫：主会话 processing？是；旧批次 <50？是 → 打断成立
T2.7 硬 abort：agent.interrupt() → 旧 process(A) 的 callModel 抛错中止
       → 不 feedback、不 completeBatch；A 仅留在上下文
T2.8 D 追加主队列；特殊提取全部（≤100/20k）→ 新批次含 D（及其他积压）
T2.9 主会话处理新批次：上下文有 A，注入【打断通知：忽略之前消息】
       → 只回复 D → 生成总结 → 反馈辅助会话
```
