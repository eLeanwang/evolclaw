## 一、核心需求

### 1.1 群聊响应的挑战

**用户描述**:
```
群聊场景下的问题：
1. 消息量大，token 消耗高
2. 上下文复杂（多人对话）
3. 需要判断参与时机
4. 需要节省成本
```

**解决方案**:
双会话机制 - 辅助会话（便宜模型）预处理 + 主会话（主力模型）精准响应

---

### 1.2 响应模式的核心思路

**用户原话**:
```
"这个我们可以这样，就是那个辅助会话输出交互的类型。
然后呢，不同的交互类型。它就是交互类型是个参数值，
这个呢会被作为 ECK vars 加入到这个主会话中，
主会话根据这个去加载。加载提示词。
就是说不同的交互类型，它可能有不同的提示词。"
```

**关键决策**:
- 辅助会话输出交互类型
- 交互类型作为 ECK vars 传递
- 主会话根据交互类型动态加载提示词

**问题**: 动态切换系统提示词会导致 Cache 失效

**最终方案**: 固定系统提示词（仅索引）+ 策略提示词按需加载（注入到用户消息）

---

## 二、核心机制澄清

### 2.1 交互形态 → 行动策略体系

#### 澄清 1: 体系的本质（重要转折）⭐

**用户原话**:
```
"关于交互形态->行动策略,这一套体系,我们的重点是建立体系。
完善具体的交互形态和行动策略应该属于系统本身需要去完善的，
例如群聊每天可以总结一下要不要调整自己的交互形态和行动策略。

所以我们的体系本身是需要能够自我优化自己的交互形态->行动策略体系。
也就是说现在有什么交互形态和交互策略是否完备不是当前最重要的，
虽然我们需要初步的设计一套合理的，但是后续可以自我进化的机制才是重点。"
```

**关键转变**:
- ❌ 从"设计完备的 35 种形态 + 21 种策略"
- ✅ 到"建立可以自我进化的框架"

**设原则**:
1. 提供初始种子（10-15 种核心形态和策略）
2. 建立进化机制（每日评估、发现问题、优化调整）
3. 支持关系级定制（每个群/人可以有自己的优化）

---

### 2.2 辅助会话功能边界（严格限制）⭐

#### 澄清 2: 输入输出边界

**用户原话**:
```
"关于辅助会话的功能边界:
1. 辅助会话的输入是来自aun的消息。而辅助会话的输出是给到主会话的消息队列。
2. 辅助会话是不会输出到对端的！
3. 辅助会话应该限制他可以用的工具和读写的文档范围权限，
   以防止辅助会话因为模型能力弱而出现错误的操作。"
```

**核心限制**:
- ✅ 输入: AUN 消息
- ✅ 输出: 结构化 JSON（给主会话消息队列）
- ❌ **绝不直接回复对端！**
- ❌ **绝不写文件！**
- ❌ **工具权限限制为只读历史**

---

#### 澄清 3: 辅助会话的四大职责

**用户原话**:
```
"辅助会话的主要目标是:
1. 交互形态的判断
2. 行动策略的选择
3. 主会话的模型选择（主会话有一个主模型，
   但是考虑到可能有声音,视频,图片的处理需要，可以选择不同的模型）"
```

**完整职责**:
1. 交互形态判断
2. 行动策略选择
3. 主会话模型选择 ⭐（新增）
4. 消息预处理（多模态、信息补全）

---

#### 澄清 4: 主会话才是执行者

**用户原话**:
```
"主会话才是完成具体任务的操作。
完成对端的回复。包括引导交互等对话。
总之,辅助会话的功能边界需要明确。"
```

**主会话职责**:
- 实际任务执行
- 对端回复
- 引导对话
- 完整工具权限

---

### 2.3 辅助会话预处理能力

#### 澄清 5: 多模态预处理

**用户原话**:
```
"辅助会话是提前处理,尤其是可以帮助完成未完整信息,
多模态信息的(例如图片,视频和文件的预处理,
可以调用不同的模型来进行处理)。
当然这本身也是交互形态的一种和行动策略的一种。"
```

**理解**:
- 多模态预处理是辅助会话的职责
- 属于现有形态（A3）+ 策略（S6）的扩展
- 不需要新增交互形态

**实现**:
- 图片 → OCR / 视觉理解
- 文件 → 提取摘要
- 视频 → 关键帧 / 转文字

---

#### 澄清 6: 消息折叠

**用户原话**:
```
"辅助会话的提前处理,是可以帮助做一些折叠的
(需要过滤的消息,但是仍然会被压缩折叠,并给出指引,
这样主会话如果需要查看这些消息仍然可以通过工具查看到)。
这个能不能算到一个交互形态的行动策略?"
```

**理解**:
- 折叠不是独立的交互形态
- 折叠是行动策略的输出维度之一（存储决策）
- 行动策略有三个输出维度：
  1. 参与决策（参与/不参与）
  2. 消息处理（原样/重写/压缩）
  3. 存储决策（完整/折叠/不存储）

---

### 2.4 单聊和群聊通用

#### 澄清 7: 应用场景

**用户原话**:
```
"双会话响应模式可以应用于单聊和群聊。"
```

**场景对比**:
- **群聊**: 过滤无关消息、判断参与时机、理解复杂上下文
- **单聊**: 预处理消息、路由简单/复杂问题、成本优化

---

### 2.5 队列操作方式

#### 澄清 8: 直接操作 vs 工具调用

**用户原话**:
```
"辅助会话对主会话的消息队列的操作是否可以直接在代码层面操作而不需要通过工具?
这样可以极大的辅助会话节省工具调用层次数加快辅助会话的处理速度"
```

**决策**: 使用结构化输出（非工具调用）

**理由**:
- ✅ 性能优先（辅助会话高频调用）
- ✅ 批量处理（一次处理多条消息）
- ✅ 操作简单（insert/ignore/fold 相对固定）

**实现**:
```typescript
// 辅助会话输出结构化 JSON
interface AuxiliaryOutput {
  decisions: AuxiliaryDecision[];
}

// 代码层面直接解析和操作队列
async function processAuxiliaryOutput(output: AuxiliaryOutput) {
  for (const decision of output.decisions) {
    if (decision.action === 'insert') {
      mainQueue.insert({...});
    }
    // ...
  }
}
```

## 三、架构设计决策

### 3.1 Cache 稳定性问题

#### 问题发现

**用户指出**:
```
"这个方案也有问题,会导致群聊的系统提示词在频繁的切换吧?
这会导致cache急剧恶化"
```

**问题分析**:
```
消息 1: 加载 S2 策略 → Cache 建立
消息 2: 加载 S7 策略 → Cache 失效
消息 3: 加载 S2 策略 → Cache 又失效
```

#### 最终方案

**设计**:
```
系统提示词（固定，可缓存）:
  - 仅包含策略索引
  - 永不改变

策略提示词（按需加载）:
  - 读取文件
  - 注入到用户消息
  - 不影响系统提示词 Cache
```

**优势**:
- ✅ Cache 100% 稳定
- ✅ 按需加载，Token 优化
- ✅ 策略独立维护

---

### 3.2 消息队列设计

#### 辅助会话消息队列

**批次触发条件**:
```
满足任一即触发:
1. 延迟 3 秒（等待连续消息）
2. 最长等待 15 秒（避免积压）
3. 紧急关键词（立即触发）
4. 队列满 50 条
```

#### 主会话消息队列

**特性**:
- 优先级队列（normal / high / interrupt）
- 支持打断
- 可被辅助会话操作

## 四、关键冲突和决策

### 冲突 1: 完备枚举 vs 自我进化

**初始方向**: 设计 35 种形态 + 21 种策略（完备枚举）

**用户澄清**: 重点是建立可以自我进化的体系

**最终决策**: 
- 提供初始种子（10-15 种）
- 建立进化机制
- 支持关系级定制

**影响**:
- 文档重点从"完整的形态/策略列表"转向"进化框架"
- 不追求初始完备性

---

### 冲突 2: 工具调用 vs 结构化输出

**初始设计**: 辅助会话通过工具调用操作主队列

**用户质疑**: 工具调用层次多，影响性能

**最终决策**: 结构化输出 + 代码层面直接操作

**影响**:
- 辅助会话输出格式改为纯 JSON
- 代码层面解析并操作队列
- 性能更优

---

### 冲突 3: 策略加载方式

**初始方向 1**: 全部加载到系统提示词（~20k tokens）

**初始方向 2**: 注入到用户消息

**用户反对**:
```
1. "这个方案不好!行动策略的提示词,这个明显不应该插入到消息提示词中!!!!"
2. "按需读取会出现重复加载的情况吗?"
3. "不要想着从消息提示词中添加!也不要想着用硬代码来搞定,应该是通过系统提示词来的!"
4. "能不能在系统提示词中提示说如果行动策略的文件没有加载就读取xxx"
```

**关键澄清**:
```
问题: 按需加载会重复加载（批次内 [S2, S7, S2] 会读 S2 两次）
两个错误方案:
  - 硬编码去重（要求辅助会话输出更结构化，容错率低）
  - 注入到用户消息（用户强烈反对）
  
正确方案:
  - 系统提示词中包含策略文件路径映射
  - 主会话模型自己判断是否需要 Read
  - 利用模型的会话内记忆能力（方案B: 首次读取后记住）
```

**最终决策**: 按需加载 + 会话内记忆

**实现方式**:
```markdown
主会话系统提示词中包含:

## 行动策略按需加载

策略文件路径映射:
- S1 → $KITS_DOCS/strategies/S1-emergency-response.md
- S2 → $KITS_DOCS/strategies/S2-direct-answer.md
...

加载方式:
1. 先浏览所有消息的策略 ID
2. 识别你不确定的策略
3. Read 对应的策略文件
4. 会话内记住已读策略，不重复读取
```

**优势**:
- ✅ Cache 稳定（系统提示词只有路径映射，固定内容）
- ✅ 按需加载（不常用策略不加载，节省 token）
- ✅ 避免重复（模型会话内记忆，首次读取后记住）
- ✅ 灵活容错（不依赖硬编码结构化输出，模型自主判断）
- ✅ 利用模型能力（而不是通过代码实现）

**影响**:
- 策略提示词独立文件，按需读取
- 不破坏 Cache
- 完全交给模型处理，不需要硬编码逻辑
