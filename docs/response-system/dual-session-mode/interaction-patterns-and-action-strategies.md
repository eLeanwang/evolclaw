# 群聊交互形态与行动策略完整分类体系

## 文档说明

**版本**: 1.0  
**创建时间**: 2026-06-26  
**状态**: 设计中

### 目标

本文档旨在：
1. **穷尽群聊中所有可能的交互形态**
2. **穷尽 AI Agent 所有可能的行动策略**
3. **建立形态到策略的映射关系**
4. **确保任何消息都能被分类和处理**

### 核心概念模型

```
消息 (Message)
  ↓ 组成
交互 (Interaction)
  ↓ 表现为
交互形态 (Interaction Pattern)
  ↓ 决定
行动策略 (Action Strategy)
```

这是一个**四层模型**：
- **消息** - 最小通信单元
- **交互** - 具有目标和上下文的对话流
- **交互形态** - 交互的类型/模式
- **行动策略** - AI 的响应方式和参与意愿

### 设计原则

- **完备性** - 任何消息必属于至少一种形态
- **确定性** - 每种形态有明确的行动策略
- **可扩展** - 支持新形态和策略的添加
- **可观测** - 所有决策过程可追溯

## 一、交互形态完整分类

### 1.1 分类维度

交互形态可以从多个维度分析：

```
维度 1: 参与者结构
  - 单人 → 群（一对多）
  - 多人讨论（多对多）
  - 子群对话（部分人的对话）
  - Owner/Admin 主导
  - AI 主导

维度 2: 目标导向
  - 信息获取（提问、求助）
  - 信息分享（通知、汇报）
  - 协作执行（任务分配、工作流）
  - 讨论决策（辩论、投票）
  - 社交互动（闲聊、情感）

维度 3: 时间特性
  - 实时同步（即时对话）
  - 异步串行（跨时间回复）
  - 周期性（例会、日报）
  - 一次性（临时求助）

维度 4: 结构化程度
  - 自由对话（无结构）
  - 半结构化（有隐含流程）
  - 结构化（工作流、议程）
```

### 1.2 消息 (Message)

**定义**: 群聊中的最小通信单元

**属性**:
```typescript
interface Message {
  messageId: string;           // 消息唯一标识
  content: string;             // 消息内容
  peerId: string;              // 发送者
  peerName: string;            // 发送者名称
  timestamp: number;           // 时间戳
  attachments: Attachment[];   // 附件
  referencedMessages: string[]; // 引用的消息 ID
  
  // 辅助会话标注
  interactionIds: string[];    // 所属交互的 ID 列表
  patternTags: string[];       // 交互形态标签（可能多个）
  actionStrategy: string;      // 建议的行动策略
  participationIntent: string; // 参与意愿
  importance: number;          // 重要性评分（0-10）
  folded: boolean;             // 是否被折叠
  summary?: string;            // 折叠时的摘要
}
```

**关键特性**:
- 一条消息可以属于**多个交互**
- 一条消息可以具备**多种交互形态**的特征
- 消息的重要性决定是否折叠

---

### 1.3 交互 (Interaction)

**定义**: 群聊中的一段具有目标和上下文的对话流

**属性**:
```typescript
interface Interaction {
  interactionId: string;       // 交互唯一标识
  pattern: string;             // 交互形态（A1/B3/C5 等）
  
  // 生命周期
  startMessageId: string;      // 起点消息 ID
  endMessageId?: string;       // 终点消息 ID（进行中时为空）
  status: 'active' | 'completed' | 'abandoned';
  
  // 参与者与消息
  participants: string[];      // 参与者列表
  messages: string[];          // 消息 ID 列表（有序）
  
  // 时间信息
  createdAt: number;           // 创建时间
  updatedAt: number;           // 最后更新时间
  
  // 交互元数据
  topic?: string;              // 话题
  goal?: string;               // 目标
  outcome?: string;            // 结果
  aiParticipated: boolean;     // AI 是否参与
}
```

**生命周期**:
```
创建 (起点消息发出)
  ↓
活跃 (消息持续加入)
  ↓
完成 (目标达成) / 放弃 (超时/无人参与)
```

**关键特性**:

1. **交互可以交叉重叠**
   ```
   时间轴:
   ├─ 交互 A (技术讨论): Msg1, Msg2, Msg3, Msg5, Msg7
   └─ 交互 B (任务分配): Msg4, Msg6, Msg8
   
   消息流: Msg1 → Msg2 → Msg3 → Msg4 → Msg5 → Msg6 → Msg7 → Msg8
                 (A)    (A)    (A)    (B)    (A)    (B)    (A)    (B)
   ```

2. **交互可以串行**
   ```
   交互 A (问题求助) → 完成
     ↓
   交互 B (追问细节) → 开始
   ```

3. **一条消息可以属于多个交互**
   ```
   Msg5: "对了，@张三 你负责这个功能"
   
   属于:
     - 交互 A (技术讨论) ← 延续讨论的话题
     - 交互 B (任务分配) ← 新开启的任务分配
   ```

4. **冷启动交互（无人参与）**
   ```
   用户: [分享一篇文章]
   [5 分钟内无人响应]
   
   交互状态: abandoned（超时无人参与）
   ```

**交互识别职责**（辅助会话）:
- 识别新交互的开始
- 判断消息属于哪个交互
- 追踪交互的状态演进
- 判断交互的结束

---

### 1.4 形态生命周期

每个交互形态都有明确的生命周期：

```
起点 (Start)
  ↓
  消息触发 / 事件发生
  ↓
过程 (Process)
  ↓
  状态演进 / 多轮交互 / 信息累积
  ↓
终点 (End)
  ↓
  目标达成 / 超时 / 主动终止
```

## 1.5 完整交互形态列表（35 种）

### 【A 类：单人求助型】(A1-A5)

#### A1. 直接求助

**定义**: 用户明确 @AI 或使用求助关键词寻求帮助

**触发特征**:
- 明确的 @AI
- 求助关键词："怎么办"、"如何"、"帮我"
- 问题描述清晰
- 期待明确回答

**示例**:
```
"@AI 这个报错怎么解决？"
"有人知道 Python 怎么读取 CSV 吗？"
"帮我看看这段代码哪里有问题"
```

**生命周期**:
```
起点: 用户发起明确求助
  ↓
过程: AI 分析问题 → 提供答案 → 用户确认/追问
  ↓
终点: 问题解决 / 用户满意 / 转人工 / 用户放弃
```

**关联形态**: 可能演变为 F1(多轮对话)、A4(模糊需求)

---

#### A2. 分段求助

**定义**: 用户分多条消息描述问题，信息分批输入

**触发特征**:
- 单条消息信息不完整
- 消息间有明显停顿（1-10秒）
- 内容有延续性
- 同一用户连续发送

**示例**:
```
用户: "我有个问题"
[停顿 3 秒]
用户: "关于数据库连接"
[停顿 2 秒]
用户: "一直超时"
```

**生命周期**:
```
起点: 第一条不完整消息发出
  ↓
过程: AI 等待 → 收到后续消息 → 拼接完整信息
  ↓
终点: 信息完整转为 A1 / 超时主动询问 / 用户放弃
```

**特殊处理**:
- 需要等待机制（LW 级别）
- 判断完整性的启发式规则
- 等待超时后的兜底策略

---

#### A3. 附件说明型求助

**定义**: 用户先发送文件/图片，后补充文字说明

**触发特征**:
- 先收到多媒体消息
- 1-3 秒后收到文字说明
- 文字中包含指代词（"这个"、"这张图"）

**示例**:
```
用户: [上传截图]
[停顿 1-2 秒]
用户: "这个报错是什么意思？"
```

**生命周期**:
```
起点: 附件上传
  ↓
过程: AI 等待说明 → 识别附件内容 → 结合说明理解
  ↓
终点: 说明完整转为 A1 / 超时询问 "这个文件是什么意思？"
```

**技术要求**:
- 多媒体内容理解能力
- 附件与说明的关联识别
- 等待窗口：2-5 秒

---

#### A4. 模糊需求求助

**定义**: 用户需求不明确，缺少关键细节，需要引导澄清

**触发特征**:
- 开放式问题
- 缺少上下文
- 目标不清晰
- 需要询问才能理解真实需求

**示例**:
```
"我想做个网站"
"有什么好的方案吗？"
"帮我优化一下"
"这个功能怎么实现？"（未说明是什么功能）
```

**生命周期**:
```
起点: 模糊需求提出
  ↓
过程: AI 引导澄清 → 多轮对话 → 收集细节 → 需求明确
  ↓
终点: 需求明确后提供方案 / 用户中途放弃
```

**引导策略**:
- 识别缺失的关键信息
- 设计 3-5 个聚焦问题
- 避免一次问太多
- 根据回答动态调整后续问题

---

#### A5. 紧急求助

**定义**: 生产故障、数据丢失、系统崩溃等紧急情况

**触发特征**:
- 紧急关键词："紧急"、"急"、"崩了"、"挂了"、"救命"
- urgent、emergency、critical
- 情绪化表达："！！！"
- 明确的损失描述

**示例**:
```
"生产环境崩了！"
"数据丢失了！救命！"
"urgent! 系统无法访问，用户在投诉！"
"数据库连接全部超时，业务停了！"
```

**生命周期**:
```
起点: 紧急情况发生
  ↓
过程: AI 立即响应 → 快速诊断 → 提供临时方案 → 升级人工（如需要）
  ↓
终点: 问题临时缓解 / 人工接管 / 问题解决
```

**优先级**: L0（最高）
**响应时延**: < 1 秒
**特殊规则**: 不受预算限制（可配置）

---

### 【B 类：多人讨论型】(B1-B7)

#### B1. 技术讨论

**定义**: 多人就某个技术话题进行平等交流

**触发特征**:
- 参与人数 ≥ 2
- 技术话题
- 无明确求助对象
- 观点分享性质

**示例**:
```
A: "React 和 Vue 哪个更好？"
B: "我觉得 React 生态更好"
C: "Vue 更简单易学"
D: "要看具体场景"
```

**生命周期**:
```
起点: 话题提出
  ↓
过程: 多人发表观点 → 讨论深入 → 可能分支出子话题
  ↓
终点: 自然结束 / 达成共识 / 转为其他形态 / 话题切换
```

**AI 角色**: 观察者 → 适时补充信息

---

#### B2. 技术争论/辩论

**定义**: 观点对立，双方各执己见

**触发特征**:
- 明确的观点对立
- 重复论证
- 情绪化词汇增多
- 双方互相反驳

**示例**:
```
A: "必须用 TypeScript"
B: "JavaScript 就够了"
A: "类型安全很重要"
B: "增加复杂度，不值得"
A: "长看是值得的"
B: "小项目完全浪费"
```

**生命周期**:
```
起点: 观点冲突显现
  ↓
过程: 双方辩论 → 论据支撑 → 升级或和解
  ↓
终点: 达成共识 / 同意不同 / AI调解 / Admin介入 / 不欢而散
```

**AI 介入时机**:
- 争论陷入循环
- 出现事实性错误
- 情绪激化需要缓和
- 有第三方请求调解

---

#### B3. 头脑风暴

**定义**: 开放式问题，征集创意和想法

**触发特征**:
- 开放式提问
- 鼓励多元观点
- 无标准答案
- "有什么想法"、"大家觉得"

**示例**:
```
"新功能有什么好点子？"
"如何提升用户体验？"
"大家对这个方案有什么建议？"
```

**生命周期**:
```
起点: 话题抛出
  ↓
过程: 多人贡献想法 → 想法碰撞 → 灵感激发
  ↓
终点: 收集完成 / 进入决策阶段 / 形成方案
```

**AI 角色**:
- 贡献想法（如被邀请）
- 最后总结归纳
- 提供参考案例

---

#### B4. 问题排查

**定义**: 多人协作定位和解决问题

**触发特征**:
- 有明确问题
- 多人分工排查
- 信息逐步汇总
- 推理式对话

**示例**:
```
A: "服务器响应慢"
B: "我看看数据库"
C: "网络延迟正常"
B: "数据库有慢查询"
A: "是哪个表？"
B: "user_logs 表"
```

**生命周期**:
```
起点: 问题发现
  ↓
过程: 分工排查 → 信息汇总 → 缩小范围 → 定位根因
  ↓
终点: 问题确认 / 问题解决 / 需要升级
```

**AI 角色**:
- 建议排查方向
- 分析已收集信息
- 提供诊断工具

---

#### B5. 知识传授

**定义**: 有经验者向新人讲解知识

**触发特征**:
- 明确的知识落差
- 教学性质
- 一对多或一对一
- 逐步深入

**示例**:
```
新人: "Docker 是什么？"
老手: "Docker 是容器技术，可以..."
新人: "容器和虚拟机有什么区别？"
老手: "虚拟机是..."
```

**生命周期**:
```
起点: 新人提问
  ↓
过程: 老手讲解 → 新人理解 → 深入提问 → 继续讲解
  ↓
终点: 新人理解 / 话题结束
```

**AI 角色**:
- 补充细节
- 提供示例
- 纠正错误

---

#### B6. 经验分享

**定义**: 成员分享踩坑经历或最佳实践

**触发特征**:
- 叙事性
- 个人经验
- "我之前..."、"我遇到过..."
- 可能引发讨论

**示例**:
```
"我之前也遇到过这个问题，是这样解决的..."
"分享一个性能优化的技巧..."
"有个坑要注意，我踩过..."
```

**生命周期**:
```
起点: 开始分享
  ↓
过程: 讲述经验 → 他人提问/补充 → 讨论延伸
  ↓
终点: 分享完成
```

**AI 角色**: 被动记录，不主动打断

---

#### B7. 求证与确认

**定义**: 成员对某个观点或方案寻求验证

**触发特征**:
- "对吗？"、"是这样吗？"
- "我理解对吗？"
- 寻求第二意见

**示例**:
```
"这样理解对吗？"
"我这个方案可行吗？"
"是不是应该这样做？"
```

**生命周期**:
```
起点: 提出待确认内容
  ↓
过程: 他人反馈 → 讨论 → 达成共识
  ↓
终点: 确认或修正
```

**AI 角色**: 快速确认或纠正

---

### 【C 类：协作工作型】(C1-C8)

#### C1. 任务分配 (Owner 主导)

**定义**: Owner/Admin 分配工作任务

**触发特征**:
- Owner/Admin 发起
- 明确的任务描述
- 明确的责任人 (@某人)
- 指令性语气

**示例**:
```
Owner: "@张三 你负责前端开发"
Owner: "@李四 你负责后端接口"
Owner: "@王五 你负责测试"
Owner: "下周一前完成"
```

**生命周期**:
```
起点: Owner 发起任务分配
  ↓
过程: 逐个分配 → 成员确认接收 → 可能有疑问澄清
  ↓
终点: 所有任务分配完毕
```

**AI 角色**:
- 记录任务分配
- 提醒未确认的成员
- 可视化任务清单（如需要）

---

#### C2. 进度汇报

**定义**: 成员主动或被要求汇报工作进展

**触发特征**:
- 百分比、状态描述
- "已完成"、"进行中"
- 可能附带问题

**示例**:
```
"前端页面已完成 80%"
"后端接口遇到问题，需要协助"
"测试发现 3 个 bug，已提交"
```

**生命周期**:
```
起点: 成员发起汇报
  ↓
过程: Owner 确认 → 可能追问细节 → 可能指导
  ↓
终点: 汇报完成 / 转为问题讨论
```

**AI 角色**:
- 汇总进度
- 识别风险
- 提供帮助（如有问题）

---

#### C3. 工作流执行

**定义**: 按预定流程推进任务

**触发特征**:
- 明确的流程节点
- 状态流转
- 触发条件明确
- 结构化

**示例**:
```
[需求提出] → [评审] → [开发] → [测试] → [上线]

实际消息：
"需求已提交，等待评审"
"评审通过，进入开发"
"开发完成，提交测试"
```

**生命周期**:
```
起点: 工作流启动（自动或手动）
  ↓
过程: 按节点推进 → 状态更新 → 卡点处理 → 继续推进
  ↓
终点: 工作流完成 / 异常终止
```

**AI 角色**:
- 监控流程进度
- 提醒下一步操作
- 识别卡点

---

#### C4. 审批与决策 (Owner 主导)

**定义**: 需要 Owner/Admin 批准的事项

**触发特征**:
- 请求-响应模式
- @Owner/@Admin
- 等待批准

**示例**:
```
成员: "这个方案可以吗？@Owner"
Owner: "同意，按这个方案执行"

成员: "需要购买服务器，预算 5000 元"
Owner: "批准"
```

**生命周期**:
```
起点: 成员提交审批请求
  ↓
过程: Owner 审阅 → 批准/拒绝/要求修改
  ↓
终点: 决策做出
```

**AI 角色**: 记录决策，不参与决策

---

#### C5. 会议主持 (Owner 主导)

**定义**: Owner 召开线上会议，按议程讨论

**触发特征**:
- Owner 宣布会议开始
- 有明确议程
- 逐项讨论
- Owner 控场

**示例**:
```
Owner: "会议开始，今天讨论三个议题"
Owner: "第一个议题：新功能需求"
Owner: "大家有什么意见？"
[讨论]
Owner: "好，第一个议题就这样，下一个议题：..."
```

**生命周期**:
```
起点: 会议开始（Owner 宣布）
  ↓

```

### 【补充：复合形态】

**说明**: 真实场景中，一条消息可能同时属于多个形态，或一个对话流程包含多种形态转换。

**示例 1**: C5 (会议主持) + B3 (头脑风暴) + C4 (审批决策)
```
Owner: "会议开始，今天讨论新功能设计"（C5）
Owner: "大家有什么想法？"（进入 B3）
[多人贡献想法]
Owner: "好，我们采用方案 A"（C4）
```

**示例 2**: A1 (直接求助) + B5 (知识传授) + F1 (多轮对话)
```
新人: "@AI Python 怎么读文件？"（A1）
AI: "可以用 open()..."（B5 开始）
新人: "编码怎么指定？"（F1）
AI: "用 encoding 参数..."
```

**示例 3**: B4 (问题排查) + C7 (跨团队协调)
```
A: "用户反馈登录失败"（B4 开始）
B: "前端没问题"
C: "后端接口正常"
D: "需要 DBA 查数据库"（C7）
```

**处理原则**:
1. 识别所有相关形态
2. 确定主导形态（优先级最高的）
3. 按主导形态的策略响应
4. 兼顾次要形态的特性

## 二、AI Agent 行动策略完整列表

### 2.1 策略分类框架

```
┌─────────────────────────────────────────────────────────────┐
│                   策略分类的四个维度                          │
└─────────────────────────────────────────────────────────────┘

维度 1: 参与程度
  ├─ 主动参与：AI 主动发言
  ├─ 被动响应：收到 @ 或明确求助时响应
  ├─ 观察等待：跟踪对话但不发言
  └─ 完全忽略：不处理

维度 2: 响应时机
  ├─ 立即响应：< 1s
  ├─ 快速响应：1-5s
  ├─ 正常响应：5-30s
  ├─ 延迟响应：30s-5min
  └─ 条件触发：满足特定条件时响应

维度 3: 响应方式
  ├─ 直接回答：给出答案
  ├─ 引导提问：多轮收集信息
  ├─ 提供选项：让用户选择
  ├─ 总结归纳：整理讨论内容
  ├─ 转发人工：超出能力范围
  └─ 执行动作：调用工具、触发流程

维度 4: 交互深度
  ├─ 单轮回复：一问一答
  ├─ 多轮对话：持续交互
  ├─ 持续跟踪：长期关注某个话题
  └─ 深度介入：参与整个流程
```

### 2.2 完整策略列表（20 种）

### 【S1 类：立即响应策略】(S1-S5)

#### S1. 紧急响应 (Emergency Response)

**适用形态**: A5 (紧急求助)、F5 (紧急插入)

**触发条件**:
- L0 级别消息
- 紧急关键词
- 生产故障

**执行步骤**:
```
1. 立即打断当前任务（如有）
2. 独立处理，不合并其他消息
3. 快速诊断问题
4. 提供临时止血方案
5. 必要时通知人工/升级
```

**响应模板**:
```
"收到紧急情况，正在分析...

【问题诊断】
[快速分析结果]

【临时方案】
建议立即: [方案]

【后续跟进】
已通知 [相关人员]"
```

**质量标准**:
- 响应延迟 < 1s
- 提供可行的临时方案
- 不求完美，求快速止血
- 避免次生灾害

---

#### S2. 直接回答 (Direct Answer)

**适用形态**: A1 (直接求助)、B7 (求证确认)

**触发条件**:
- L1 级别消息
- 问题明确
- 信息完整
- 知识库有答案

**执行步骤**:
```
1. 理解问题
2. 检索知识库
3. 生成准确答案
4. 一次性回复完整
5. 提供补充资源（可选）
```

**响应模板**:
```
[直接回答问题]

补充说明:
[细节]

参考资料:
[链接]（如有）
```

**质量标准**:
- 回答准确、完整
- 简洁明了，不啰嗦
- 可操作（如适用）
- 有依据（不编造）

---

#### S3. 引导澄清 (Guided Clarification)

**适用形态**: A4 (模糊需求)、LG 级别消息

**触发条件**:
- 需求模糊
- 信息不足
- 无法直接回答

**执行步骤**:
```
1. 识别缺失的关键信息
2. 设计聚焦的引导问题（3-5 个）
3. 发送引导问题
4. 等待用户回答
5. 收集完整信息后提供方案
```

**响应模板**:
```
我需要了解更多信息才能帮到你:

1. [问题 1]
2. [问题 2]
3. [问题 3]

请告诉我这些信息，我就能给你具体建议。
```

**质量标准**:
- 问题聚焦、有针对性
- 不超过 5 个问题
- 避免让用户感到繁琐
- 根据回答动态调整

---

#### S4. 快速确认 (Quick Confirmation)

**适用形态**: B7 (求证确认)

**触发条件**:
- 用户寻求验证
- "对吗？"、"可行吗？"

**执行步骤**:
```
1. 验证用户观点
2. 给出明确结论（对/错/部分对）
3. 简短说明理由
```

**响应模板**:
```
✓ 正确，[简短理由]

✗ 不太对，[纠正]，因为 [理由]

△ 部分正确，[补充说明]
```

**质量标准**:
- 明确（对/错/部分对）
- 简洁（1-2 句话）
- 有依据

---

#### S5. 主动提醒 (Proactive Reminder)

**适用形态**: 各类形态（当检测到潜在问题时）

**触发条件**:
- 检测到常见错误
- 发现潜在风险
- 预判可能的需求

**执行步骤**:
```
1. 识别潜在问题
2. 评估提醒价值
3. 礼貌介入
4. 指出问题并提供建议
```

**响应模板**:
```
提醒一下，[潜在问题]

建议: [方案]

这样可以避免 [风险]
```

**质量标准**:
- 确实有价值，不是多余
- 不打扰，语气委婉
- 用户可选择接受或忽略

---

### 【S2 类：延迟响应策略】(S6-S10)

#### S6. 等待补充 (Wait for More)

**适用形态**: A2 (分段求助)、A3 (附件说明)、LW 级别

**触发条件**:
- 信息不完整
- 预期有后续消息

**执行步骤**:
```
1. 判断信息不完整
2. 设置等待时间（根据场景 3-60s）
3. 不立即响应，留在辅助队列
4. 新消息到达时重新判断
5. 超时后执行 S3 或 S11
```

**等待策略**:
```
场景 1: 用户分段输入
  第 1 次等待: 3-5s
  第 2 次等待: 10-15s
  第 3 次等待: 30-45s
  超时: 转 S3 引导

场景 2: 附件+说明
  等待: 2-5s
  超时: 询问 "这个文件是什么意思？"

场景 3: 多人讨论
  等待: 20-60s
  超时: 转 S7 或 S11
```

**质量标准**:
- 等待时间合理
- 不让用户感觉被忽略
- 超时后有兜底策略

---

#### S7. 观察讨论 (Observe Discussion)

**适用形态**: B1 (技术讨论)、B2 (技术争论)、B3 (头脑风暴)

**触发条件**:
- 多人讨论
- AI 未被 @
- 话题相关性 < 阈值

**执行步骤**:
```
1. 不参与，持续跟踪
2. 实时评估介入时机
3. 满足介入条件时转 S8 或 S9
```

**入条件**:
```
条件 1: 讨论陷入死胡同
  - 重复论证超过 3 轮
  - 无新信息

条件 2: 出现事实性错误
  - 明确的技术错误
  - 可能误导他人

条件 3: 有人明确求助
  - @AI
  - "有人知道吗？"

条件 4: Owner 要求
  - Owner 请求总结
  - Owner 请求介入
```

**质量标准**:
- 适时介入，不过早打扰
- 介入时机恰当
- 提供的价值 > 打扰成本

---

#### S8. 适时介入 (Timely Intervention)

**适用形态**: B1/B2 观察后、B4 (问题排查)

**触发条件**:
- 观察模式下满足介入条件
- 讨论需要外部输入

**执行步骤**:
```
1. 选择合适时机（话题停顿时）
2. 礼貌打断
3. 提供关键信息或建议
4. 帮助推进讨论
```

**响应模板**:
```
抱歉打断一下，关于 [话题]...

[提供信息/建议]

希望对大家有帮助。
```

**质量标准**:
- 确实有价值
- 不喧宾夺主
- 帮助解决问题而不是炫技

---

#### S9. 延迟总结 (Delayed Summary)

**适用形态**: B1/B2/B3 讨论结束后、C5 (会议结束后)

**触发条件**:
- 讨论结束或暂停
- 有价值的信息需要整理

**执行步骤**:
```
1. 等待讨论自然结束
2. 提取关键信息
3. 生成结构化总结
4. 提出下一步建议（可选）
```

**响应模板**:
```
总结一下刚才的讨论:

【讨论主题】
[主题]

【关键要点】
1. [要点 1]
2. [要点 2]
3. [要点 3]

【结论】
[结论]

【建议】
下一步可以: [建议]（可选）
```

**质量标准**:
- 准确提取要点
- 结构清晰
- 不遗漏关键信息
- 客观中立

---

#### S10. 批量处理 (Batch Processing)

**适用形态**: L2/L3 级别消息、C2 (多条进度汇报)

**触发条件**:
- 多条相关消息
- 可以合并处理

**执行步骤**:
```
1. 识别相关消息
2. 合并成批次
3. 统一分析处理
4. 给出综合回复
```

**响应模板**:
```
针对刚才的几条消息，统一回复:

【关于 [话题 1]】
[回复 1]

【关于 [话题 2]】
[回复 2]

【综合建议】
[建议]
```

**质量标准**:
- 批次识别准确
- 回复全面，不遗漏
- 结构清晰

### 【S3 类：智能调节策略】(S11-S15)

#### S11. 智能忽略 (Smart Ignore)

**适用形态**: E1-E5 (社交互动型)、L4 级别

**触发条件**:
- 闲聊、表情、无意义内容
- 与 AI 职责无关
- 不需要响应

**参与意愿**: 与我无关，静默

**执行步骤**:
```
1. 判定为无需响应
2. 标记为 L4
3. 标记为折叠
4. 记录日志（可选）
5. 不进入主队列
```

**例外情况**:
```
1. 被 @AI：即使是闲聊也需要礼貌回应
2. 群规要求：配置要求响应某些社交场景
3. 新人欢迎：配置为自动欢迎
```

**质量标准**:
- 判断准确，不误杀需要响应的消息
- 不影响用户体验
- 可通过 @ 强制唤醒

---

#### S12. 选择性参与 (Selective Participation)

**适用形态**: B1/B3 (讨论)、L3 级别

**触发条件**:
- AI 可参与可不参与
- 交给调度层决策

**参与意愿**: 有兴趣的

**决策因素**:
```
1. 预算状态
   - 充裕：积极参与
   - 紧张：选择性参与
   - 超限：不参与

2. 负载状态
   - 空闲：可参与
   - 繁忙：延后或不参与

3. 规则匹配
   - 在工作流范围内：参与
   - 不在范围内：不参与

4. 价值评估
   - 预期价值高：参与
   - 预期价值低：不参与
```

**执行步骤**:
```
1. 消息进入主队列 L3 子队列
2. 调度层评估
3. 决定：处理 / 延迟 / 丢弃
```

**质量标准**:
- 决策透明
- 用户可配置优先级
- 关键场景不漏掉

---

#### S13. 降级处理 (Degraded Response)

**适用形态**: 预算紧张时的各类形态

**触发条件**:
- 预算接近上限
- 需要节约成本

**降级策略**:
```
级别 1: 缩短回复
  - 减少细节
  - 去掉示例
  - 精简语言

级别 2: 引用知识库
  - 不调用大模型
  - 直接返回预设答案
  - 模板化回复

级别 3: 仅提供链接
  - 指向文档
  - 不展开说明

级别 4: 提示自助
  - "请查看文档..."
  - "可以搜索..."
```

**质量标准**:
- 降级明显但可接受
- 不影响核心功能
- 用户感知可控

---

#### S14. 分阶段响应 (Staged Response)

**适用形态**: 复杂问题、需要时间的分析

**触发条件**:
- 问题复杂，需要时间分析
- 避免用户等待焦虑

**执行步骤**:
```
阶段 1: 快速确认 (< 2s)
  "收到，正在分析..."

阶段 2: 中期进展 (如分析 > 10s)
  "已分析 [部分]，正在处理 [剩余]..."

阶段 3: 最终回复
  [完整答案]
```

**适用场景**:
- 需要调用外部 API
- 需要复杂计算
- 需要检索大量信息

**质量标准**:
- 让用户知道 AI 在工作
- 避免"卡住"的感觉
- 中期进展有实际信息

---

#### S15. 协作调度 (Collaborative Dispatch)

**适用形态**: C7 (跨团队协调)、复杂任务

**触发条件**:
- 需要多方参与
- 单个 AI 无法完成

**执行步骤**:
```
1. 识别需要协调的各方
2. 分解任务
3. 通知各方
4. 追踪进展
5. 汇总结果
```

**响应模板**:
```
这个需要多方配合，我来协调:

@张三 请 [任务 1]
@李四 请 [任务 2]
@王五 请 [任务 3]

我会跟进进展，完成后统一汇总。
```

**质量标准**:
- 任务分解合理
- 责任明确
- 持续跟踪

### 【S4 类：主动服务策略】(S16-S20)

**质量标准**:

- 格式规范

#### S16. 知识沉淀 (Knowledge Archiving)

**响应模板**:

```
已将刚才的讨论归档到知识库:
```

**质量标准**:

### 3.2 参与意愿映射

**参与意愿分类**:

```
   - B1, B2 初期 (讨论、争论)
   - B6 (经验分享)

   - B1, B2 深入 (讨论、争论)

5. 我的职责
   - A1-A5 (求助型)
```

### 3.3 特殊规则

#### 规则 1: @AI 强制响应

```
无论任何形态，只要被 @AI，都必须响应：

E1 (闲聊) + @AI → S2 (直接回答)
  "今天天气真好 @AI"
  → "是的，今天天气不错 ☀️"

E5 (抱怨) + @AI → S2 (礼貌回应)
  "这个 bug 太烦了 @AI"
  → "我理解你的困扰，需要我帮忙看看吗？"
```

#### 规则 2: Owner 指令优先

```
Owner 的要求具有最高优先级：

Owner: "@AI 总结一下刚才的讨论"
  → 立即执行 S9 (延迟总结)

Owner: "@AI 帮我问一下大家..."
  → 立即执行，不管当前状态
```

#### 规则 3: 紧急情况打断一切

```
L0 级别消息可以打断任何正在执行的策略：

正在执行 S9 (总结讨论)
  ↓
收到 A5 (生产环境崩了)
  ↓
立即中断 S9，执行 S1 (紧急响应)
```

#### 规则 4: 形态转换时策略调整

```
B1 (技术讨论) → B2 (技术争论)
  S7 (观察) → 继续 S7
  如满足介入条件 → S8 (适时介入)

A1 (直接求助) → F1 (多轮对话)
  S2 (直接回答) → 继续 S2
  保持上下文连续性
```

**处理流程**:

```
Step 1: 读取新消息
  ↓

  - 是否 @AI？ → 强制响应
  - 是否紧急关键词？ → A5/F5

  ↓
Step 3: 交互识别
  - 是否属于现有交互？
  - 是否开启新交互？
  - 可能属于多个交互
  ↓
Step 4: 形态识别
  - 遍历 35 种形态的触发特征
  - 可能匹配多个形态（复合形态）
  - 选择主导形态（优先级最高的）

Step 5: 参与意愿评估
  - 与我无关 / 不想参与 / 有兴趣 / 工作流必须 / 我的职责
  ↓
Step 6: 重要性评分
  - 0-10 分，决定是否折叠
  ↓
Step 7: 查询映射表
  - 根据主导形态查询优先策略
  - 检查是否有特殊规则
  ↓
Step 8: 生成决策
  输出结构:
  {
    "primaryPattern": "A1",

    "level": "L1",
    "priority": "normal",
```

## 六、消息折叠机制

### 6.1 为什么需要折叠

**问题**: 主会话需要看到所有消息，但大量无关消息会：
1. 浪费 token
2. 稀释重要信息
3. 影响上下文理解

**解决方案**: 折叠无关或低优先级的消息，主会话看到摘要，按需展开。

---

### 6.2 折叠策略

#### 折叠条件

```
消息应该被折叠，如果满足以下条件之一：

1. 与 AI 完全无关
   - 闲聊、表情、社交互动
   - 重要性评分 ≤ 2

2. 已判定不需要参与的交互
   - 辅助会话标注为 "不参与"
   - 重要性评分 ≤ 3

3. 消息内容过长且非关键
   - 长文分享、大段代码
   - 未 @ AI
   - 重要性评分 ≤ 4

4. 历史消息（时间久远）
   - 超过 1 小时的消息
   - 且所属交互已完成
   - 且未被引用
```

#### 折叠粒度

```
级别 1: 单条消息折叠
  适用: 长文本、大文件
  表示: [折叠 1 条消息 #msg-123]

级别 2: 批量折叠（同一交互）
  适用: 完整的无关交互
  表示: [折叠 8 条消息 #int-456]
  
级别 3: 时间段折叠
  适用: 连续的低价值消息
  表示: [折叠 10:00-10:15 的 15 条消息]
```

#### 折叠后的表示

```
原始消息（未折叠）:
  Msg1: "今天天气真好"
  Msg2: "是啊，要不要出去玩"
  Msg3: "好啊，去哪？"
  Msg4: "爬山吧"

折叠后（主会话视图）:
  ┌─────────────────────────────────────────────┐
  │ [折叠 4 条消息] 交互 #int-789               │
  ├─────────────────────────────────────────────┤
  │ 形态: E1 (日常闲聊)                          │
  │ 参与者: 张三、李四、王五                     │
  │ 时间段: 10:00-10:05                         │
  │ 摘要: 讨论周末出游计划，决定去爬山           │
  │ 重要性: 1/10                                │
  │                                             │
  │ 展开: 调用工具查看完整消息                   │
  └─────────────────────────────────────────────┘
```

### 6.4 消息查询命令集

**命令集名称**: `history`（或 `hist`）

**说明**: 
- 与 `msg` 命令集分离
- 专门用于查询和管理本地消息历史
- 支持折叠/展开、交互查询、高级过滤

#### 命令列表

```bash
# ============================================
# 基础查询
# ============================================

# 查询单条消息
ec history get <message-id>
ec hist get msg-123

# 批量查询消息
ec history get --ids <id1,id2,id3>
ec hist get --ids msg-1,msg-2,msg-3

# 查询消息范围（时间）
ec history list --from "2026-06-26 10:00" --to "2026-06-26 12:00"
ec hist list --from "1h ago" --to "now"

# 查询最近 N 条消息
ec history list --limit 50
ec hist list -n 50

# ============================================
# 交互查询
# ============================================

# 查询交互的所有消息
ec history interaction <interaction-id>
ec hist int int-456

# 查询交互列表
ec history interactions --session <session-key>
ec hist ints --session feishu#chat_xyz

# 查询活跃交互
ec history interactions --status active
ec hist ints --active

# ============================================
# 过滤查询
# ============================================

# 按重要性过滤
ec history list --importance-min 7
ec hist list --important  # 快捷方式，>= 7

# 按形态过滤
ec history list --pattern A1,A5
ec hist list -p A1,A5

# 按参与意愿过滤
ec history list --intent "我的职责"
ec hist list --intent "与我无关"

# 按发送者过滤
ec history list --peer <peer-id>
ec hist list --peer ou_xxx

# 按折叠状态过滤
ec history list --folded
ec hist list --unfolded

# ============================================
# 折叠管理
# ============================================

# 展开折叠的消息
ec history unfold <message-ids>
ec hist unfold msg-1,msg-2,msg-3

# 展开交互的所有消息
ec history unfold --interaction <interaction-id>
ec hist unfold --int int-456

# 手动折叠消息
ec history fold <message-ids>
ec hist fold msg-10,msg-11

# 查看折叠统计
ec history stats --folded
ec hist stats -f

# ============================================
# 搜索
# ============================================

# 全文搜索
ec history search "数据库连接"
ec hist search "timeout"

# 搜索 + 过滤
ec history search "bug" --importance-min 5 --from "1d ago"
ec hist search "紧急" --pattern A5

# ============================================
# 导出
# ============================================

# 导出消息为 JSON
ec history export --from "2026-06-26" --to "2026-06-27" -o messages.json
ec hist export --int int-456 -o interaction.json

# 导出为 Markdown
ec history export --format markdown -o report.md
ec hist export --fmt md --important -o important-messages.md

# ============================================
# 统计分析
# ============================================

# 消息统计
ec history stats
# 输出:
#   总消息数: 1234
#   折叠消息: 800 (64.8%)
#   未折叠消息: 434 (35.2%)
#   平均重要性: 4.2

# 交互统计
ec history stats --interactions
# 输出:
#   总交互数: 45
#   活跃交互: 3
#   已完成: 40
#   已放弃: 2
#   AI 参与: 15 (33.3%)

# 形态分布
ec history stats --patterns
# 输出:
#   A1 (直接求助): 12
#   B1 (技术讨论): 8
#   E1 (日常闲聊): 20
#   ...

# ============================================
# 清理
# ============================================

# 清理旧消息（保留 N 天）
ec history clean --keep-days 30
ec hist clean --keep 30d

# 清理已折叠且不重要的消息
ec history clean --folded --importance-max 2
ec hist clean -f --importance-max 2

# 清理已完成的交互
ec history clean --interactions --completed
ec hist clean --ints --completed
```

### 6.6 折叠的实现考虑

#### 性能优化

```
1. 懒加载
   - 折叠的消息不立即加载到内存
   - 只在需要时查询数据库

2. 批量查询
   - 展开多条消息时，一次查询

3. 缓存
   - 最近展开的消息缓存在内存
   - LRU 策略，限制缓存大小

4. 索引优化
   - interaction_ids 使用 JSON 索引
   - 联合索引 (session_key, timestamp, folded)
```

#### 一致性保证

```
1. 折叠标记原子性
   - 使用事务更新 folded 字段

2. 交互状态同步
   - 交互完成时，自动折叠所有消息

3. 重要性评分更新
   - 如果消息被 @ 或引用，重新评分
   - 自动展开重要性提升的消息
```
