# S1: 紧急响应策略

**适用场景**: 紧急求助、生产故障、系统崩溃

**策略特点**: 快速、止血、不求完美

---

## 何时使用

### 交互形态
- A5-紧急求助
- F5-紧急插入

### 属性特征
```
urgency: 紧急
emotionalTone: [紧张] 或 [焦虑]
aiRelevance: 必须 AI
```

### 触发词
- "紧急"、"urgent"
- "崩了"、"挂了"
- "生产环境"
- "线上故障"

---

## 执行原则

### 1. 速度优先

```
不追求完美，追求快速止血

优先级:
  1. 立即响应（30秒内）
  2. 临时方案（能用就行）
  3. 后续优化（稳定后改进）
```

### 2. 分阶段处理

```
阶段 1: 快速止血（1-2分钟）
  - 识别问题类型
  - 给出临时方案
  - 能恢复服务即可

阶段 2: 根因分析（有时间再做）
  - 深入分析原因
  - 给出长期方案

阶段 3: 预防措施（可选）
  - 避免再次发生
```

### 3. 明确优先级

```
生命周期:
  用户安全 > 数据完整性 > 服务可用性 > 用户体验

操作优先级:
  回滚 > 降级 > 修复 > 优化
```

---

## 执行步骤

### Step 1: 快速理解（10秒）

```
关键信息:
  - 什么出问题了？
  - 影响范围多大？
  - 现在什么状态？

快速判断:
  - 能否立即恢复？
  - 需要回滚吗？
  - 有备份吗？
```

### Step 2: 给出临时方案（30秒）

```
优先方案:
  1. 重启服务
  2. 回滚版本
  3. 切换备用
  4. 降级功能

说明要点:
  - 操作步骤（1-2-3）
  - 预期效果
  - 风险提示
```

### Step 3: 跟踪结果

```
询问:
  "执行结果如何？"
  "服务恢复了吗？"

根据反馈:
  - 如果恢复 → 后续优化建议
  - 如果未恢复 → 给出备选方案
```

## 回复模板

### 模板 1: 服务崩溃

```
[紧急] 快速恢复步骤：

1. 立即重启服务
   ```bash
   sudo systemctl restart <service-name>
   ```

2. 检查日志
   ```bash
   tail -100 /var/log/<service>.log
   ```

3. 如果还不行，回滚到上一个版本
   ```bash
   git checkout <last-stable-commit>
   npm run deploy
   ```

先把服务恢复，我们再分析根本原因。

执行后告诉我结果。
```

### 模板 2: 数据库问题

```
[紧急] 数据库连接问题快速处理：

立即操作：
1. 检查连接数
   ```sql
   SHOW PROCESSLIST;
   ```

2. 如果连接满了，kill 长时间查询
   ```sql
   KILL <process_id>;
   ```

3. 临时增加连接数（治标）
   ```sql
   SET GLOBAL max_connections = 500;
   ```

这是临时方案，稳定后我们优化查询和配置。

现在什么情况？
```

### 模板 3: API 超时

```
[紧急] API 超时应急方案：

快速止血：
1. 启用降级模式（如果有）
2. 增加超时时间（临时）
3. 限流保护后端

如果没有降级：
1. 重启服务
2. 清理缓存
3. 检查依赖服务

告诉我当前状态，我给具体步骤。
```

## 常见场景

### 场景 1: 生产环境崩溃

```
用户: "紧急！生产环境崩了！"

你的回复:
  [紧急] 立即操作：
  
  1. 先回滚到上一个稳定版本
  2. 同时我需要知道：
     - 崩溃前做了什么操作？
     - 有报错信息吗？
     - 多久开始的？
  
  回滚命令：
  [具体命令]
  
  执行后告诉我结果。
```

### 场景 2: 数据丢失风险

```
用户: "数据库连接断了，担心数据丢失！"

你的回复:
  [紧急] 先保护数据：
  
  1. 立即停止写操作
  2. 检查最后一次备份时间
  3. 不要重启数据库（可能丢失内存数据）
  
  现在：
  - 数据库进程还在吗？
  - 有报错日志吗？
  
  等你确认，我给恢复步骤。
```

### 场景 3: 用户无法访问

```
用户: "用户都访问不了了！"

你的回复:
  [紧急] 分情况处理：
  
  如果是服务器问题：
  1. 检查服务状态
  2. 检查端口是否开放
  
  如果是 DNS 问题：
  1. 临时用 IP 访问
  2. 检查 DNS 配置
  
  先告诉我：
  - ping 得通吗？
  - 端口能访问吗？
  
  然后我给具体步骤。
```

## 质量标准

### ✅ 好的紧急响应

```
特征:
  - 30 秒内给出第一步操作
  - 步骤清晰（1-2-3）
  - 优先止血，不追求完美
  - 明确告诉用户"这是临时方案"
  - 持续跟踪结果
```

### ❌ 不好的紧急响应

```
问题:
  - 先问一堆问题才给方案
  - 给出的方案太复杂
  - 追求完美解决方案
  - 不说明风险
  - 给完方案就不管了
```

---

## 注意事项

### 1. 风险提示

```
任何操作都要说明风险：
  "这个操作会重启服务，会有 1-2 分钟中断"
  "回滚会丢失最近的配置更改"
  "这是临时方案，后续需要正式修复"
```

### 2. 数据安全

```
涉及数据的操作：
  - 先确认有备份
  - 不要直接删除
  - 考虑数据一致性
```

### 3. 后续跟进

```
问题解决后：
  - 建议后续优化措施
  - 提醒做根因分析
  - 记录事故复盘
```

## 示例对话

```
用户: "紧急！生产数据库连不上了！"

你: [紧急] 立即检查：

1. 先确认数据库进程
   ```bash
   ps aux | grep mysql
   ```

2. 如果进程在，检查端口
   ```bash
   netstat -an | grep 3306
   ```

3. 如果进程不在，启动数据库
   ```bash
   sudo systemctl start mysql
   ```

执行后告诉我结果，我根据情况给下一步。

---

用户: "进程在，但连不上"

你: 好，进程在说明数据库没挂。

现在检查：
1. 连接数是否满了
   ```bash
   mysql -u root -p
   SHOW PROCESSLIST;
   ```

2. 如果看到很多连接，临时增加
   ```sql
   SET GLOBAL max_connections = 500;
   ```

3. 同时检查应用是否连接池配置过小

这是临时方案，稳定后我们优化。

现在能连上了吗？

---

用户: "好了！谢谢！"

你: 好的，服务恢复了。

建议后续做这几件事：
1. 分析为什么连接数突然增加
2. 优化数据库连接池配置
3. 加监控告警（连接数阈值）

需要帮忙分析原因吗？
```

---

**记住**: 紧急响应的核心是"快速止血"，不是"完美解决"。先让服务恢复，再慢慢优化。
