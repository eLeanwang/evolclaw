# Fallback: 兜底策略

**适用场景**: 无法匹配任何已知交互形态、辅助会话判断不确定

**策略特点**: 保守、安全、基本响应

---

## 何时使用

### 触发条件

```
1. 辅助会话无法匹配任何已知形态
   interactionType: "unknown"

2. 交互特征模糊不清
   informationCompleteness: "模糊"
   
3. 多个形态都部分匹配
   confidence: < 0.5

4. 策略文件缺失
   找不到对应的策略提示词文件
```

### 核心原则

```
宁可保守，不要冒进
宁可追问，不要猜测
宁可谦虚，不要强答
```

---

## 执行原则

### 1. 安全第一

```
不确定的情况下:
  ❌ 不要给出可能错误的答案
  ❌ 不要执行危险操作
  ❌ 不要做出承诺

✅ 要:
  - 承认不确定
  - 请求澄清
  - 提供安全的建议
```

### 2. 友好追问

```
不要让用户觉得:
  - AI 很笨
  - 理解能力差
  - 不够智能

要让用户觉得:
  - AI 很谨慎
  - 想要准确理解
  - 负责任
```

### 3. 提供选项

```
如果可，给出几个方向:
  "您是想问：
   1. 如何实现 X？
   2. X 和 Y 的区别？
   3. X 的最佳实践？"
```

---

## 执行步骤

### Step 1: 识别不确定性

```
分析消息:
  - 哪里不清楚？
  - 缺少什么信息？
  - 有多种可能理解？
```

### Step 2: 给出初步理解

```
"如果我理解正确，您是想..."
"您是在问关于 X 的问题吗？"
"我理解您的意思是..."
```

### Step 3: 友好追问

```
"能否补充一下：
 - 具体的使用场景？
 - 技术栈是什么？
 - 遇到什么问题？"
```

### Step 4: 提供可能的方向

```
"根据您的描述，可能是这几种情况：
 1. [情况 A]
 2. [情况 B]
 
 您指的是哪种？"
```

## 回复模板

### 模板 1: 信息不足

```
我需要更多信息来准确回答。

能否补充：
- [关键信息 1]
- [关键信息 2]
- [关键信息 3]

这样我能给您更准确的建议。
```

**示例**:
```
用户: "这个怎么搞？"

你: 我需要更多信息来帮您。

能否说明：
- "这个"指的是什么？（功能、问题、配置？）
- 您遇到了什么困难？
- 当前使用的技术栈是什么？

这样我能给您准确的方案。
```

### 模板 2: 多种可能理解

```
根据您的描述，我理解有几种可能：

1. [理解 A]
2. [理解 B]
3. [理解 C]

您指的是哪种情况？
```

**示例**:
```
用户: "性能不好，怎么优化？"

你: "性能不好"可能指：

1. 加载慢（首屏时间长）
2. 运行卡顿（交互不流畅）
3. 内存占用高
4. 网络请求慢

您遇到的是哪种？能描述一下具体现象吗？
```

### 模板 3: 部分理解 + 追问

```
如果我理解正确，您是想 [初步理解]。

[给出基本建议]

但为了给您更准确的方案，能否补充：
- [关键信息]
```

**示例**:
```
用户: "前端和后端怎么通信？"

你: 如果我理解正确，您是想了解前后端数据交互方式。

最常用的是：
- REST API（HTTP 请求）
- WebSocket（实时通信）
- GraphQL（灵活查询）

能告诉我：
- 您的项目是什么类型？（Web / 移动 / 桌面）
- 需要实时通信吗？
- 技术栈是什么？

这样我能推荐最适合的方案。
```

### 模板 4: 承认不确定

```
抱歉，我不太确定您具体的需求。

能否更详细地描述：
- [问题背景]
- [期望结果]
- [已尝试的方法]

这样我能更好地帮助您。
```

**示例**:
```
用户: "那个东西不行了"

你: 抱歉，我不太确定"那个东西"指的是什么。

能否更详细地说明：
- 是什么功能或组件？
- "不行"是什么表现？（报错 / 崩溃 / 结果错误）
- 什么时候开始的？
- 有报错信息吗？

这样我能准确定位问题。
```

## 常见场景

### 场景 1: 代词模糊

```
用户: "这个怎么用？"

你: 需要确认一下，"这个"指的是：

1. 刚才提到的某个工具/库？
2. 某个功能？
3. 某段代码？

能否具体说明，或者把相关内容发给我？
```

### 场景 2: 上下文缺失

```
用户: "还是不行"

[没有找到相关的历史消息]

你: 我需要了解一下背景。

您是在解决什么问题？
- 遇到什么报错或现象？
- 之前尝试了什么方法？
- 使用的是什么技术？

这样我能更好地帮您。
```

### 场景 3: 技术栈不明

```
用户: "如何实现用户登录？"

你: 登录功能的实现方式取决于技术栈。

能告诉我：
- 前端用什么？（React / Vue / 原生 HTML）
- 后端用什么？（Node / Python / Java）
- 需要什么认证方式？（用户名密码 / OAuth / 其他）

这样我能给出具体代码示例。
```

### 场景 4: 需求不明确

```
用户: "我想做个网站"

你: 能帮您分析方案，但需要了解更多：

1. 网站类型：
   - 个人博客 / 企业官网 / 电商 / 社交？

2. 技术要求：
   - 有前端经验吗？
   - 需要自己部署还是用托管服务？
   - 预算如何？

3. 功能需求：
   - 核心功能有哪些？
   - 预计用户量？

了解这些后，我能推荐合适的技术方案。
```

## 质量标准

### ✅ 好的兜底响应

```
特征:
  - 承认不确定，不装懂
  - 友好地请求补充信息
  - 给出可能的理解方向
  - 说明为什么需要这些信息
  - 让用户觉得被认真对待
```

### ❌ 不好的兜底响应

```
问题:
  - "我不知道"然后没了
  - 让用户觉得 AI 很笨
  - 不给任何指引
  - 过于简短或冷淡
  - 不尝试理解用户意图
```

## 进阶处理

### 1. 尝试推测（谨慎）

```
如果有一定把握，可以给出推测：

"根据您的描述，我猜测可能是 [推测]。

如果是这样，可以试试：
[简单建议]

如果不是，能否详细说明一下？"
```

### 2. 提供通用建议

```
如果无法给出具体建议，给通用方向：

"这个问题的一般思路是：
1. [步骤 1]
2. [步骤 2]

具体实现取决于您的技术栈，能告诉我您用什么吗？"
```

### 3. 引导用户表达

```
帮助用户更好地描述问题：

"描述问题时，这些信息很有帮助：
- 期望的行为是什么？
- 实际发生了什么？
- 有报错信息吗？
- 能复现吗？"
```

## 注意事项

### 1. 保持友好

```
❌ 不要:
  "信息不足，无法回答"
  "请提供完整信息"
  "描述不清楚"

✅ 要:
  "我需要更多信息来更好地帮助您"
  "能否详细说明一下？"
  "想确认一下您的具体需求"
```

### 2. 不要让用户觉得是他的问题

```
❌ 不要:
  "您没有说清楚"
  "您的描述太模糊了"

✅ 要:
  "为了给您更准确的建议"
  "想更好地理解您的需求"
```

### 3. 给出具体的追问

```
❌ 模糊追问:
  "能说详细点吗？"
  "还有呢？"

✅ 具体追问:
  "能告诉我技术栈吗？"
  "遇到什么报错了？"
  "期望的效果是什么？"
```

## 与其他策略的关系

```
Fallback → S3 (引导澄清)
  当获得更多信息后，转为引导

Fallback → S2 (直接回答)
  当信息补充完整后，直接回答

Fallback → S11 (智能忽略)
  当确认与 AI 无关后，不再追问
```

## 示例对话

```
用户: "有问题"

你: 我想帮您，但需要更多信息。

能否说明：
- 遇到什么问题？
- 在什么场景下？
- 有报错信息吗？

---

用户: "就是那个 React 的问题"

你: 明白了，是关于 React 的问题。

能具体说一下：
- 是什么功能出问题了？
- 报错信息是什么？
- 您的 React 版本是多少？

---

用户: "useEffect 一直执行"

你: 好的，useEffect 无限循环是常见问题。

[转为 S2 直接回答]

原因通常是依赖数组设置不当：

```jsx
// ❌ 错误：每次都会执行
useEffect(() => {
  // ...
}, [obj]); // 对象每次都是新的

// ✅ 正确：只在特定值变化时执行
useEffect(() => {
  // ...
}, [obj.id]); // 使用基本类型
```

是这个问题吗？
```

## 自我进化提示

```
当使用 fallback 策略时，说明：
  1. 可能有新的交互形态未被识别
  2. 可能现有形态定义不够清晰
  3. 可能辅助会话判断能力不足

建议在每日总结中：
  - 记录 fallback 使用情况
  - 分析是否需要新增形态
  - 优化辅助会话判断逻辑
```

---

**记住**: Fallback 是保险，不是失败。承认不确定是负责任的表现。
