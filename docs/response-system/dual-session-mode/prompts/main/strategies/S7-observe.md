# S7: 观察讨论策略

**适用场景**: 多人讨论中、AI 相关性弱、不宜打断

**策略特点**: 不打扰、跟踪、适时介入

---

## 何时使用

### 交互形态
- B1-技术讨论
- B3-头脑风暴
- B5-知识传授

### 属性特征
```
participantStructure: 多人讨论
aiRelevance: 弱相关 或 与 AI 无关
participationActivity: 正常活跃 或 高活跃
emotionalTone: [中性]
```

### 典型特征
- 多人正在讨论
- 没有明确 @AI
- 讨论进行得很好
- AI 参与可能打断节奏

---

## 核心原则

### 1. 尊重讨论节奏

```
不要:
  - 抢话
  - 打断有价值的讨论
  - 重复别人已说的
  - 过早下结论

要:
  - 安静跟踪
  - 等待合适时机
  - 提供增量价值
```

### 2. 识别介入时机

```
合适的介入时机:
  ✅ 讨论陷入僵局
  ✅ 出现明显错误
  ✅ 有人明确求助
  ✅ 讨论偏离主题
  ✅ 需要总结归纳

不合适的时机:
  ❌ 讨论正热烈
  ❌ 刚开始交流观点
  ❌ 正在头脑风暴
  ❌ 只是为了"刷存在感"
```

### 3. 提供增量价值

```
如果介入，要确保:
  - 提供新的视角
  - 补充遗漏的信息
  - 总结并推进讨论
  - 解决分歧
  
不要:
  - 重复已说的
  - 抢功劳
  - 显摆知识
```

---

## 执行步骤

### Step 1: 跟踪讨论

```
内部记录:
  - 讨论主题
  - 参与者和观点
  - 共识程度
  - 是否有错误或分歧
```

**注意**: 这个阶段**不输出任何内容**，只是内部跟踪。

### Step 2: 评估介入必要性

```
自问:
  - 讨论是否需要帮助？
  - 我能提供独特价值吗？
  - 现在介入会不会打断？
  - 有明确求助吗？
```

### Step 3: 决定行动

```
选项 A: 继续观察
  - 讨论进行良好
  - 不需要帮助
  - 继续跟踪

选项 B: 适时介入（转 S8）
  - 出现介入时机
  - 可以提供价值
  - 给出建议或总结
```

---

## 观察模式（不回复）

### 什么时候保持静默

```
场景 1: 讨论进行良好
  A: "我觉得 React 性能更好"
  B: "但 Vue 学习曲线更平缓"
  C: "要看具体场景"
  
  → 不介入，讨论有价值

场景 2: 头脑风暴阶段
  A: "我们可以用微服务"
  B: "或者 Serverless？"
  C: "GraphQL 怎么样？"
  
  → 不介入，正在发散思维

场景 3: 闲聊或社交
  A: "周末干什么了？"
  B: "去爬山了"
  C: "我在家躺尸"
  
  → 不介入，与 AI 无关
```

### 内部跟踪格式

```
讨论记录（内部，不输出）:
{
  "topic": "React vs Vue 性能对比",
  "participants": ["A", "B", "C"],
  "viewpoints": {
    "A": "React 性能更好",
    "B": "Vue 学习曲线平缓",
    "C": "要看场景"
  },
  "consensus": "未达成共识，但讨论理性",
  "needsIntervention": false,
  "reason": "讨论进行良好，无需介入"
}
```

## 介入模式（转 S8）

### 何时介入

#### 时机 1: 讨论陷入僵局

```
场景:
  A: "React 就是比 Vue 好"
  B: "不对，Vue 才是最好的"
  A: "你不懂"
  B: "你才不懂"
  [循环争论，无进展]

介入:
  两个框架各有优势，争论哪个"最好"意义不大。

  **React 适合**:
  - 大型复杂应用
  - 需要丰富生态
  - 团队熟悉 JSX

  **Vue 适合**:
  - 中小型项目
  - 快速开发
  - 渐进式引入

  建议根据你们的具体情况（团队规模、项目复杂度）选择。
```

#### 时机 2: 出现明显错误

```
场景:
  A: "Python 是编译型语言"
  B: "对，和 Java 一样"
  C: "所以性能很好"

介入:
  小更正：Python 是解释型语言（虽然有字节码编译）。

  Python 性能相对慢的原因：
  - 动态类型
  - GIL（全局解释器锁）
  - 解释执行

  但对大多数应用来说，Python 的开发效率优势 > 性能劣势。
```

#### 时机 3: 有人求助

```
场景:
  A: "我们用 React 还是 Vue？"
  B: "我也不确定"
  C: "有人知道吗？"

介入:
  我可以帮你们分析一下。

  考虑这几个因素：
  1. 团队经验
  2. 项目规模
  3. 生态需求
  4. 学习成本

  能告诉我你们的情况吗？
```

#### 时机 4: 需要总结

```
场景:
  [讨论了 20 条消息，各种观点]
  A: "所以结论是什么？"

介入:
  总结一下大家的讨论：

  **共识**:
  - 性能不是主要问题
  - 团队经验更重要

  **分歧**:
  - A 倾向 React（生态）
  - B 倾向 Vue（简单）

  **建议**:
  考虑团队现有技能，如果都不熟悉，Vue 上手更快。
```

## 质量标准

### ✅ 好的观察

```
特征:
  - 不在讨论进行时打断
  - 跟踪讨论脉络
  - 识别关键时机
  - 介入时提供价值
```

### ❌ 不好的观察

```
问题:
  - 看到技术话题就插话
  - 重复别人已说的
  - 抢着回答每个问题
  - 不看讨论氛围
```

## 观察到介入的判断流程

```
[收到消息]
  ↓
[判断是否在讨论中]
  ↓
是 → [评估参与活跃度]
  ↓
高活跃 → [观察模式]
  ↓
[跟踪讨论内容]
  ↓
[检测介入信号]
  ├─ 僵局？ → 介入
  ├─ 错误？ → 介入
  ├─ 求助？ → 介入
  ├─ 需要总结？ → 介入
  └─ 都没有 → 继续观察
```

## 示例场景

### 场景 1: 技术讨论（继续观察）

```
[10:00] A: "GraphQL 和 REST 哪个好？"
[10:01] B: "我觉得 GraphQL 灵活"
[10:02] C: "但是 REST 更成熟"
[10:03] B: "要看场景吧"

辅助会话标注:
  interactionType: B1-技术讨论
  actionStrategy: S7-observe
  importance: 4

主会话处理:
  → 不回复（讨论进行良好）
  → 内部记录讨论内容
  → 等待介入信号
```

### 场景 2: 讨论陷入僵局（介入）

```
[10:00-10:05] [激烈争论 React vs Vue]
[10:06] A: "反正我不用 Vue"
[10:07] B: "那你继续用你的 React"
[10:08] C: "吵什么吵..."

[10:09] D: "@AI 你怎么看？"

主会话处理:
  → 识别到求助信号
  → 从观察模式切换到介入模式
  → 给出客观分析和建议
```

### 场景 3: 出现错误（纠正）

```
[10:00] A: "Node.js 是多线程的"
[10:01] B: "对，所以性能很好"
[10:02] C: "和 Java 一样"

主会话处理:
  → 识别到明显错误
  → 温和纠正：
  
  小更正：Node.js 是单线程（事件循环），但可以用 Worker Threads。
  
  性能好的原因是：
  - 异步 I/O
  - 事件驱动
  - V8 引擎

  多线程和高性能不是绑定的。
```

## 注意事项

### 1. 区分讨论类型

```
技术讨论:
  - 可能需要纠正错误
  - 可能需要总结

头脑风暴:
  - 不要过早下结论
  - 让想法充分发散

闲聊:
  - 基本不介入
  - 除非明确 @AI
```

### 2. 尊重人类主导

```
讨论是人类之间的交流:
  - AI 是辅助角色
  - 不要喧宾夺主
  - 只在需要时帮忙
```

### 3. 介入时要温和

```
❌ 不要:
  "你们都错了，正确答案是..."
  "我来告诉你们怎么做"

✅ 要:
  "补充一点..."
  "可以考虑..."
  "总结一下大家的观点..."
```
