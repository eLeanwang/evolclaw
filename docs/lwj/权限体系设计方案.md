# EvolClaw 权限体系设计方案（宏观）

> 本文档从宏观角度重新设计权限机制，并对齐 `docs/config/01-overview.md` 的配置体系：所有配置参数统一进入 `config.json`，权限控制在 API / ConfigManager 层完成，不再新增独立的 `roles.json`、`roles/` 或 `role-assignments.json` 作为目标设计。
> 生成日期：2026-07-07

---

## 1. 核心结论

权限体系分成两个互不依赖的权限面：

1. **管理权限面**：`owner` / `admin`。身份名单配置在 config 中，能力由代码硬编码。
2. **用户权限面**：内置用户角色 + 自定义用户角色。角色定义、默认角色、对用户/群的角色分配都进入现有 `config.json` 体系。

目标不是再发明一套权限文件，而是复用配置体系 v3 已经确定的边界：

```text
agents/defaults.json → agents/{aid}/config.json → agents/{aid}/relations/{peerKey}/config.json
```

下文路径沿用 `docs/config/01-overview.md` 的描述方式，均以 `{evolclaw_home}` 作为配置根目录。

其中：

- agent 级 `config.json`：描述这个 agent 的管理身份、用户角色定义、默认角色。
- relation 级 `config.json`：描述这个 agent 面向某个用户或某个群时的角色归属与关系级覆盖。
- 代码：管理能力、用户面能力上限、内置角色基线。

---

## 2. 管理权限面

### 2.1 配置在哪里

管理身份只配置在 config 体系中：

| 层级 | 文件 | 用途 |
|------|------|------|
| 进程级 | `{evolclaw_home}/evolclaw.json` | daemon / control 面 owner 名单 |
| 全局级 | `{evolclaw_home}/agents/defaults.json` | 可选的全局 agent owner/admin 默认名单 |
| Agent 级 | `{evolclaw_home}/agents/{aid}/config.json` | 该 agent 的 `owners` / `admins` |

管理身份使用 AID：

```jsonc
{
  "owners": ["alice.aid.pub"],
  "admins": ["bob.aid.pub"]
}
```

relation 级配置不得定义 owner/admin。关系级是用户权限面，不是管理身份入口。

### 2.2 如何认证

远程身份认证由 AUN 保证：

1. owner/admin 的私钥留在其自己的设备或 AUN keystore，不在 agent 本机。
2. AUN 完成远程身份认证后，向 EvolClaw 交付已认证的发送方 AID。
3. EvolClaw 只做精确相等比对：`authenticatedAid ∈ owners/admins`。

未经 AUN 认证的自称 AID 一律不进入管理面。

### 2.3 能力在哪里

owner/admin 的能力不在 config 中定义：

- owner：最高权限，能力全集，由代码给定。
- admin：受托管理权限，由代码白名单给定，不能修改 owner 名单，不能执行 owner 专属破坏性操作。

这意味着：

- 修改 config 不能削弱 owner。
- 修改 config 不能把普通用户提权成 owner/admin。
- 若要扩大 admin 能力，必须改代码、走评审和发版。

## 3. 用户权限面

用户权限面解决“访问 agent 的人或群能做什么”。它由三类信息组成：

| 类型 | 配置位置 | 说明 |
|------|----------|------|
| 内置角色基线 | 代码 | `member` / `visitor` 的默认能力；`visitor` 中文名为“访客” |
| 用户角色定义 | agent 级 `config.json` | 自定义角色、内置角色收紧、默认角色 |
| 角色归属 | relation 级 `config.json` | 某用户、某群、某群成员是什么角色 |

### 3.1 Agent 级角色策略

用户角色定义放在：

```text
{evolclaw_home}/agents/{aid}/config.json
```

建议结构：

```jsonc
{
  "roles": {
    "defaultRoles": {
      "private": null,
      "group": "visitor"
    },
    "definitions": {
      "member": {
        "description": "团队成员",
        "allowAccess": true,
        "permissions": {},
        "commandPermissions": {}
      },
      "visitor": {
        "description": "访客，低信任只读访问者",
        "allowAccess": true,
        "permissions": {},
        "commandPermissions": {}
      },
      "reviewer": {
        "description": "只读审阅者",
        "allowAccess": true,
        "permissions": {
          "baseagents.claude.model": {
            "default": "claude-haiku-4-5-20251001",
            "allowOverride": false
          }
        },
        "commandPermissions": {
          "category:read": { "allow": true },
          "*": { "allow": false }
        }
      }
    }
  }
}
```

说明：

- `defaultRoles` 是私聊/群聊没有显式角色时的兜底。
- `defaultRoles.private` / `defaultRoles.group` 可设为 `null`，表示没有默认角色；无角色时直接拒绝访问。
- `definitions` 是本 agent 的用户角色定义。
- 内置用户角色只有 `member` 与 `visitor`。`visitor` 表示“访客”，用于低信任、只读或最低风险访问场景。
- 内置角色可在这里收紧，但不能删除基线。
- 自定义角色只能获得用户面能力上限内的能力。
- `owner` / `admin` 不允许在 `roles.definitions` 中定义。

### 3.2 Relation 级角色归属

对端用户或群的角色归属放在：

```text
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json
```

`peerKey` 格式沿用配置体系：

```text
{channelType}#{urlEncode(channelId)}
```

私聊关系示例：

```jsonc
// agents/bot.aid.pub/relations/aun#alice.aid.pub/config.json
{
  "roles": {
    "assigned": "member"
  }
}
```

群关系示例：

```jsonc
// agents/bot.aid.pub/relations/aun#grp-123/config.json
{
  "roles": {
    "assigned": "visitor",
    "members": {
      "bob.aid.pub": "member",
      "eve.aid.pub": "reviewer"
    }
  }
}
```

语义：

- 私聊 relation 的 `roles.assigned`：这个用户在私聊里的角色。
- 群 relation 的 `roles.assigned`：这个群的默认角色。
- 群 relation 的 `roles.members[aid]`：某个群成员在该群内的专属角色。

这样 `group-member` 的“群 × 人”关系自然归属到群 relation config，不需要额外文件。

## 4. 配置保护

本方案依赖 config 体系既有保护，不再引入独立 HMAC / manifest 设计。

### 4.1 直接文件访问保护

Hook 禁止 agent 直接读写：

- `{evolclaw_home}/evolclaw.json`
- `{evolclaw_home}/agents/defaults.json`
- `{evolclaw_home}/agents/{aid}/config.json`
- `{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json`
- `{evolclaw_home}/.env`
- `{evolclaw_home}/backups/config/`

agent 不能通过普通文件操作改 owner、admin、角色定义或角色归属。

### 4.2 受控修改入口

所有修改必须走：

- CLI：`ec config`、`ec model`、未来的 `ec role`
- ECWeb / control API
- ConfigManager 内部 API

API 层负责判断：

- 调用方是谁；
- 是否是 owner/admin；
- 是否允许写目标字段；
- 是否允许写目标 scope；
- 是否需要审批；
- 是否记录审计。

### 4.3 Schema 与快照

角色相关字段进入 agent-config / relation-config schema：

- agent schema 约束 `roles.defaultRoles`、`roles.definitions`。
- relation schema 约束 `roles.assigned`、`roles.members`。
- 配置变更进入 `logs/config-audit.jsonl`。
- 配置快照覆盖 agent/relation config，可通过 snapshot / restore 回滚。

这比新增独立角色文件更一致，因为保护、审计、回滚、迁移都走同一套机制。

### 4.4 权限守卫

必须保留以下硬规则：

1. `roles.definitions` 不接受 `owner` / `admin`。
2. `roles.assigned` 和 `roles.members[*]` 不接受 `owner` / `admin`。
3. 用户角色最终能力 = 角色声明能力 ∩ 用户面能力上限。
4. 未知角色、非法配置、缺失角色均 fail-closed 为“无有效角色”，直接拒绝访问。
5. relation config 不能声明管理身份。
6. 修改 owner 名单只能由 owner 执行。

## 5. 对用户 / 对群的角色判断流程

### 5.1 私聊

输入：

- `selfAid`：本 agent
- `actorAid`：AUN 已认证的发送方 AID
- `chatType = private`
- `peerKey = {channelType}#{actorAid}`

流程：

```text
1. AUN 认证 actorAid
2. 管理面判定：
   actorAid ∈ owners  → owner
   actorAid ∈ admins  → admin
3. 读取私聊 relation config：
   agents/{aid}/relations/{peerKey}/config.json（其中 {aid}=selfAid）
4. 若 roles.assigned 存在 → 使用该角色
5. 否则 → 使用 agent config roles.defaultRoles.private
6. 若默认角色为 `null`、角色不存在或非法 → 无有效角色，直接拒绝
```

优先级：

```text
owner/admin > 私聊 roles.assigned > defaultRoles.private > 无角色拒绝
```

默认建议：

- `defaultRoles.private = null`（陌生私聊默认无角色，直接拒绝）

### 5.2 群聊

输入：

- `selfAid`：本 agent
- `actorAid`：AUN 已认证的发言人 AID
- `groupId`：群 ID
- `groupPeerKey = {channelType}#{groupId}`
- `privatePeerKey = {channelType}#{actorAid}`

流程：

```text
1. AUN 认证 actorAid
2. 管理面判定：
   actorAid ∈ owners  → owner
   actorAid ∈ admins  → admin
3. 读取群 relation config：
   agents/{aid}/relations/{groupPeerKey}/config.json（其中 {aid}=selfAid）
4. 若 groupConfig.roles.members[actorAid] 存在
   → 使用该群成员专属角色
5. 否则读取私聊 relation config：
   agents/{aid}/relations/{privatePeerKey}/config.json（其中 {aid}=selfAid）
   若 privateConfig.roles.assigned 存在
   → 继承私聊角色
6. 否则若 groupConfig.roles.assigned 存在
   → 使用群默认角色
7. 否则 → 使用 agent config roles.defaultRoles.group
8. 若默认角色为 `null`、角色不存在或非法 → 无有效角色，直接拒绝
```

优先级：

```text
owner/admin
> 群成员专属 roles.members[actorAid]
> 私聊 roles.assigned 继承
> 群默认 roles.assigned
> defaultRoles.group
> 无角色拒绝
```

默认建议：

- `defaultRoles.group = visitor`（若希望陌生群也拒绝，可设为 `null`）

## 6. 修改方式

| 目标 | 修改位置 | 谁能改 | 入口 |
|------|----------|--------|------|
| 增删 owner | agent 级 `config.json.owners` | owner | control / ECWeb / owner API |
| 增删 admin | agent 级 `config.json.admins` | owner | control / ECWeb / admin API |
| 扩大 admin 能力 | 代码 | 开发者 | 代码评审 + 发版 |
| 新增自定义角色 | agent 级 `config.json.roles.definitions` | owner/admin | `ec config` / `ec role define` |
| 收紧内置角色 | agent 级 `config.json.roles.definitions` | owner/admin | `ec config` / `ec role update` |
| 修改默认角色 | agent 级 `config.json.roles.defaultRoles` | owner/admin | `ec config` / `ec role default` |
| 给私聊用户分配角色 | 私聊 relation `config.json.roles.assigned` | owner/admin | `ec config --peer` / `ec role assign` |
| 给群设置默认角色 | 群 relation `config.json.roles.assigned` | owner/admin | `ec config --peer <group>` / `ec role assign` |
| 给群成员单独分配角色 | 群 relation `config.json.roles.members[aid]` | owner/admin | `ec role assign --group --member` |
| 开放用户面新能力上限 | 代码 | 开发者 | 代码评审 + 发版 |

---

## 7. 关键不变量

1. owner/admin 的能力永远来自代码。
2. owner/admin 的身份只来自 AUN 已认证 AID 与 config 名单的精确匹配。
3. 用户角色配置只能进入 agent/relation `config.json`，不新增独立角色配置文件。
4. 用户角色不能定义或分配为 `owner` / `admin`。
5. 用户角色能力永远受代码中的用户面能力上限封顶。
6. relation 级配置只影响用户面，不能提升为管理身份。
7. 配置缺失、损坏、未知角色、非法角色统一变为“无有效角色”，直接拒绝访问。
8. 所有配置修改走 ConfigManager / CLI / API，并纳入 schema、审计、快照、回滚。
