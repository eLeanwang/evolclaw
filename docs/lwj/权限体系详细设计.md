# EvolClaw 权限体系详细设计方案

> 本文档是《权限体系设计方案（宏观）》的落地细化版。
> 设计依据：`docs/config/01-overview.md`、`docs/config/07-security.md`。
> 核心决策：角色相关配置不再单独写 `roles.json`、`roles/` 或 `role-assignments.json`，全部进入现有 agent 级 / relation 级 `config.json`，复用 ConfigManager、schema、Hook、审计、快照与回滚机制。
> 生成日期：2026-07-07

---

## 0. 总览

权限体系分三类对象：

| 对象 | 解决的问题 | 配置/定义位置 | 是否可配置 |
|------|------------|----------------|------------|
| 管理权限 | 谁能管理系统 | 身份在 config，能力在代码 | 身份可配置，能力不可配置 |
| 用户角色 | 访问用户/群属于什么角色 | agent/relation `config.json` | 可配置 |
| 用户权限 | 角色能执行什么 | 角色定义 + 代码能力上限 | 上限不可配置，角色能力可配置 |

核心存储边界：

```text
{evolclaw_home}/
├── evolclaw.json
├── agents/
│   ├── defaults.json
│   └── {aid}/
│       ├── config.json
│       └── relations/{peerKey}/
│           └── config.json
```

角色相关信息的归属：

| 信息 | 目标位置 |
|------|----------|
| owner/admin 名单 | `evolclaw.json`、`agents/defaults.json`、`agents/{aid}/config.json` |
| owner/admin 能力 | 代码硬编码 |
| 内置用户角色基线 | 代码硬编码 |
| 自定义用户角色定义 | `agents/{aid}/config.json.roles.definitions` |
| 私聊默认角色 / 群默认兜底 | `agents/{aid}/config.json.roles.defaultRoles`；可设为 `null` 表示无默认角色 |
| 某私聊用户的角色 | `agents/{aid}/relations/{privatePeerKey}/config.json.roles.assigned` |
| 某群的默认角色 | `agents/{aid}/relations/{groupPeerKey}/config.json.roles.assigned` |
| 某群成员的专属角色 | `agents/{aid}/relations/{groupPeerKey}/config.json.roles.members[memberAid]` |

## 1. 管理权限（owner / admin）

### 1.1 配置在哪里

管理权限由“身份名单 + 代码能力”组成。

身份名单配置在 config 中：

```jsonc
// agents/{aid}/config.json
{
  "owners": ["alice.aid.pub"],
  "admins": ["bob.aid.pub"]
}
```

层级建议：

| 层级 | 文件 | 建议用途 |
|------|------|----------|
| 进程级 | `{evolclaw_home}/evolclaw.json.owners` | daemon / control 面最高管理者 |
| 全局级 | `{evolclaw_home}/agents/defaults.json.owners/admins` | 多 agent 共享的默认管理名单 |
| Agent 级 | `{evolclaw_home}/agents/{aid}/config.json.owners/admins` | 单 agent 专属管理名单 |
| Relation 级 | 不允许 | 关系级不能定义管理身份 |

能力定义只在代码中：

```ts
OWNER_CAPABILITIES = allOperations
ADMIN_CAPABILITIES = userPlaneManagement + normalOperations - ownerOnlyDangerousOperations
```

### 1.2 如何保护

管理身份受 config 体系保护：

- Hook 禁止 agent 直接读写 `evolclaw.json`、`defaults.json`、agent `config.json`。
- 修改必须走 ConfigManager / CLI / ECWeb / control API。
- schema 校验 `owners` / `admins` 必须是 AID 列表。
- 配置修改进入 `config-audit.jsonl`。
- 快照机制可回滚错误配置。

管理能力受代码保护：

- owner/admin 不从 `roles.definitions` 读取。
- `roles.definitions.owner` / `roles.definitions.admin` 必须被 schema 或加载逻辑拒绝。
- relation config 里出现 `owners` / `admins` 必须被 schema 拒绝。

### 1.3 怎么修改

| 修改目标 | 谁能改 | 入口 |
|----------|--------|------|
| 增删 owner | owner | control / ECWeb / owner API |
| 增删 admin | owner | control / ECWeb / admin API |
| 修改 admin 能力边界 | 开发者 | 代码评审 + 发版 |

管理名单修改约束：

1. admin 不能修改 owner 名单。
2. admin 不能把自己或他人提升为 owner。
3. agent 不能直接写 config 文件。
4. 未经 AUN 认证的 AID 不能触发管理面判定。

### 1.4 怎么使用

每次请求先做管理面判定：

```text
1. AUN 认证发送方 AID
2. 若 authenticatedAid ∈ owners → owner
3. 否则若 authenticatedAid ∈ admins → admin
4. 否则进入用户角色解析
```

命中 owner/admin 后直接使用代码中的管理能力，不再查用户角色配置。

### 1.5 怎么添加权限

owner 能力恒为全集，不通过配置添加。

admin 新增能力必须改代码中的 `ADMIN_CAPABILITIES`。这样做是刻意的：管理能力边界属于可信计算基，不能通过 config 改大。

## 2. 用户角色（内置 + 自定义）

### 2.1 配置在哪里

用户角色定义放在 agent 级 config：

```text
{evolclaw_home}/agents/{aid}/config.json
```

推荐 schema 结构：

```jsonc
{
  "roles": {
    "defaultRoles": {
      "private": null,
      "group": "visitor"
    },
    "definitions": {
      "member": {
        "description": "团队成员",
        "allowAccess": true,
        "permissions": {
          "permissionMode": {
            "default": "auto",
            "allowOverride": false
          }
        },
        "commandPermissions": {
          "category:read": { "allow": true },
          "category:write-own": { "allow": true },
          "*": { "allow": false }
        }
      },
      "visitor": {
        "description": "访客，低信任只读访问者",
        "allowAccess": true,
        "permissions": {
          "permissionMode": {
            "default": "readonly",
            "allowOverride": false
          }
        },
        "commandPermissions": {
          "category:read": { "allow": true },
          "*": { "allow": false }
        }
      },
      "reviewer": {
        "description": "只读审阅者",
        "allowAccess": true,
        "permissions": {
          "baseagents.claude.model": {
            "default": "claude-haiku-4-5-20251001",
            "allowOverride": false,
            "allowedModels": ["claude-haiku-*"]
          },
          "permissionMode": {
            "default": "readonly",
            "allowOverride": false
          }
        },
        "commandPermissions": {
          "category:read": { "allow": true },
          "*": { "allow": false }
        }
      }
    }
  }
}
```

说明：

- `defaultRoles`：私聊/群聊没有显式角色时的兜底；值可为 `null`，表示没有默认角色并直接拒绝访问。
- `definitions`：本 agent 的用户角色定义。
- `member` / `visitor` 是内置用户角色，可在这里收紧或覆盖用户面配置；`visitor` 中文名为“访客”。
- `reviewer` 等是自定义角色。
- `owner` / `admin` 不属于用户角色，不能写入 `definitions`。

### 2.2 如何保护

用户角色定义不再依赖独立角色文件，直接复用 agent `config.json` 保护：

- Hook 禁止 agent 直接写 agent `config.json`。
- 只允许 owner/admin 经受控 API 修改。
- agent-config schema 校验角色结构、角色名、权限字段。
- 写入 ConfigManager 后清理相关缓存。
- 变更进入 config 审计日志。
- 快照可回滚。

必须增加的角色守卫：

1. 角色名禁止 `owner`、`admin`。
2. 角色名建议限制为 `[a-z0-9_-]+`。
3. 内置角色不能删除，只能收紧。
4. 自定义角色必须通过 schema 校验。
5. 自定义角色最终能力必须经过用户面能力上限过滤。

### 2.3 怎么修改

推荐提供两层入口：

| 入口 | 面向对象 | 行为 |
|------|----------|------|
| `ec role define/update/delete` | 管理员友好 | 内部写 agent `config.json.roles.definitions` |
| `ec config set roles... --self <aid>` | 通用配置入口 | 直接写 config 字段 |

权限要求：

- owner/admin 可以定义和修改用户角色。
- member/visitor 不能修改角色定义。
- admin 不能修改 owner/admin 管理能力，因为它们不在角色定义里。

### 2.4 怎么使用

角色解析得到角色名后：

```text
1. 从代码读取内置角色基线
2. 从 agent config 读取 roles.definitions
3. 将配置覆盖合并到内置基线
4. 若是自定义角色，校验后加入角色表
5. 若角色不存在、非法或默认角色为 `null` → 无有效角色，直接拒绝
6. 对角色能力应用用户面能力上限
```

内置角色建议：

| 角色 | 用途 | 默认访问 |
|------|------|----------|
| `member` | 已信任用户 | 自身范围读写 |
| `visitor` | 访客/群默认 | 受限只读或低风险操作 |

> 不再设置 `anonymous` 内置角色。未知、未认证、缺失角色、非法角色统一视为“无有效角色”，运行时直接拒绝访问。

### 2.5 怎么添加角色

新增 `reviewer` 的推荐流程：

1. owner/admin 调用 `ec role define reviewer --self <aid>`。
2. API 生成对 `agents/{aid}/config.json.roles.definitions.reviewer` 的 patch。
3. ConfigManager 校验 schema。
4. 用户面能力上限过滤越界权限。
5. 写入 config、记录审计、刷新缓存。
6. 后续可在 relation config 中把用户或群分配为 `reviewer`。

## 3. 用户权限（角色能力）

### 3.1 配置在哪里

用户权限是角色定义的一部分，放在：

```text
agents/{aid}/config.json.roles.definitions.{role}
```

两类权限：

| 类型 | 字段 | 作用 |
|------|------|------|
| 字段级权限 | `permissions` | 控制模型、permissionMode、chatmode 等字段默认值和是否可覆盖 |
| 命令级权限 | `commandPermissions` | 控制能否执行某个 operation |

能力上限放在代码中，不放 config：

```ts
USER_PLANE_CAPABILITY_CEILING = {
  allowedOperations: [...],
  deniedOperations: ['role.assign', 'system.restart', 'storage.delete', ...],
  dangerousOperations: []
}
```

### 3.2 如何保护

用户权限保护分三层：

1. **配置保护**：角色能力写在 agent `config.json`，由 Hook/API/schema/审计/快照保护。
2. **能力上限**：配置声明能力必须与代码白名单取交集。
3. **运行时约束**：`ownPeerOnly`、`ownAgentOnly`、`privateOnly`、`groupOnly` 等约束限制使用范围。

危险规则：

- 用户面角色不允许获得管理操作。
- 用户面角色不允许获得 owner/admin 专属危险操作。
- `*` 通配不能放行危险操作。
- 危险操作必须显式授权，但用户面能力上限默认不包含危险操作。

### 3.3 怎么添加权限

给角色加命令权限：

```jsonc
{
  "roles": {
    "definitions": {
      "reviewer": {
        "commandPermissions": {
          "session.list": {
            "allow": true,
            "scopes": ["relation"],
            "constraints": { "ownPeerOnly": true }
          }
        }
      }
    }
  }
}
```

给角色限制模型：

```jsonc
{
  "roles": {
    "definitions": {
      "reviewer": {
        "permissions": {
          "baseagents.claude.model": {
            "default": "claude-haiku-4-5-20251001",
            "allowOverride": false,
            "allowedModels": ["claude-haiku-*"]
          }
        }
      }
    }
  }
}
```

如果要添加的能力超出用户面能力上限，配置层写入也不会生效。必须先改代码能力上限并发版。

## 4. 角色归属（对用户 / 对群分配角色）

### 4.1 配置在哪里

角色归属放在 relation 级 config：

```text
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json
```

#### 私聊用户

```jsonc
// agents/bot.aid.pub/relations/aun#alice.aid.pub/config.json
{
  "roles": {
    "assigned": "member"
  }
}
```

#### 群默认

```jsonc
// agents/bot.aid.pub/relations/aun#grp-123/config.json
{
  "roles": {
    "assigned": "visitor"
  }
}
```

#### 群成员专属

```jsonc
// agents/bot.aid.pub/relations/aun#grp-123/config.json
{
  "roles": {
    "assigned": "visitor",
    "members": {
      "bob.aid.pub": "member",
      "eve.aid.pub": "reviewer"
    }
  }
}
```

### 4.2 为什么放 relation config

相对独立 `role-assignments.json`，relation config 更适合目标设计：

- config 体系已经有完整保护，不需要新增授权文件保护。
- 私聊角色与该用户的模型、chatmode、permissionMode 等关系级配置放在一起。
- 群成员角色是“群 × 人”的关系，放在群 relation config 的 `roles.members` 下最自然。
- 快照、schema、审计、迁移都复用既有配置体系。
- 单个 relation 文件损坏只影响该用户或该群，影响面更小。

### 4.3 如何保护

relation 角色归属受 relation `config.json` 保护：

- Hook 禁止 agent 直接写。
- relation-config schema 校验 `roles.assigned` 和 `roles.members`。
- ConfigManager 是唯一写入入口。
- owner/admin 才能改 role assignment 字段。
- `roles.assigned` / `roles.members[*]` 禁止写 `owner` / `admin`。
- role 必须存在于内置角色或 agent `roles.definitions`。

### 4.4 怎么修改

| 操作 | 写入位置 |
|------|----------|
| 给私聊用户分配角色 | 私聊 relation `roles.assigned` |
| 撤销私聊用户角色 | 删除私聊 relation `roles.assigned` |
| 给群设置默认角色 | 群 relation `roles.assigned` |
| 撤销群默认角色 | 删除群 relation `roles.assigned` |
| 给群成员设置专属角色 | 群 relation `roles.members[memberAid]` |
| 撤销群成员专属角色 | 删除群 relation `roles.members[memberAid]` |

建议提供命令：

```bash
ec role assign --self bot.aid.pub --peer aun#alice.aid.pub --role member
ec role assign --self bot.aid.pub --group aun#grp-123 --role visitor
ec role assign --self bot.aid.pub --group aun#grp-123 --member bob.aid.pub --role member
ec role revoke --self bot.aid.pub --peer aun#alice.aid.pub
ec role revoke --self bot.aid.pub --group aun#grp-123 --member bob.aid.pub
```

命令只是友好入口，实际仍写 relation `config.json`。

## 5. 默认角色

默认角色配置在 agent 级 config：

```jsonc
{
  "roles": {
    "defaultRoles": {
      "private": null,
      "group": "visitor"
    }
  }
}
```

建议默认：

| 场景 | 默认角色 | 理由 |
|------|----------|------|
| 私聊 | `null` | 陌生私聊默认无角色，直接拒绝 |
| 群聊 | `visitor` | 群里通常需要最小可用读/回复能力；若希望陌生群也拒绝，可设为 `null` |

代码兜底：

```text
roles.defaultRoles.private 缺失 → null → 无角色拒绝
roles.defaultRoles.group 缺失 → visitor（推荐兜底，可按需改为 null）
```

如果默认角色名不存在或非法，视为无有效角色并直接拒绝。

## 6. 私聊角色判断流程

上下文：

```text
selfAid = 当前 agent AID
actorAid = AUN 已认证发言人 AID
chatType = private
privatePeerKey = {channelType}#{urlEncode(actorAid)}
```

流程：

```text
1. AUN 认证 actorAid
   未认证 → actorAid 不进入管理面，后续只能落用户面最小权限

2. 管理面判定
   actorAid ∈ owners → owner
   actorAid ∈ admins → admin

3. 读取私聊 relation config
   agents/{selfAid}/relations/{privatePeerKey}/config.json

4. 若 relation.roles.assigned 存在
   → candidateRole = relation.roles.assigned

5. 否则
   → candidateRole = agent.roles.defaultRoles.private ?? null

6. 校验 candidateRole
   null / 不存在 / 非法 / owner / admin → 无有效角色，直接拒绝

7. 加载角色定义并应用能力上限
```

优先级：

```text
owner/admin > private relation roles.assigned > defaultRoles.private > 无角色拒绝
```

## 7. 群聊角色判断流程

上下文：

```text
selfAid = 当前 agent AID
actorAid = AUN 已认证发言人 AID
groupId = 群 ID
groupPeerKey = {channelType}#{urlEncode(groupId)}
privatePeerKey = {channelType}#{urlEncode(actorAid)}
```

流程：

```text
1. AUN 认证 actorAid

2. 管理面判定
   actorAid ∈ owners → owner
   actorAid ∈ admins → admin

3. 读取群 relation config
   agents/{selfAid}/relations/{groupPeerKey}/config.json

4. 群成员专属角色
   若 groupConfig.roles.members[actorAid] 存在
   → candidateRole = groupConfig.roles.members[actorAid]

5. 私聊角色继承
   否则读取 agents/{selfAid}/relations/{privatePeerKey}/config.json
   若 privateConfig.roles.assigned 存在
   → candidateRole = privateConfig.roles.assigned

6. 群默认角色
   否则若 groupConfig.roles.assigned 存在
   → candidateRole = groupConfig.roles.assigned

7. 系统群默认
   否则 → candidateRole = agent.roles.defaultRoles.group ?? 'visitor'

8. 校验 candidateRole
   null / 不存在 / 非法 / owner / admin → 无有效角色，直接拒绝

9. 加载角色定义并应用能力上限
```

优先级：

```text
owner/admin
> 群成员专属 roles.members[actorAid]
> 私聊 roles.assigned 继承
> 群 roles.assigned 默认
> defaultRoles.group
> 无角色拒绝
```

说明：

- 群成员专属最精确，优先级最高。
- 私聊继承表示“我在私聊里信任这个人，在群里默认也信任”，但可被群成员专属覆盖。
- 群默认用于整群统一策略。

## 8. 完整鉴权链路

```text
接入请求
  │
  ▼
AUN 身份认证
  │
  ▼
管理面判定（owners/admins）
  │ 命中
  ├────────────► owner/admin 代码能力 → 操作鉴权
  │
  │ 未命中
  ▼
用户角色解析
  私聊：relation roles.assigned → defaultRoles.private
  群聊：members[actor] → private assigned → group assigned → defaultRoles.group
  │
  ▼
角色定义加载
  代码内置基线 + agent config roles.definitions
  │
  ▼
能力上限过滤
  role capability ∩ USER_PLANE_CAPABILITY_CEILING
  │
  ▼
命令级鉴权
  commandPermissions + scope + constraints + dangerous gate
  │
  ▼
允许 / 拒绝 / 审计
```

## 9. 修改 / 使用速查表

| 我想做什么 | 改哪里 | 谁能做 | 推荐入口 |
|-----------|--------|--------|----------|
| 增删 owner | agent `config.json.owners` | owner | `ec owner add/remove` |
| 增删 admin | agent `config.json.admins` | owner | `ec admin add/remove` |
| 扩大 admin 能力 | 代码 | 开发者 | PR + 发版 |
| 新增自定义角色 | agent `config.json.roles.definitions.{role}` | owner/admin | `ec role define` |
| 修改角色权限 | agent `config.json.roles.definitions.{role}` | owner/admin | `ec role update` |
| 修改默认角色 | agent `config.json.roles.defaultRoles` | owner/admin | `ec role default` |
| 给私聊用户分配角色 | 私聊 relation `config.json.roles.assigned` | owner/admin | `ec role assign --peer` |
| 给群设置默认角色 | 群 relation `config.json.roles.assigned` | owner/admin | `ec role assign --group` |
| 给群成员单独设角色 | 群 relation `config.json.roles.members[aid]` | owner/admin | `ec role assign --group --member` |
| 调整某用户模型/行为 | 对应 relation `config.json` 的模型/行为字段 | 按字段权限 | `ec config set --peer` |
| 开放用户面新操作 | 代码能力上限 | 开发者 | PR + 发版 |

## 10. Schema 建议

### 10.1 AgentConfig.roles

```ts
interface AgentRolesPolicy {
  defaultRoles?: {
    private?: string | null;
    group?: string | null;
  };
  definitions?: Record<string, UserRoleDefinition>;
}
```

### 10.2 RelationConfig.roles

```ts
interface RelationRolesPolicy {
  assigned?: string;
  members?: Record<string, string>;
}
```

私聊 relation 使用 `assigned`。

群 relation 使用：

- `assigned`：群默认角色；
- `members`：群内成员专属角色。

### 10.3 UserRoleDefinition

```ts
interface UserRoleDefinition {
  description: string;
  allowAccess?: boolean;
  permissions?: Record<string, FieldPermission>;
  commandPermissions?: Record<string, CommandPermission>;
}
```

schema 必须禁止：

- `definitions.owner`
- `definitions.admin`
- `assigned = owner/admin`
- `members.* = owner/admin`

## 11. 迁移建议

如果当前系统仍存在旧文件：

| 旧位置 | 新位置 |
|--------|--------|
| `{evolclaw_home}/roles.json.defaultRoles` | `agents/{aid}/config.json.roles.defaultRoles` |
| `{evolclaw_home}/roles.json.roles.{role}` | `agents/{aid}/config.json.roles.definitions.{role}` |
| `role-assignments.json private::{peer}` | `relations/{privatePeerKey}/config.json.roles.assigned` |
| `role-assignments.json group::{group}` | `relations/{groupPeerKey}/config.json.roles.assigned` |
| `role-assignments.json group-member::{group}::{peer}` | `relations/{groupPeerKey}/config.json.roles.members[peer]` |

迁移策略：

1. 先读旧文件，生成 config patch。
2. 经 ConfigManager 写入 agent/relation config。
3. 生成快照。
4. 保留旧文件只读一版作为回滚参考。
5. 新代码只读 config，不再读旧文件。

## 12. 关键不变量

1. owner/admin 能力永远来自代码。
2. owner/admin 身份只能由 config 名单 + AUN 已认证 AID 判定。
3. 用户角色定义只放 agent `config.json`。
4. 用户/群/群成员角色归属只放 relation `config.json`。
5. 用户角色不能定义或分配为 owner/admin。
6. 用户角色能力永远受代码上限封顶。
7. 未知角色、非法配置、缺失配置一律变为无有效角色并直接拒绝。
8. agent 不能直接写任何 config 文件。
9. 所有角色配置修改都走 ConfigManager / CLI / API，并纳入 schema、审计、快照、回滚。
