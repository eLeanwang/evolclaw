## 1. 角色（Roles）

### 1.1 内置角色

系统定义 5 个内置角色，构成隐式的权限层级（从高到低）。类型枚举位于 `src/types.ts`：

```ts
export type BuiltinRole = 'owner' | 'admin' | 'member' | 'guest' | 'anonymous';
```

定义位置：`src/config/builtin-roles.ts` 的 `getBuiltinRolesConfig()`。

| 角色 | 说明 | allowAccess | permissionMode（默认，不可覆盖） | 默认模型 |
|------|------|:-----------:|--------------------------------|----------|
| `owner` | Agent 拥有者，完全控制 | `true` | `bypass` | `claude-opus-4-8`，`allowedModels: ['*']` |
| `admin` | 管理员，受控的危险操作权限 | `true` | `request` | `claude-sonnet-4-6`，允许 `claude-opus-*` / `sonnet-*` / `haiku-*` |
| `member` | 团队成员，自身范围访问 | `true` | `auto` | `claude-sonnet-4-6`，允许 `claude-sonnet-*` / `haiku-*` |
| `guest` | 访客，私聊只读 + 自身范围 | `true` | `readonly` | `claude-haiku-4-5-20251001`，仅 `claude-haiku-*` |
| `anonymous` | 匿名用户，无命令访问权 | **`false`** | `readonly` | `claude-haiku-4-5-20251001` |

### 1.2 默认角色分配

```ts
defaultRoles: { private: 'anonymous', group: 'guest' }
```

- 私聊会话默认落到 `anonymous`
- 群聊会话默认落到 `guest`

### 1.3 角色数据结构

`RoleDefinition`（`src/types.ts`）由三部分组成：

- `description` — 说明文本
- `allowAccess?` — 是否允许访问命令（默认 `true`，`anonymous` 显式为 `false`）
- `permissions: Record<string, FieldPermission>` — 字段级权限（模型、effort、chatmode、dispatch 等）
- `commandPermissions?: Record<string, CommandPermission>` — 命令级权限规则

`FieldPermission`：

```ts
{ default, allowOverride, allowedModels?, allowedValues?, reason? }
```

### 1.4 层级/继承实现方式

系统**没有显式的数字 level 字段**，层级通过以下方式体现：

- `permissions` 的默认值与 `allowedModels` 白名单逐级收紧
- `commandPermissions` 规则粒度逐级收窄（owner/admin 用 `'*': {allow:true}`，member 用 category 白名单，guest 逐条列举，anonymous 用 `'*': {allow:false}`）
- 代码中 `isAdminRole()`（`command-handler.ts`）把 `owner` 与 `admin` 归为管理员：`return role === 'owner' || role === 'admin';`

## 2. 权限控制（Permission Control）

系统包含**三层独立的权限检查**。

### 2.1 层 A：命令级鉴权（核心）

核心函数：`authorizeCommand(ctx)`，位于 `src/core/command/command-permission.ts`。
返回 `CommandAuthorizationDecision`（`allow: true` 或 `allow: false` + `code`）。

鉴权流程（按顺序，任一失败即拒绝）：

1. **操作存在性** — `getOperationMeta(operation)` 查 operation registry，未知 → `NOT_ALLOWED`
2. **来源检查** — `opMeta.sources` 不含 `ctx.source` → `NOT_ALLOWED`（如 `role.assign` 仅限 `ecweb`/`control`）
3. **角色存在性** — `getRoleDefinition(role)` 未知 → `ROLE_ACCESS_DENIED`
4. **角色访问开关** — `roleDef.allowAccess === false` → `ROLE_ACCESS_DENIED`（`anonymous` 在此被拦）
5. **规则匹配** — `matchCommandPermission()` 按优先级匹配，无匹配 → `NO_PERMISSION`
6. **allow 判断** — 匹配到的 `permission.allow === false` → `NOT_ALLOWED`
7. **危险操作门禁** — `opMeta.dangerous` 且非显式危险授权 → `DANGEROUS_NOT_GRANTED`
8. **scope 检查** — `intent.scope` 不在 `permission.scopes || opMeta.defaultScopes` → `SCOPE_MISMATCH`
9. **约束检查** — `checkConstraints()` 不满足 → `ARGUMENT_MISMATCH`

**规则匹配优先级** `getRuleRank()`（rank 越高越优先；同 rank 下 deny 规则 +1，即同级 deny 胜过 allow）：

| 规则形式 | rank |
|----------|:----:|
| 精确匹配 operation | 1000 |
| namespace.*（如 `model.*`） | 800 |
| `category:<类别>` | 600 |
| `dangerous:*` | 400 |
| `*`（仅对非危险操作生效） | 200 |

**显式危险授权** `isExplicitDangerousGrant()`：要求 `permission.allow === true && permission.dangerous === true`，且规则是 `dangerous:*` 或精确匹配（非通配、非 category）。
危险操作无法通过 `'*'` 通配放行——`'*'` 规则的 rank 判定里显式排除了危险操作。

调用入口示例：`slash-handler.ts`（source=`slash`）、`menu-handler.ts`、`command-handler.ts`、`ec-command-permission.ts`、`cli/model.ts`。

### 2.2 层 B：EC 命令鉴权

`src/core/command/ec-command-permission.ts` 的 `authorizeEcCommand(command, ctx)`，用于拦截 agent 在会话内通过 Bash 调用的 `ec msg|group|ctl send|file` 命令：

- 用 `parseEvolclawSendCommand()`（`permission.ts`）解析
- `toOperationId()` 映射为 `ec.<scope>.<action>`（如 `ec.msg.send`）
- `resolveCommandScope()`：`ctl`→`control`；`msg/group`→有 selfAid 则 `relation`，否则 `agent`
- 复用 `authorizeCommand()`，source 固定为 `agent-tool`
- 返回 `null` 表示非 EC 命令（调用方回退到工具层白名单/危险检测）；返回非 `null` 即最终裁决

### 2.3 层 C：模型权限

`src/core/model/model-permission.ts`：

- `getRoleModelPermission(role, baseagent)` — 读取 `baseagents.<ba>.model` 的 `FieldPermission`，返回 `{ defaultModel, allowOverride, allowedModels, constrained }`
- `validateModelSelectionForRole()` — 返回 code `MODEL_OVERRIDE_DISABLED` / `MODEL_NOT_ALLOWED` / `INVALID_VALUE`
- 其余：`isModelAllowedForRoleBaseagent()`、`filterModelsForRole()`、`constrainResolvedModelForRole()`
- 白名单匹配用 `isModelAllowedByPatterns()`（`role-constraints.ts`），支持 `*` 全通配与 `claude-sonnet-*` 前缀匹配

### 2.4 角色解析（谁是什么角色）

`src/config/peer-role-resolver.ts` 的 `resolvePeerRoleDetail(ctx)` 决定 peer 的有效角色，优先级：

1. **静态 owner** — `isStaticAgentOwner()` 检查 agent `config.json` 的 `owners` 数组 → `owner`
2. **私聊** — `getPrivateRoleAssignment()`，否则 `defaultRoleFor('private')`
3. **群聊** — group-member assignment → private-inherited → group-default → `defaultRoleFor('group')`

`isAuthenticated(userId)` 用正则 `/^[a-z0-9_-]+\.(aid|agentid)\.pub$/i` 判断是否为认证 AID。**未知角色一律降级为 `anonymous`。**

## 3. 权限配置位置（Config Location）

### 3.1 配置根目录

由 `resolveRoot()`（`src/paths.ts`）解析，优先级：

1. 环境变量 `EVOLCLAW_HOME`
2. 当前目录（若存在 `agents/defaults.json`）
3. `~/.evolclaw`

### 3.2 配置文件

通过 `ConfigTarget` 枚举（`src/config/config-manager.ts`）和 `targetPath()` 映射：

| 配置 | ConfigTarget | 磁盘路径 | 说明 |
|------|--------------|----------|------|
| 全局角色定义 | `Roles` | `{root}/roles.json` | **overlay/diff 格式** |
| 角色分配 | `RoleAssignments` | `{root}/agents/{aid}/role-assignments.json` | 每 agent 一份 |
| Agent 配置 | `Agent` | `{root}/agents/{aid}/config.json` | 含 `owners` 数组 |
| 进程配置 | `Process` | `{root}/evolclaw.json` | |

### 3.3 roles.json 的 overlay 机制（重要）

`roles.json` **不存全量**，只存相对 `getBuiltinRolesConfig()` 基线的差异（diff）：

- **读取**：`resolveRoles()` = `mergeRolesConfig(builtin, overlay)`
- **写入**：`writeRoles()` = `diffRolesConfig(builtin, full)` 后写盘
- 合并/diff 逻辑在 `src/config/roles-merge.ts`，`permissions` 与 `commandPermissions` 均逐字段合并

### 3.4 Schema

- `kits/schemas/roles.schema.{1,2,3,4}.json`，当前版本 **v4**（`$schema_version: 4`）
- v4 相对 v3 新增 `commandPermissions` 字段
- schema 标记 `x-permission: "H"`（H 类保护文件，见第 5 节）
- role-assignments 用 `$schema_version: 2`

### 3.5 缓存

`src/config/roles-cache.ts`：`ROLES_CACHE = Map<string, RoleDefinition>`。
`roles.ts` 的 `getRoleDefinition()` 先查缓存再读配置；`writeRoles()` 写入后会 `clearRolesCache()`。

## 4. 角色权限映射（Role Permissions）

### 4.1 Operation Registry

`src/core/command/operation-registry.ts` 定义所有操作的元数据：

```ts
OperationMeta { id, category, dangerous, defaultScopes, description, sources? }
```

相关枚举（`src/types.ts`）：

- `OperationCategory`：`read | diagnose | write-own | write-agent | process | dangerous`
- `CommandScope`：`relation | role | agent | process | filesystem | control | raw-cli`
- `CommandSource`：`slash | menu | menu.cli | ctl | ipc | ecweb | control | agent-tool`

注册的操作命名空间（约 50 个）：`model.*`（list/current/info/check/use/effort/reset）、`session.*`、`file.*`、`trigger.*`、`role.assign`/`role.revoke`、`agent.*`（list/show/getConfig/create/reload/delete）、`system.*`（status/restart/upgrade）、`stats.*`（含危险的 `stats.sqlReadonly`、`stats.rebuild`）、`aid.*`、`storage.*`（含危险的 `storage.delete`）、`gateway.read`/`gateway.write`、`config.read`/`config.write`、`ec.msg.*`/`ec.group.*`/`ec.ctl.*`、`cli.exec.raw`、`shell.exec`（预留）、`rce.exec`（预留）。

### 4.2 各角色的 commandPermissions

**owner / admin**（几乎全权）：

```ts
'role.assign': { allow: true, scopes: ['agent'] },
'role.revoke': { allow: true, scopes: ['agent'] },
'*': { allow: true },
'dangerous:*': { allow: true, dangerous: true, constraints: { requireDaemonOwner: true } },
```

区别：owner 的 `permissionMode` 默认 `bypass` 且模型 `['*']`；admin 默认 `request`，模型受白名单约束，`dispatch` 只能 `mention`。

**member**（own-scope）：

```ts
'role.assign': { allow: false }, 'role.revoke': { allow: false },
'category:read': { allow: true },
'category:write-own': { allow: true },
'model.*': { allow: true, scopes: ['relation','agent'], constraints: { ownPeerOnly: true, ownAgentOnly: true } },
'ec.msg.send': { allow: true, constraints: { ownPeerOnly: true } },
'ec.msg.file': { allow: true, constraints: { ownPeerOnly: true } },
'ec.group.send': { allow: true, constraints: { groupOnly: true } },
'ec.group.file': { allow: true, constraints: { groupOnly: true } },
'ec.ctl.*': { allow: false },
'cli.exec.raw': { allow: false, dangerous: true },
```

**guest**（私聊只读 + 自身范围，逐条列举）：

```ts
'role.assign'/'role.revoke': { allow: false },
'model.list'/'model.current': { allow: true, scopes: ['relation'], constraints: { ownPeerOnly, ownAgentOnly, privateOnly } },
'model.use': { allow: true, scopes: ['relation'], constraints: { ownPeerOnly, ownAgentOnly, privateOnly, requireFieldOverride: 'baseagents.claude.model' } },
'session.list': { allow: true, scopes: ['relation'], constraints: { ownPeerOnly, privateOnly } },
'ec.msg.send': { allow: true, scopes: ['relation'], constraints: { ownPeerOnly, privateOnly } },
'ec.msg.file'/'ec.group.*'/'ec.ctl.*': { allow: false },
'cli.exec.raw': { allow: false, dangerous: true },
'dangerous:*': { allow: false, dangerous: true },
```

**anonymous**：`allowAccess: false`（第 4 步就被拦），并且 `'*': { allow: false }`。

### 4.3 角色分配（Role Assignments）

`src/config/role-assignments.ts`。三种 scope `RoleAssignmentScope = 'private' | 'group' | 'group-member'`，key 生成规则：

- `private::{encodeURIComponent(peerId)}`
- `group::{groupId}`
- `group-member::{groupId}::{peerId}`

CRUD 接口：`setPrivate/Group/GroupMemberRoleAssignment`、`getXxx`、`deleteXxx`、`listRoleAssignments`。
`role.assign`/`role.revoke` 操作 sources 限 `ecweb`/`control`，scopes 限 `agent`——即分配角色本身也是受控命令。

## 5. 权限保护（Protection）

### 5.1 约束系统（Constraints）

`checkConstraints()`（`command-permission.ts`），`CommandPermissionConstraints`（`src/types.ts`）支持：

- `ownPeerOnly` — 命令参数中的 peer/peerKey 只能是 actor 自己（防越权操作他人）
- `ownAgentOnly` — `args.self` 必须等于 `ctx.selfAid`
- `privateOnly` / `groupOnly` — 限定 chatType
- `requireDaemonOwner` — `ctx.isDaemonOwner` 必须为真
- `requireControlChannel` — `ctx.fromControlChannel` 必须为真
- `requireExplicitDangerousGrant` — 强制显式危险授权
- `requireFieldOverride` — 校验 `permissions[field].allowOverride` 且值在白名单内
- `forbiddenFlags` / `allowedArgs` / `deniedArgs` — 参数级白/黑名单
- `allowedConfigKeys` / `allowedPrefixes` — config key 与路径前缀白名单（沙箱）
- 执行环境约束：`timeoutMs` / `outputLimitBytes` / `cwdPolicy` / `envAllowlist`

### 5.2 防特权升级

- `role.assign`/`role.revoke` 对 member/guest/anonymous 硬编码 `{ allow: false }`，且 operation sources 仅 `ecweb`/`control`（普通会话渠道无法触发）
- 危险操作（`dangerous: true`）永远无法被 `'*'` 通配放行，必须 `dangerous:*` 显式授权 + `requireDaemonOwner`
- 各角色 `permissionMode` 均 `allowOverride: false`，关系级配置不能提升自己的权限模式
- 未知角色统一降级到 `anonymous`

### 5.3 运行时命令防护（`src/core/permission.ts`）

独立于 operation 鉴权的工具层防护（PreToolUse hook / canUseTool）：

- **绝对禁止 `ABSOLUTE_FORBIDDEN`**（任何角色/模式都不可授权）：`shutdown`、`reboot`、`mkfs`、`format C:`、`dd if=...of=/dev`。经 `checkBlacklist()` 拦截。
- **危险命令 `DANGEROUS_PATTERNS`**（需用户审批）：`rm -rf`、`sudo`、`chmod 777`、写设备文件、Windows `rd /s`/`del /s`/`reg delete`/`net stop`、`pkill`/`killall`。经 `checkDangerousCommand()` 检测，`requestDangerousCommandPermission()` 走审批网关。
- **只读模式 `READONLY_WRITE_PATTERNS`**（`checkReadonly()`）：只读模式下 Write/Edit 只允许写入 `{projectPath}/.evolclaw/tmp/`，Bash 拦截 mkdir/touch/cp/mv/rm/git commit/npm install 等写入意图。
- **H 类文件保护 `H_CLASS_PATTERNS`**（`checkHClassWrite()`）：agent 不可直接写入的系统关键文件——`evolclaw.json`、`agents/defaults.json`、`agents/*/config.json`、`agents/*/relations/*/config.json`、`backups/config/`、`.snapshots/`、`CA/`、`aids/*/cert|keys/`、`.device_id`、`.env`、`.seed.`、`.migrated-` 等。roles schema 也标记 `x-permission: "H"`。

### 5.4 人工审批网关 `PermissionGateway`（`permission.ts`）

三态决策 `PermissionDecision = 'allow' | 'always' | 'deny'`。`requestPermission()` 通过富交互卡片（允许/始终允许/拒绝）或文本降级请求用户。`always` 缓存到 `alwaysAllow` Map；`clearAlwaysAllow()` 在切换权限模式时重置；`cancelAll()` 中断时取消 pending 请求。

### 5.5 审计日志（`src/core/command/command-audit.ts`）

`auditCommandAuthorization(event)`，触发条件 `shouldAudit`：

```ts
decision === 'deny' || (decision === 'allow' && dangerous) ||
operation.startsWith('role.') || operation === 'cli.exec.raw'
```

即所有拒绝、危险操作放行、角色变更、原始 CLI 都记录。deny 用 `logger.warn`，marker 为 `DENY`/`DANGEROUS_ALLOW`/`ALLOW`。`hashArgv()` 用 SHA256 取前 16 位对命令参数做哈希（不落明文）。审计记录含 role、actorId、matchedRule、code、reason 等。
