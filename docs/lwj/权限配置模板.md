# EvolClaw 完整权限配置模板（按权限域）

> 本文档按“权限域”整理 EvolClaw 的权限配置模板，并说明当前系统已有的权限控制如何落到 config.json 中。
> 生成日期：2026-07-07
> 参考代码：`src/config/builtin-roles.ts`、`src/core/command/operation-registry.ts`、`src/core/command/command-permission.ts`、`src/config/role-constraints.ts`、`src/core/permission.ts`

---

## 1. 先看结论

权限配置不要只写一堆 `commandPermissions`。应该按权限域理解，再映射到系统已有控制点。

| 权限域 | 配置位置 | 当前系统控制点 |
|--------|----------|----------------|
| 管理身份权限 | `owners` / `admins` | AUN 已认证 AID + config 名单 |
| 模型权限 | `permissions.baseagents.*` + `model.*` | `FieldPermission` + `model.*` operation |
| 执行模式权限 | `permissions.permissionMode` | `permissionMode` + 工具层 Hook |
| 文件读取权限 | `file.list` / `file.fetch` | Operation Registry + `allowedPrefixes` |
| 文件写入权限 | `permissionMode` + Bash/工具层 | `checkReadonly` + H 类保护 + Bash 危险检测 |
| 可操作路径 | 每个命令的 `constraints.allowedPrefixes` | `checkAllowedPrefixes()` |
| Bash 命令执行权限 | `cli.exec.raw` / `shell.exec` / `rce.exec` + `permissionMode` | Operation Registry + `checkBlacklist` + `checkDangerousCommand` |
| EC 命令执行权限 | `ec.msg.*` / `ec.group.*` / `ec.ctl.*` | `authorizeEcCommand()` + `ownPeerOnly/groupOnly` |
| 会话权限 | `session.*` | Operation Registry |
| 触发器权限 | `trigger.*` | Operation Registry |
| 配置读写权限 | `config.read` / `config.write` + `allowedConfigKeys` | Operation Registry + ConfigManager/API |
| 角色管理权限 | `role.assign` / `role.revoke` | sources 限 `ecweb/control`，用户面禁止 |
| Agent/System/Storage/AID 权限 | `agent.*` / `system.*` / `storage.*` / `aid.*` | 管理面，用户面默认禁止 |

配置文件路径沿用 `docs/config/01-overview.md`：

```text
{evolclaw_home}/evolclaw.json
{evolclaw_home}/agents/defaults.json
{evolclaw_home}/agents/{aid}/config.json
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json
```

## 2. 权限配置的三层结构

### 2.1 管理身份

管理身份放在 agent 级 config：

```jsonc
{
  "owners": ["alice.aid.pub"],
  "admins": ["bob.aid.pub"]
}
```

说明：

- `owner/admin` 是管理权限面，不是用户角色。
- `owner/admin` 的能力不放在 `roles.definitions` 里。
- AUN 负责认证远程 AID，EvolClaw 只比对已认证 AID 是否在名单中。

### 2.2 用户角色定义

用户角色定义放在：

```text
{evolclaw_home}/agents/{aid}/config.json
```

```jsonc
{
  "roles": {
    "defaultRoles": {
      "private": null,
      "group": "visitor"
    },
    "definitions": {
      "visitor": {
        "description": "访客，低信任只读访问者",
        "allowAccess": true,
        "permissions": {},
        "commandPermissions": {}
      }
    }
  }
}
```

### 2.3 用户/群角色归属

角色归属放在 relation 级 config：

```jsonc
// 私聊：{evolclaw_home}/agents/{aid}/relations/aun#alice.aid.pub/config.json
{
  "roles": {
    "assigned": "member"
  }
}
```

```jsonc
// 群：{evolclaw_home}/agents/{aid}/relations/aun#grp-123/config.json
{
  "roles": {
    "assigned": "visitor",
    "members": {
      "bob.aid.pub": "reviewer"
    }
  }
}
```

## 3. 权限域配置说明

### 3.1 模型权限

模型权限由两部分组成：

1. 字段级权限：能用什么模型、能不能覆盖默认模型。
2. 命令级权限：能不能执行 `model.list/current/use/effort/reset`。

配置模板：

```jsonc
{
  "permissions": {
    "baseagents.claude.model": {
      "default": "claude-haiku-4-5-20251001",
      "allowOverride": true,
      "allowedModels": ["claude-haiku-*", "claude-sonnet-*"]
    },
    "baseagents.claude.effort": {
      "default": "low",
      "allowOverride": true,
      "allowedValues": ["low", "medium"]
    }
  },
  "commandPermissions": {
    "model.list": { "allow": true, "scopes": ["relation"] },
    "model.current": { "allow": true, "scopes": ["relation"] },
    "model.use": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true,
        "requireFieldOverride": "baseagents.claude.model"
      }
    },
    "model.effort": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true,
        "requireFieldOverride": "baseagents.claude.effort"
      }
    },
    "model.reset": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true
      }
    }
  }
}
```

当前系统如何执行：

- `model.*` 来自 `operation-registry.ts`。
- `requireFieldOverride` 会回查角色 `permissions`。
- `allowedModels` 使用通配符匹配，如 `claude-sonnet-*`。
- 如果 `allowOverride:false`，relation config 中写了模型也会被角色默认值覆盖。

### 3.2 执行模式权限

执行模式控制底层工具行为，不等于命令权限。

配置模板：

```jsonc
{
  "permissions": {
    "permissionMode": {
      "default": "readonly",
      "allowOverride": false
    }
  }
}
```

建议：

| 角色 | permissionMode | 说明 |
|------|----------------|------|
| 无角色 | 无 | 直接拒绝访问 |
| `visitor` | `readonly` | 访客，只读或最低风险访问 |
| `reviewer` | `readonly` | 审阅 |
| `member` | `auto` | 常规协作 |
| `admin` | 代码决定，通常 `request` | 管理面 |
| `owner` | 代码决定，通常 `bypass` | 管理面 |

当前系统如何执行：

- `permissionMode` 影响 Claude/Codex/Gemini runner 的工具执行模式。
- `readonly` 会触发 `checkReadonly()`，阻止 Write/Edit/NotebookEdit 和写入型 Bash。
- `permissionMode` 不能替代 `commandPermissions`，两者都必须通过。

#### 行为参数权限必须逐字段声明

`chatmode`、`dispatch`、`show_activities`、`flush_delay`、`debounce`、`enable_rich_content` 这类 relation 可覆盖字段，也必须像模型一样明确：

- 默认值是什么；
- 是否允许 relation 覆盖；
- 如果允许，允许改成哪些值。

推荐用细粒度字段路径，而不是只写一个大对象：

```jsonc
{
  "permissions": {
    "chatmode.private": {
      "default": "interactive",
      "allowOverride": true,
      "allowedValues": ["interactive", "proactive"]
    },
    "chatmode.group": {
      "default": "proactive",
      "allowOverride": true,
      "allowedValues": ["interactive", "proactive"]
    },
    "chatmode.nothuman": {
      "default": "proactive",
      "allowOverride": false,
      "allowedValues": ["interactive", "proactive"]
    },
    "dispatch": {
      "default": "mention",
      "allowOverride": false,
      "allowedValues": ["mention", "broadcast"]
    },
    "show_activities": {
      "default": "all",
      "allowOverride": true,
      "allowedValues": ["all", "none"]
    },
    "flush_delay": {
      "default": 3,
      "allowOverride": true,
      "allowedValues": [0, 1, 3, 5, 10]
    },
    "debounce": {
      "default": 0,
      "allowOverride": true,
      "allowedValues": [0, 1, 2, 3, 5, 10]
    },
    "enable_rich_content": {
      "default": false,
      "allowOverride": true,
      "allowedValues": [true, false]
    }
  }
}
```

原则：任何 relation config 中允许出现的行为字段，都应该在角色 `permissions` 中有对应声明。没有声明的字段应按 fail-closed 处理，或至少记录审计告警。

### 3.3 文件读取权限

当前 Operation Registry 已有文件读操作：

- `file.list`
- `file.fetch`

配置模板：

```jsonc
{
  "commandPermissions": {
    "file.list": {
      "allow": true,
      "scopes": ["filesystem"],
      "constraints": {
        "allowedPrefixes": [
          "{projectPath}/",
          "{projectPath}/docs/",
          "{projectPath}/README.md"
        ]
      }
    },
    "file.fetch": {
      "allow": true,
      "scopes": ["filesystem"],
      "constraints": {
        "allowedPrefixes": [
          "{projectPath}/docs/",
          "{projectPath}/README.md"
        ]
      }
    }
  }
}
```

当前系统如何执行：

- `allowedPrefixes` 由 `checkAllowedPrefixes()` 检查。
- H 类文件仍被工具层保护，即使路径前缀误配也不能让 agent 写 config/.env/快照/密钥。

### 3.4 文件写入权限

当前系统没有普通用户可直接配置的 `file.write` operation。文件写入主要由工具层控制：

- Write/Edit/NotebookEdit
- Bash 写入命令
- permissionMode
- H 类文件保护

配置建议：

```jsonc
{
  "permissions": {
    "permissionMode": {
      "default": "readonly",
      "allowOverride": false
    }
  },
  "commandPermissions": {
    "cli.exec.raw": {
      "allow": false,
      "dangerous": true
    },
    "shell.exec": {
      "allow": false,
      "dangerous": true
    },
    "rce.exec": {
      "allow": false,
      "dangerous": true
    }
  }
}
```

如果未来要开放文件写入，应新增明确 operation，例如：

```jsonc
{
  "file.write": {
    "allow": true,
    "scopes": ["filesystem"],
    "constraints": {
      "allowedPrefixes": ["{projectPath}/.evolclaw/tmp/"]
    }
  }
}
```

但当前设计建议：

- `visitor/reviewer` 不允许文件写。
- `member` 默认不通过 raw bash 写文件。
- 文件生成类需求优先写入 `{projectPath}/.evolclaw/tmp/`。

### 3.5 可操作路径权限

路径权限不是单独的角色字段，而是放在具体命令的 constraints 中。

配置模板：

```jsonc
{
  "commandPermissions": {
    "file.fetch": {
      "allow": true,
      "scopes": ["filesystem"],
      "constraints": {
        "allowedPrefixes": [
          "{projectPath}/docs/",
          "{projectPath}/src/",
          "{projectPath}/README.md"
        ]
      }
    },
    "cli.exec.raw": {
      "allow": false,
      "dangerous": true,
      "constraints": {
        "allowedPrefixes": ["{projectPath}/"]
      }
    }
  }
}
```

路径权限必须遵守硬保护：

```text
禁止写：
{evolclaw_home}/evolclaw.json
{evolclaw_home}/agents/defaults.json
{evolclaw_home}/agents/{aid}/config.json
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json
{evolclaw_home}/.env
{evolclaw_home}/backups/config/
证书、密钥、device_id、seed、迁移标记等系统文件
```

### 3.6 Bash 命令执行权限

Bash 权限必须拆成三层理解：

1. 角色是否允许 raw/shell/rce operation。
2. permissionMode 是否允许工具写入。
3. 工具层危险命令是否被拦截或要求审批。

配置模板：

```jsonc
{
  "permissions": {
    "permissionMode": {
      "default": "request",
      "allowOverride": false
    }
  },
  "commandPermissions": {
    "cli.exec.raw": {
      "allow": false,
      "dangerous": true
    },
    "shell.exec": {
      "allow": false,
      "dangerous": true
    },
    "rce.exec": {
      "allow": false,
      "dangerous": true
    }
  }
}
```

如果是管理面代码能力，可以允许但必须显式危险授权：

```jsonc
{
  "commandPermissions": {
    "cli.exec.raw": {
      "allow": true,
      "dangerous": true,
      "scopes": ["raw-cli"],
      "constraints": {
        "requireDaemonOwner": true,
        "allowedPrefixes": ["{projectPath}/"]
      }
    }
  }
}
```

当前系统硬保护：

- 绝对禁止：`shutdown`、`reboot`、`mkfs`、`format C:`、`dd ... of=/dev`。
- 危险需审批：`rm -rf`、`sudo`、`chmod 777`、写设备文件、`rd /s`、`del /s`、`reg delete`、`net stop`、`pkill`、`killall`。
- readonly 模式阻止 `mkdir/touch/cp/mv/rm/chmod/chown/git commit/npm install/pip install` 等写入命令。

### 3.7 EC 命令执行权限

EC 命令是 agent 在会话内通过 Bash 调用 `ec msg|group|ctl send|file` 时的权限控制。

配置模板：

```jsonc
{
  "commandPermissions": {
    "ec.msg.send": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "privateOnly": true
      }
    },
    "ec.msg.file": {
      "allow": false
    },
    "ec.group.send": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "groupOnly": true
      }
    },
    "ec.group.file": {
      "allow": false
    },
    "ec.ctl.send": {
      "allow": false
    },
    "ec.ctl.file": {
      "allow": false
    }
  }
}
```

建议：

| 角色 | 私聊发送 | 私聊文件 | 群发送 | 群文件 | ctl |
|------|----------|----------|--------|--------|-----|
| 无角色 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 |
| visitor | 可选，仅私聊 own peer | 禁止 | 禁止 | 禁止 | 禁止 |
| reviewer | 禁止或只允许文本 | 禁止 | 禁止 | 禁止 | 禁止 |
| member | 允许 own peer / group | 允许或按需 | 允许 group | 允许或按需 | 禁止 |
| admin/owner | 代码管理面决定 | 代码管理面决定 | 代码管理面决定 | 代码管理面决定 | 代码管理面决定 |

当前系统如何执行：

- `ec.msg.*` / `ec.group.*` / `ec.ctl.*` 来自 Operation Registry。
- `authorizeEcCommand()` 会把 Bash 中的 EC 命令解析为 operation。
- `ownPeerOnly` 防止发给别人。
- `groupOnly` 限制只能群聊。

### 3.8 配置读写权限

配置读写是高风险权限。

配置模板：

```jsonc
{
  "commandPermissions": {
    "config.read": {
      "allow": false,
      "dangerous": true
    },
    "config.write": {
      "allow": false,
      "dangerous": true
    }
  }
}
```

如果未来给受限管理员开放某些配置写入，应限制 key：

```jsonc
{
  "config.write": {
    "allow": true,
    "dangerous": true,
    "scopes": ["process"],
    "constraints": {
      "requireControlChannel": true,
      "allowedConfigKeys": [
        "roles.defaultRoles",
        "roles.definitions.reviewer",
        "roles.assigned",
        "roles.members"
      ]
    }
  }
}
```

但目标设计建议：

- 用户面角色禁止 `config.write`。
- `roles.*` 字段只能 owner/admin 通过 ConfigManager/API 改。
- agent 不能直接写 config 文件。

### 3.9 角色管理权限

角色管理包括：

- 修改角色定义；
- 给用户/群分配角色；
- 撤销角色。

当前 operation：

```jsonc
{
  "role.assign": {
    "allow": false
  },
  "role.revoke": {
    "allow": false
  }
}
```

管理面可由代码开放：

```jsonc
{
  "role.assign": {
    "allow": true,
    "scopes": ["agent"]
  },
  "role.revoke": {
    "allow": true,
    "scopes": ["agent"]
  }
}
```

硬规则：

- `role.assign` / `role.revoke` 当前 sources 限 `ecweb` / `control`。
- 普通会话渠道不能触发角色分配。
- 分配目标不能是 `owner` / `admin`。
- owner/admin 身份只能改 `owners` / `admins` 名单。

### 3.13 Agent/System/Storage/AID 权限

这些权限属于管理面，用户角色模板中应默认拒绝。

```jsonc
{
  "commandPermissions": {
    "agent.*": { "allow": false },
    "system.*": { "allow": false },
    "storage.*": { "allow": false },
    "aid.*": { "allow": false },
    "gateway.*": { "allow": false }
  }
}
```

危险操作包括但不限于：

```text
agent.getConfig
agent.create
agent.reload
agent.delete
system.restart
system.upgrade
storage.upload
storage.download
storage.delete
aid.listLocal
aid.showLocal
gateway.read
gateway.write
config.read
config.write
```

{

          "permissionMode": {

            "allowOverride": false

          },

        "commandPermissions": {
          // 模型权限
          "model.list": {
            "allow": true,
            "scopes": ["relation"],

## 6. 用户面能力上限

配置中的用户角色永远不能突破代码上限。

建议代码中维护：

```ts
USER_PLANE_CAPABILITY_CEILING = {
  allowOperations: [
    "model.list",
    "model.current",
    "model.use",
    "model.effort",
    "model.reset",
    "session.list",
    "session.create",
    "session.rename",
    "trigger.list",
    "stats.summary",
    "stats.session",
    "stats.context",
    "file.list",
    "file.fetch",
    "ec.msg.send",
    "ec.msg.file",
    "ec.group.send",
    "ec.group.file"
  ],
  denyOperations: [
    "role.assign",
    "role.revoke",
    "config.write",
    "gateway.write",
    "agent.*",
    "system.*",
    "storage.*",
    "aid.*",
    "cli.exec.raw",
    "shell.exec",
    "rce.exec",
    "dangerous:*"
  ],
  allowCategories: ["read", "write-own"],
  denyCategories: ["write-agent", "process", "dangerous"]
}
```

执行规则：

```text
最终用户权限 = 角色配置权限 ∩ USER_PLANE_CAPABILITY_CEILING
```

即使配置写了：

```jsonc
{
  "system.restart": { "allow": true },
  "dangerous:*": { "allow": true, "dangerous": true }
}
```

用户面最终也必须拒绝。

## 8. 落地校验规则

### 8.1 角色定义校验

- 角色名必须匹配 `[a-z0-9_-]+`。
- 禁止定义 `owner` / `admin`。
- `commandPermissions` 的 key 必须是：
  - operation id，如 `model.use`；
  - namespace wildcard，如 `model.*`；
  - category rule，如 `category:read`；
  - `dangerous:*`；
  - `*`。
- `scopes` 必须来自 `relation | role | agent | process | filesystem | control | raw-cli`。
- `constraints` 只能使用当前支持字段。

### 8.2 角色归属校验

- `roles.assigned` 不能是 `owner` / `admin`。
- `roles.members[*]` 不能是 `owner` / `admin`。
- 角色必须存在。
- AUN 场景下 `members` key 建议使用 AID。

### 8.3 配置写入校验

- `roles.definitions` 只能 owner/admin 修改。
- relation `roles.assigned` / `roles.members` 只能 owner/admin 修改。
- 普通用户不能通过 `config.write` 修改权限字段。
- agent 不能直接写 config 文件，只能走 ConfigManager/API。
