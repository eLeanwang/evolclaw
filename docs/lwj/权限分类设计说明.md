# EvolClaw 权限分类设计说明

> 本文档从设计角度说明 EvolClaw 权限体系应该如何分类。
> 分类原则不是按代码模块、CLI 命令或角色名称划分，而是按**受保护资源 / 能力域**划分。
> 配置路径表述遵循 `docs/config/01-overview.md`，统一使用 `{evolclaw_home}`。
>
> 目标角色口径：管理面为 `owner` / `admin`；用户面内置角色为 `member` / `visitor`（访客）。
> 没有角色、未知角色、非法角色不再降级到 `anonymous`，而是直接拒绝访问。

---

## 1. 总体分类原则

权限分类先回答一个问题：

> 这个权限到底在保护什么？

因此，EvolClaw 的权限不应该只写成一堆 `commandPermissions`，也不应该只围绕 `owner/admin/member/visitor` 角色来组织。

推荐按以下 12 个权限域分类：

| 编号 | 权限域 | 保护对象 |
|---|---|---|
| A | 身份与管理面权限 | 谁能管理 agent / daemon |
| B | 访问准入与角色归属权限 | 谁能进入 agent，会以什么用户角色进入 |
| C | 模型与推理资源权限 | 能用什么模型、推理强度、baseagent |
| D | 会话与对话行为权限 | 会话、话题、chatmode、dispatch、输出行为 |
| E | 文件与路径权限 | 能读写哪些文件、能操作哪些路径 |
| F | Bash / Shell 执行权限 | 能否执行本机命令、raw CLI、危险命令 |
| G | EC 通信命令权限 | 能否私聊/群聊/control 发消息或文件 |
| H | 配置读写权限 | 能否读取或修改 config.json 体系 |
| I | 角色与授权管理权限 | 能否定义、修改、分配、撤销角色 |
| J | 自动化与触发器权限 | 能否创建自动任务、定时任务、webhook |
| K | Agent / 系统 / 存储 / AID 权限 | 高危系统资源与身份密钥资源 |
| L | 审计与安全策略权限 | 审计日志、安全策略、审批缓存、回滚 |

这种分类方式的好处：

1. **用户能理解**：每类都对应一个真实受保护对象。
2. **配置能落地**：每类都能映射到 `permissions`、`commandPermissions`、ConfigManager 或 Hook。
3. **审计能归类**：日志可以按权限域检索。
4. **扩展稳定**：新增功能先判断属于哪个权限域，再补 operation、schema 和配置。
5. **安全边界清晰**：Bash、配置、角色管理不会混在普通业务命令里。

## 2. 配置体系位置

权限相关配置统一进入既有 config 体系，不新增独立 `roles.json` / `roles/` / `role-assignments.json` 作为目标设计。

```text
{evolclaw_home}/
├── evolclaw.json
└── agents/
    ├── defaults.json
    └── {aid}/
        ├── config.json
        └── relations/{peerKey}/
            └── config.json
```

核心归属：

| 信息 | 目标位置 |
|---|---|
| daemon 管理 owner | `{evolclaw_home}/evolclaw.json.owners` |
| agent owner/admin | `{evolclaw_home}/agents/{aid}/config.json.owners/admins` |
| 用户角色定义 | `{evolclaw_home}/agents/{aid}/config.json.roles.definitions` |
| 默认角色 | `{evolclaw_home}/agents/{aid}/config.json.roles.defaultRoles` |
| 私聊用户角色 | `{evolclaw_home}/agents/{aid}/relations/{privatePeerKey}/config.json.roles.assigned` |
| 群默认角色 | `{evolclaw_home}/agents/{aid}/relations/{groupPeerKey}/config.json.roles.assigned` |
| 群成员专属角色 | `{evolclaw_home}/agents/{aid}/relations/{groupPeerKey}/config.json.roles.members[memberAid]` |
| 关系级模型/行为覆盖 | relation 级 `config.json` 对应字段 |

`peerKey` 建议沿用配置体系约定：

```text
{channelType}#{urlEncode(channelId)}
```

示例：

```text
aun#alice.aid.pub
aun#grp-123
feishu#ou_xxx
```

## 3. 通用权限配置结构

一个用户角色通常由两部分组成：

```jsonc
{
  "permissions": {
    "permissionMode": {
      "default": "readonly",
      "allowOverride": false,
      "allowedValues": ["readonly"]
    }
  },
  "commandPermissions": {
    "model.list": {
      "allow": true,
      "scopes": ["relation"]
    }
  }
}
```

### 3.1 `permissions`

字段级权限，控制配置字段的默认值、是否允许覆盖、允许覆盖成什么。

适合控制：

- 模型：`baseagents.claude.model`
- 推理强度：`baseagents.claude.effort`
- 执行模式：`permissionMode`
- 对话模式：`chatmode.private/group/nothuman`
- 群分发策略：`dispatch`
- 活动显示：`show_activities`
- 输出延迟：`flush_delay`
- 防抖：`debounce`
- 富文本：`enable_rich_content`

### 3.2 `commandPermissions`

操作级权限，控制某个 operation 能不能执行、在哪个 scope 执行、带什么约束。

适合控制：

- `model.*`
- `file.*`
- `ec.msg.*`
- `session.*`
- `config.*`
- `role.*`
- `trigger.*`
- `agent.*`
- `system.*`
- `storage.*`
- `aid.*`

### 3.3 `constraints`

运行时约束，控制同一个 operation 的可用范围。

常见约束：

| 约束 | 含义 |
|---|---|
| `ownPeerOnly` | 只能操作当前对端 |
| `ownAgentOnly` | 只能操作当前 agent |
| `privateOnly` | 只能私聊使用 |
| `groupOnly` | 只能群聊使用 |
| `requireDaemonOwner` | 要求 daemon owner |
| `requireControlChannel` | 要求控制通道 |
| `requireFieldOverride` | 要求对应字段允许覆盖 |
| `allowedArgs` | 参数白名单 |
| `deniedArgs` | 参数黑名单 |
| `forbiddenFlags` | 禁止某些 flag |
| `allowedConfigKeys` | 只能改指定 config key |
| `allowedPrefixes` | 只能访问指定路径前缀 |

## 4. A. 身份与管理面权限

### 4.1 保护什么

保护“谁能管理系统”。

包括：

- daemon owner
- agent owner
- agent admin
- control / ECWeb 管理入口

### 4.2 配置在哪里

```jsonc
// {evolclaw_home}/agents/{aid}/config.json
{
  "owners": ["alice.aid.pub"],
  "admins": ["bob.aid.pub"]
}
```

daemon 级：

```jsonc
// {evolclaw_home}/evolclaw.json
{
  "owners": ["daemon-owner.aid.pub"]
}
```

### 4.3 如何保护

- 远程身份由 AUN 认证。
- EvolClaw 只信任 AUN 交付的已认证 AID。
- `owner/admin` 能力不放入 `roles.definitions`。
- relation 级配置不能声明 `owners/admins`。
- 修改 owner 名单只能由 owner 执行。
- 修改 admin 名单只能由 owner 执行。
- 管理能力边界由代码硬编码，不允许通过 config 放大。

### 4.4 设计要点

`owner/admin` 是管理权限面，不是用户角色。

不能这样设计：

```jsonc
{
  "roles": {
    "definitions": {
      "owner": {}
    }
  }
}
```

必须拒绝：

```text
roles.definitions.owner
roles.definitions.admin
roles.assigned = owner
roles.members[*] = admin
```

## 5. B. 访问准入与角色归属权限

### 5.1 保护什么

保护“谁能进入 agent，会以什么用户角色进入”。

内置用户角色：

| 角色 | 含义 |
|---|---|
| `member` | 可信成员 |
| `visitor` | 访客，低信任只读或最低风险访问 |

无角色：

```text
null / undefined / unknown role / invalid role => 直接拒绝访问
```

不再设置 `anonymous` 内置角色。

### 5.2 配置在哪里

agent 级默认角色：

```jsonc
// {evolclaw_home}/agents/{aid}/config.json
{
  "roles": {
    "defaultRoles": {
      "private": null,
      "group": "visitor"
    }
  }
}
```

私聊角色：

```jsonc
// {evolclaw_home}/agents/{aid}/relations/aun#alice.aid.pub/config.json
{
  "roles": {
    "assigned": "member"
  }
}
```

群默认和群成员专属角色：

```jsonc
// {evolclaw_home}/agents/{aid}/relations/aun#grp-123/config.json
{
  "roles": {
    "assigned": "visitor",
    "members": {
      "alice.aid.pub": "member",
      "bob.aid.pub": "reviewer"
    }
  }
}
```

### 5.3 私聊判断流程

```text
1. AUN 认证 actorAid
2. 若 actorAid ∈ owners → owner
3. 若 actorAid ∈ admins → admin
4. 读取 private relation config
5. 若 relation.roles.assigned 存在 → 使用该用户角色
6. 否则使用 agent.roles.defaultRoles.private
7. 若结果为 null / 不存在 / 非法 / owner / admin → 拒绝访问
```

优先级：

```text
owner/admin
> private relation roles.assigned
> defaultRoles.private
> 无角色拒绝
```

### 5.4 群聊判断流程

```text
1. AUN 认证 actorAid
2. 若 actorAid ∈ owners → owner
3. 若 actorAid ∈ admins → admin
4. 读取 group relation config
5. 若 group.roles.members[actorAid] 存在 → 使用群成员专属角色
6. 否则读取 private relation config
7. 若 private.roles.assigned 存在 → 继承私聊角色
8. 否则若 group.roles.assigned 存在 → 使用群默认角色
9. 否则使用 agent.roles.defaultRoles.group
10. 若结果为 null / 不存在 / 非法 / owner / admin → 拒绝访问
```

优先级：

```text
owner/admin
> group roles.members[actorAid]
> private roles.assigned
> group roles.assigned
> defaultRoles.group
> 无角色拒绝
```

## 6. C. 模型与推理资源权限

### 6.1 保护什么

保护模型能力、推理强度、成本和 baseagent 选择。

包含：

```text
active_baseagent
baseagents.*.model
baseagents.*.effort
model.list
model.current
model.info
model.check
model.use
model.effort
model.reset
```

### 6.2 配置模板

```jsonc
{
  "permissions": {
    "active_baseagent": {
      "default": "claude",
      "allowOverride": false,
      "allowedValues": ["claude"]
    },
    "baseagents.claude.model": {
      "default": "claude-haiku-4-5-20251001",
      "allowOverride": false,
      "allowedModels": ["claude-haiku-*"]
    },
    "baseagents.claude.effort": {
      "default": "low",
      "allowOverride": false,
      "allowedValues": ["low"]
    }
  },
  "commandPermissions": {
    "model.list": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true
      }
    },
    "model.current": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true
      }
    },
    "model.use": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true,
        "requireFieldOverride": "baseagents.claude.model"
      }
    },
    "model.effort": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "ownAgentOnly": true,
        "requireFieldOverride": "baseagents.claude.effort"
      }
    }
  }
}
```

### 6.3 设计要点

- 模型权限必须同时看字段权限和命令权限。
- `model.use` 允许不代表可以切到任意模型。
- `allowOverride: false` 时，即使 relation config 写了模型，也应被角色默认值覆盖。
- `allowedModels` 应支持通配符，例如 `claude-sonnet-*`。
- 高成本模型应只给 `member` 或管理面角色。

## 7. D. 会话与对话行为权限

### 7.1 保护什么

保护用户如何使用会话，以及 agent 如何回应。

包含：

```text
session.list
session.create
session.rename
session.delete
session.fork
session.compact
session.rewind
chatmode.private
chatmode.group
chatmode.nothuman
dispatch
show_activities
flush_delay
debounce
enable_rich_content
```

### 7.2 行为字段权限模板

```jsonc
{
  "permissions": {
    "chatmode.private": {
      "default": "interactive",
      "allowOverride": true,
      "allowedValues": ["interactive", "proactive"]
    },
    "chatmode.group": {
      "default": "proactive",
      "allowOverride": false,
      "allowedValues": ["proactive"]
    },
    "chatmode.nothuman": {
      "default": "proactive",
      "allowOverride": false,
      "allowedValues": ["proactive"]
    },
    "dispatch": {
      "default": "mention",
      "allowOverride": false,
      "allowedValues": ["mention"]
    },
    "show_activities": {
      "default": "none",
      "allowOverride": false,
      "allowedValues": ["none"]
    },
    "flush_delay": {
      "default": 5,
      "allowOverride": false,
      "allowedValues": [5]
    },
    "debounce": {
      "default": 0,
      "allowOverride": false,
      "allowedValues": [0]
    },
    "enable_rich_content": {
      "default": false,
      "allowOverride": false,
      "allowedValues": [false]
    }
  }
}
```

### 7.3 会话命令权限模板

```jsonc
{
  "commandPermissions": {
    "session.list": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true
      }
    },
    "session.create": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true
      }
    },
    "session.rename": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true
      }
    },
    "session.delete": {
      "allow": false
    }
  }
}
```

### 7.4 设计要点

- `chatmode` 必须拆成 private/group/nothuman 或定义清楚对象结构。
- 每个行为字段都要有 `default`、`allowOverride`、`allowedValues`。
- 群聊行为应比私聊更保守。
- `session.delete`、`rewind`、`compact` 等影响历史或状态的操作应谨慎开放。

## 8. E. 文件与路径权限

### 8.1 保护什么

保护本地文件系统。

需要拆成三类：

1. 文件读取权限。
2. 文件写入权限。
3. 可操作路径范围。

### 8.2 文件读取权限模板

```jsonc
{
  "commandPermissions": {
    "file.list": {
      "allow": true,
      "scopes": ["filesystem"],
      "constraints": {
        "allowedPrefixes": [
          "{projectPath}/docs/",
          "{projectPath}/README.md"
        ]
      }
    },
    "file.fetch": {
      "allow": true,
      "scopes": ["filesystem"],
      "constraints": {
        "allowedPrefixes": [
          "{projectPath}/docs/",
          "{projectPath}/README.md"
        ]
      }
    }
  }
}
```

### 8.3 文件写入权限

文件写入不应该只靠 `commandPermissions`。

需要同时依赖：

- `permissionMode`
- Hook 的 readonly 检查
- H 类文件保护
- `allowedPrefixes`
- dangerous command 检测
- ConfigManager 禁止直接写 config

低权限角色建议：

```text
visitor: 禁止写项目文件，只允许读取非常有限路径
reviewer: 禁止写项目文件
member: 可按需写项目工作区，但仍禁止 H 类文件
```

### 8.4 H 类文件

以下文件/目录不应允许 agent 直接写：

```text
{evolclaw_home}/evolclaw.json
{evolclaw_home}/agents/defaults.json
{evolclaw_home}/agents/{aid}/config.json
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json
{evolclaw_home}/.env
{evolclaw_home}/backups/config/
证书、密钥、AID keystore、快照目录
```

这些只能通过受控 API / ConfigManager 修改。

## 9. F. Bash / Shell 执行权限

### 9.1 保护什么

保护本机命令执行能力。

包含：

```text
cli.exec.raw
shell.exec
rce.exec
permissionMode
dangerous command approval
readonly bash block
```

### 9.2 配置模板

低权限角色：

```jsonc
{
  "commandPermissions": {
    "cli.exec.raw": {
      "allow": false,
      "dangerous": true
    },
    "shell.exec": {
      "allow": false,
      "dangerous": true
    },
    "rce.exec": {
      "allow": false,
      "dangerous": true
    },
    "dangerous:*": {
      "allow": false,
      "dangerous": true
    }
  }
}
```

高权限也应显式授权危险操作：

```jsonc
{
  "commandPermissions": {
    "dangerous:*": {
      "allow": true,
      "dangerous": true,
      "constraints": {
        "requireDaemonOwner": true
      }
    }
  }
}
```

### 9.3 设计要点

- Bash 是最高风险域，应单独分类。
- `*` 不应隐式授予危险命令。
- 危险操作必须显式 `dangerous: true`。
- `visitor` 不应拥有 raw bash。
- `member` 即使可写项目文件，也不等于可执行任意 shell。
- `ec role assign` 这类管理命令即使以 Bash 形式出现，也应进入委托管理命令流程，而不是普通 raw bash。

## 10. G. EC 通信命令权限

### 10.1 保护什么

保护 agent 对外发送消息/文件的能力。

包含：

```text
ec.msg.send
ec.msg.file
ec.group.send
ec.group.file
ec.ctl.send
ec.ctl.file
```

### 10.2 配置模板

```jsonc
{
  "commandPermissions": {
    "ec.msg.send": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "ownPeerOnly": true,
        "privateOnly": true
      }
    },
    "ec.msg.file": {
      "allow": false
    },
    "ec.group.send": {
      "allow": true,
      "scopes": ["relation"],
      "constraints": {
        "groupOnly": true
      }
    },
    "ec.group.file": {
      "allow": false
    },
    "ec.ctl.*": {
      "allow": false
    }
  }
}
```

### 10.3 设计要点

- 私聊发送要绑定 `ownPeerOnly`。
- 群聊发送要绑定 `groupOnly`。
- 文件发送比文本发送风险更高，应单独控制。
- control 通道不等于普通聊天通道。
- agent 会话内通过 Bash 调用 EC 命令时，应先解析成 `ec.*` operation，再做角色鉴权。

## 11. H. 配置读写权限

### 11.1 保护什么

保护整个 config.json 体系。

包含：

```text
config.read
config.write
allowedConfigKeys
ConfigManager
schema validation
config audit
snapshot / restore
```

### 11.2 配置模板

```jsonc
{
  "commandPermissions": {
    "config.read": {
      "allow": true,
      "scopes": ["relation", "agent"],
      "constraints": {
        "allowedConfigKeys": [
          "baseagents.claude.model",
          "baseagents.claude.effort",
          "permissionMode",
          "chatmode.private",
          "chatmode.group"
        ]
      }
    },
    "config.write": {
      "allow": false
    }
  }
}
```

管理面可配置：

```jsonc
{
  "commandPermissions": {
    "config.write": {
      "allow": true,
      "scopes": ["agent", "relation"],
      "constraints": {
        "allowedConfigKeys": [
          "roles.defaultRoles",
          "roles.definitions",
          "roles.assigned",
          "roles.members",
          "baseagents.*",
          "chatmode.*"
        ]
      }
    }
  }
}
```

### 11.3 设计要点

- 配置权限不是普通文件写权限。
- 允许写文件不代表允许写 config。
- config 写入必须走 ConfigManager。
- 所有 config 写入必须 schema 校验。
- 权限相关字段必须额外审计。

## 12. I. 角色与授权管理权限

### 12.1 保护什么

保护权限体系自身。

包含：

```text
role.define
role.update
role.delete
role.assign
role.revoke
role.default
```

这是“改权限的权限”，必须单独分类。

### 12.2 配置位置

角色定义：

```text
{evolclaw_home}/agents/{aid}/config.json.roles.definitions
```

角色分配：

```text
{evolclaw_home}/agents/{aid}/relations/{peerKey}/config.json.roles.assigned
{evolclaw_home}/agents/{aid}/relations/{groupPeerKey}/config.json.roles.members
```

### 12.3 管理操作模板

```jsonc
{
  "commandPermissions": {
    "role.assign": {
      "allow": false
    },
    "role.revoke": {
      "allow": false
    },
    "role.define": {
      "allow": false
    },
    "role.update": {
      "allow": false
    },
    "role.delete": {
      "allow": false
    }
  }
}
```

管理面能力应由代码决定，普通用户角色默认禁止。

### 12.4 必须守住的规则

1. 用户角色不能定义 `owner/admin`。
2. 用户角色不能分配 `owner/admin`。
3. `member/visitor` 不能修改角色定义。
4. `admin` 可以管理用户角色，但不能修改 owner 名单。
5. `owner` 才能修改 owner/admin 管理身份。
6. 所有角色变更必须审计。
7. 角色不存在、非法或配置损坏时直接拒绝。

### 12.5 Bash 委托管理命令

如果允许 owner 通过消息驱动 agent 执行：

```bash
ec role assign --self bot.aid.pub --peer aun#alice.aid.pub --role member
```

不能把它当普通 Bash。

应进入以下二选一流程：

1. Hook 短路执行：Hook 识别后直接走 `agent-delegated -> authorizeCommand -> handler`。
2. Hook 签发一次性委托凭证：CLI 携 token 调 daemon / ActionGateway 二次鉴权。

详细见：

```text
docs/lwj/Bash委托管理命令权限方案对比.md
```

```jsonc
    },

      "allow": false
    }

```

### 13.3 设计要点

- 触发器会绕过即时用户交互，风险高于普通命令。
- 创建/修改/启用触发器应要求 owner/admin。
- 若允许 member 创建触发器，必须绑定 owner peer、scope、频率、最大执行次数。
- 触发器执行时也必须带原始创建者和授权上下文。
- 自动化操作必须完整审计。

### 14.2 配置模板

普通用户角色默认：

```jsonc
{
  "commandPermissions": {
    "agent.*": { "allow": false },
    "system.*": { "allow": false },
    "storage.*": { "allow": false },
    "aid.*": { "allow": false },
    "gateway.*": { "allow": false }
```

### 14.3 设计要点

- `aid.import/export` 涉及身份材料，必须进入管理面。
- `gateway.write` 可能影响外部可访问面，应管理面控制。
- 这类操作应默认对用户角色关闭。

```jsonc
      "allow": false
```

- 安全策略修改应只允许 owner/admin。

## 16. 角色建议基线

### 16.1 `visitor`

定位：低信任访客。

建议能力：

- 只读。
- 可查询有限模型信息。
- 可查询有限会话信息。
- 可选允许私聊文本回复。
- 禁止文件发送。
- 禁止 Bash/raw CLI。
- 禁止配置写入。
- 禁止角色管理。
- 禁止触发器写操作。
- 禁止系统/存储/AID/gateway 管理操作。

### 16.2 `member`

定位：可信协作者。

建议能力：

- 可用中等模型。
- 可在自身范围内操作会话。
- 可在自身范围内发送私聊/群聊消息。
- 可按路径白名单读取文件。
- 可按需写入非 H 类项目文件。
- 默认不开放 raw Bash；如开放必须带约束和审计。
- 禁止角色管理。
- 禁止 owner/admin 管理操作。
- 禁止系统级危险操作。

### 16.3 自定义角色

示例：

- `reviewer`：只读审阅者。
- `developer`：项目协作者，可读写指定路径。
- `operator`：运维辅助，只能执行低风险诊断命令。

自定义角色必须满足：

```text
最终能力 = 角色声明能力 ∩ 用户面能力上限
```

## 17. 新增权限时的设计流程

新增一个功能时，不要先问“哪个角色能用”，而是按以下顺序：

1. 这个功能保护的资源属于哪个权限域？
2. 是否需要新增 operation？
3. operation 的 scope 是什么？
4. operation 是否 dangerous？
5. 允许哪些 source 调用？
6. 需要哪些 constraints？
7. 是否还需要字段级 `permissions` 配合？
8. 配置写入位置在哪里？
9. 是否需要 ConfigManager/schema 支持？
10. 是否需要审计？
11. `visitor` 应该怎么拒绝？
12. `member` 是否允许，允许到什么范围？
13. owner/admin 是否由代码管理面处理？

示例：新增预算功能 `budget.set`

```text
权限域：模型与资源成本 / 安全策略
operation：budget.set
scope：relation / agent
dangerous：false 或 true，取决于是否影响成本上限
source：slash / menu / ecweb / control
constraints：ownPeerOnly, allowedArgs, requireFieldOverride
字段权限：budget.daily_limit
审计：需要
visitor：拒绝
member：只允许自身范围和有限额度
owner/admin：管理面可配置
```

## 18. 最小落地清单

要让上述分类真正落地，需要至少完成：

1. Operation Registry 给所有操作标注权限域。
2. `roles.definitions` schema 支持 `member` / `visitor` / 自定义角色。
3. `roles.defaultRoles.private/group` 支持 `string | null`。
4. 角色解析支持“无角色拒绝”。
5. `owner/admin` 禁止出现在用户角色定义和分配中。
6. ConfigManager 对权限相关字段做写入守卫。
7. Hook 禁止 agent 直写 config 文件。
8. Bash 管理命令进入委托执行流程。
9. 审计日志记录权限域、operation、actor、target、结果。
10. 测试按权限域覆盖：允许、拒绝、越权、非法配置、未知角色。

## 19. 总结

推荐最终分类：

```text
A. 身份与管理面
B. 访问准入与角色归属
C. 模型与推理资源
D. 会话与对话行为
E. 文件与路径
F. Bash / Shell 执行
G. EC 通信命令
H. 配置读写
I. 角色与授权管理
J. 自动化与触发器
K. Agent / 系统 / 存储 / AID
L. 审计与安全策略
```

这套分类应该成为后续权限模板、配置 schema、文档、审计日志和测试用例的统一组织方式。

一句话原则：

> 先按受保护资源分类，再映射到角色、字段权限、命令权限、运行时约束和审计。
