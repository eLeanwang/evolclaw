# EvolClaw 演进路线图（讨论稿）

> **状态**：需求讨论稿，**当前不进入开发**。
> EvolClaw 正在大规模重构多 Agent 系统，本文档先把方向和细节对齐清楚，等重构落地后再分主题逐项推进。
>
> **时间**：2026-05-14

---

## 摘要

EvolClaw 后续要做的功能可以归成两组共 10 个主题：

**核心主题（4 项，相互依赖，要一起设计）**

1. 多 Agent 体系
2. 用户分类
3. 消息分类
4. 用户权限体系

**通用机制 + 长期方向（6 项）**

5. Trigger（独立通用触发器）
6. 对话 track（统计/记录）
7. 会话归档到 Memory
8. 归档文件 + 索引
9. 自动滚动（按条数/长度自动开新会话）
10. `/new` 命令（开新会话时自动归档老会话）

下面分别展开。

---

## 1. 多 Agent 体系

### 1.1 目标

同一台机器上要能**同时启动/创建多个 Agent 实例**，每个 Agent 独立运行、独立配置。

### 1.2 现状问题

当前所有配置都集中在 `~/.evolclaw/data/evolclaw.json` 一个文件里，且配置是**按 channel 维度**组织的（`channels.feishu / channels.wechat / channels.aun ...`），结构上无法承载"多 Agent"概念。

### 1.3 目标方案

**一个 Agent 一个配置文件**，统一放在：

```
~/.evolclaw/agents/<agent-name>.json
```

每个文件描述一个完整的 Agent 实例（AID、绑定的 channel、AI 后端、owner、权限策略等）。

### 1.4 待对齐的细节

- 文件命名规则：`<aid>.json` / `<agent-name>.json` / 还是别的标识
- 旧 `evolclaw.json` 的处理：保留为全局默认配置 / 一次性迁移 / 兼容期共存
- 多实例并发模型：同进程多实例 vs 多进程；`sessions.db` 怎么隔离（每 Agent 一个 db / 共享 db 加 agent_id 字段）
- 启动入口：`evolclaw start --agent <name>` / `evolclaw run <name>` / 默认全启动
- Agent 之间的关系：完全独立 / 可共享某些资源（比如 AUN keystore、Memory 索引）

## 2. 用户分类

### 2.1 目标

给"对端"打分类标签，作为权限、存储路径、行为差异的统一依据。

### 2.2 内置分类

- `owner` —— 主人
- `AID agent` —— 其他 AI agent（对端是 AI 而不是人类）
- `AID` —— 普通 AID 用户（一般是人类）
- `guest` —— 访客
- `VIP` —— VIP 用户

### 2.3 自定义

用户可以新增自己的分组。每个分类承载三类属性：

- **权限**（喂给 #4 用户权限体系）
- **存储路径**（不同分类的会话/数据存在不同目录）
- **其他属性**（待补充）

### 2.4 与现有 channel role 的关系

当前 evolclaw 在 channel 层已经有 `owner / admin / guest / anonymous` 四种 role（见 `aun.ts` 注入的 `对端身份: owner` 等 token）。新的"用户分类"是把这套语义**升级、扩充、可定制化**——分类不再只来自 channel 层判断，而是一套独立的、用户可配置的标签体系。

### 2.5 待对齐的细节

- 分类是**全局**还是**每 Agent 独立**（不同 Agent 可以对同一个对端打不同标签）
- 一个对端能否属于多个分类（多标签 vs 单分类）
- 自定义分类的配置位置（是和 Agent 配置文件放一起，还是独立文件）

## 3. 消息分类

### 3.1 目标

在 **AUN payload 协议层**新增一个分类字段，让前端可以按分类做**差异化渲染**。

### 3.2 基础分类

| 分类 | 说明 | 渲染示例 |
|---|---|---|
| 用户回复 | Agent 给用户的正式回复内容 | 普通气泡 |
| 思考 | Agent 的 thought/reasoning 过程 | 折叠灰色块 |
| 事件 | 结构化事件（JSON 格式文本） | 按字段渲染卡片/进度条 |
| 状态 | 任务状态（开始/完成/中断/错误等） | 状态徽章 |
| 文件 | 文件类消息 | 附件卡片 |
| 其他 | 兜底 | 默认渲染 |

### 3.3 待对齐的细节

- **字段命名**：复用现有 `payload.type`（已有 `text/quote/image/...`），还是新增独立字段如 `payload.kind` / `payload.category`
- **维度关系**：现有 `type` 是"内容形态"维度（text/image/file），新分类是"语义角色"维度（回复/思考/事件）——这是两个**正交**维度，应分两个字段
- **协议侧改动**：是否需要 AUN SDK / 网关侧配合升级，还是 evolclaw 在 `payload` 里加扩展字段就够（前端自行识别）
- **向后兼容**：老前端不认识新字段时的兜底行为
- 分类清单是固定的还是可扩展的（用户/Agent 自定义新分类）

## 4. 用户权限体系

### 4.1 目标

基于 #2 用户分类决定"谁能干什么"。是分类的**消费方**。

### 4.2 现状

`aun.ts` 中已有粗粒度策略：

```ts
canSwitchProject:    role === 'owner' || role === 'admin'
canListProjects:     role === 'owner' || role === 'admin'
canCreateSession:    任何人
canDeleteSession:    任何人
canImportCliSession: role === 'owner' || role === 'admin'
```

### 4.3 目标方案

把权限矩阵从硬编码迁出来，挂在用户分类上——每个分类声明一组权限。新的分类天然带新的权限组。

### 4.4 待对齐的细节

- 权限粒度：保持目前命令级（canX/canY），还是细化到具体行为
- 权限的存储位置：内嵌在分类定义里 / 独立的 RBAC 文件
- 默认权限（未分类对端的兜底）

---

## 5. Trigger

### 5.1 定位

**独立的通用触发器机制**——不绑死任何具体业务，提供"满足条件就执行动作"的基础能力。

### 5.2 用途示例

- 会话消息超过 N 条 → 触发归档（→ #9 自动滚动）
- 收到特定关键字 → 触发动作
- 定时触发
- 状态变化触发

### 5.3 与归档体系的关系

#9（自动滚动）和 #10（`/new` 命令）会**消费** trigger，但 trigger 本身是通用基础设施，独立设计、独立交付。

### 5.4 待对齐的细节

- 触发条件的描述方式：DSL / JS 脚本 / 内置类型
- 动作的描述方式
- 配置位置（每 Agent 一份 / 全局）

## 6. 对话 Track（统计/记录）

### 6.1 目标

记录和用户对话的统计数据：消息数、字数、活跃度、按时间维度聚合等。

### 6.2 用途

- 给用户看的活动概览
- 喂给 #9 自动滚动的判定条件（"消息条数/总长度超阈值"）
- 后续做用户洞察、行为分析

---

## 7. 会话归档到 Memory

### 7.1 目标

把完成的会话内容沉淀成持久 Memory，让 Agent 跨会话保留记忆。

### 7.2 与 Claude Memory 的关系

类似 Claude Code 的 `~/.claude/memory` 体系——按主题切片、可检索、能在新会话中被加载回上下文。

---

## 8. 归档文件 + 索引

### 8.1 目标

- 每次归档落**一个独立文件**
- 同步建**索引**，让后续会话能快速检索"我之前和这个用户聊过什么"

### 8.2 与 #7 的关系

#7 是"为什么归档（持续记忆）"，#8 是"怎么归档（文件 + 索引）"。两者共同构成归档体系的存储层。

---

## 9. 自动滚动

### 9.1 目标

会话超过阈值（消息条数 或 总长度）时，自动**归档当前会话 + 开新会话**。

### 9.2 实现路径

- 条件判定 ← 来自 #6 track
- 触发机制 ← 来自 #5 trigger
- 执行动作：归档（#7 + #8）+ 创建新会话（#10）

是几个机制的组合应用。

---

## 10. `/new` 命令（手动开新会话）

### 10.1 目标

用户主动开新会话时：

1. 自动**归档**老会话（#7 + #8）
2. 创建新会话
3. 新会话能**带上沉淀的记忆**继续对话

### 10.2 体验目标

每次开新会话都不是"从零开始"，而是"带着已沉淀记忆的延续"。长期持续记忆能力的关键入口。

## 优先级与节奏建议

> 仅供讨论，按目前各主题的依赖关系给出。

**第一阶段（重构期同步设计）**

- #1 多 Agent 体系（结构基础，最先动）
- #2 用户分类、#3 消息分类、#4 用户权限体系（与 #1 同期，避免后续大改）

**第二阶段（基础能力补齐）**

- #5 Trigger
- #6 Track
- #7 + #8 归档体系

**第三阶段（用户可见特性）**

- #9 自动滚动
- #10 `/new` 命令
