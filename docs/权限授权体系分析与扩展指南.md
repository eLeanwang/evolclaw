> 文档类型：架构分析 + 实施指南
> 生成日期：2026-07-02
> 适用范围：`src/config/roles*`、`src/core/command/*`、`src/core/permission.ts`

---

## 第一部分：现状分析

### 一、体系架构概览

EvolClaw 实现了一个**多层次、细粒度**的权限授权体系，融合 RBAC（基于角色的访问控制）与 ABAC（基于属性的访问控制），主要包含以下维度：

**1. 角色分层（5级）**

| 角色 | 说明 | 默认权限模式 |
|---|---|---|
| `owner` | Agent 拥有者，关系/agent 级最高权限；进程级仍受 `evolclaw.json.owners` 约束 | `bypass` |
| `admin` | 管理员，可执行部分管理操作；危险操作仍需额外约束 | `request` |
| `member` | 团队成员，own-scope 访问 | `auto` |
| `guest` | 访客，私聊 own-scope 只读 | `readonly` |
| `anonymous` | 匿名用户，禁止访问 | `readonly`（且 `allowAccess=false`） |

**2. 权限控制层**

- 角色访问控制（`allowAccess`）— 是否允许该角色接触 agent
- 字段权限控制（`FieldPermission`）— 配置字段的默认值/可覆盖性/白名单
- 命令权限控制（`CommandPermission`）— 操作级别的允许/拒绝 + 作用域 + 约束
- 工具使用控制（`PermissionGateway`）— Bash/Write/Edit 等工具调用的人工审批
- H 类文件保护 — 配置/证书/快照文件禁止 agent 通过受保护写入路径直接修改
- 危险命令检测 — `rm -rf`、`sudo`、`chmod 777` 等模式匹配拦截

**3. 权限模式（PermissionMode）**

`bypass`（完全绕过）/ `request`（需审批）/ `auto`（自动判断）/ `readonly`（只读）/ `edit` / `plan` / `noask`

**4. 命令执行权限模型（Operation-based）**

这是 v4 版本引入的统一模型，核心思想：

> `owner/admin/member/guest/custom role` 只是默认策略名，不是代码硬边界；真正的权限边界应该是 **operation、scope、constraints、dangerous metadata 和可审计授权决策**。

链路：`命令入口 → CommandIntent（归一化） → Operation Registry（元数据） → authorizeCommand()（鉴权） → 约束检查 → 执行/拒绝`

**当前落地口径**：`authorizeCommand()` 已经是模型、menu、CLI 透传、部分 control/process 操作的统一授权核心；但 slash/menu 仍保留若干历史的 `isAdmin`/`isOwner`/`policy.can*` 内联判断。本文后续将这类路径标记为“待迁移”，避免把目标态误读为全量现状。

### 二、完善程度评估

#### ✅ 已实现且完善的部分

**1. 角色定义与解析（90分）**
- 5 级角色层次清晰，职责明确
- 支持私聊/群聊差异化默认角色（`defaultRoles.private/group`）
- 多来源角色解析优先级：`assignment → private-inherited → group-default → default`
- AID 认证机制（`isAuthenticated`）
- 角色缓存机制（`roles-cache.ts`）

**2. 字段权限约束（85分）**

每个字段支持：
```typescript
{
  default: any;              // 默认值
  allowOverride: boolean;    // 是否允许覆盖
  allowedModels?: string[];  // 模型白名单（支持通配符 claude-sonnet-*）
  allowedValues?: any[];     // 值白名单
}
```
- 支持嵌套路径（如 `baseagents.claude.model`）
- 通配符模式匹配
- 违规检测与自动降级到默认值
- 多重约束合并（`mergeWithRoleConstraints`）

**3. 命令权限系统（82分）**

```typescript
commandPermissions: {
  '*': { allow: true },
  'dangerous:*': { allow: true, dangerous: true, constraints: { requireDaemonOwner: true } },
  'category:read': { allow: true },
  'model.use': {
    allow: true,
    scopes: ['relation'],
    constraints: { ownPeerOnly: true, privateOnly: true, requireFieldOverride: 'baseagents.claude.model' }
  }
}
```
- 规则匹配优先级：精确匹配 > 命名空间(`ns.*`) > 类别(`category:x`) > 危险通配符(`dangerous:*`) > 全局通配符(`*`)
- 作用域控制（relation/role/agent/control/process/raw-cli...）
- 多维度约束：`ownPeerOnly`、`ownAgentOnly`、`privateOnly`、`groupOnly`、`requireDaemonOwner`、`requireControlChannel`、`forbiddenFlags`、`allowedArgs`/`deniedArgs`、`requireFieldOverride`
- 危险操作要求显式授权（`isExplicitDangerousGrant`），无法通过 `*` 通配符隐式获得
- 仍存在迁移缺口：`slash-handler.ts`、`menu-handler.ts` 中部分命令还直接判断 `isAdmin`/`isOwner`，尚未完全归一到 operation 授权模型
- 注意危险操作匹配细节：如果某个 namespace 下同时存在普通操作和危险操作，不应只配置 `namespace.*`；危险操作需要精确规则或 `dangerous:*`，否则高优先级 namespace 通配符会先命中并被 `isExplicitDangerousGrant()` 拒绝

**4. 工具安全防护（78分）**
- 绝对禁止命令：`shutdown`、`reboot`、`mkfs`、`format C:`、`dd of=/dev/*`
- 危险命令检测（需人工审批）：`rm -rf`、`sudo`、`chmod 777`、设备重定向、Windows `rd /s`/`del /s`、`reg delete`、`net stop`、`pkill`/`killall`
- 只读模式拦截：Write/Edit/NotebookEdit 仅允许写入 `.evolclaw/tmp/`；Bash 拦截写入类命令（git commit/push、npm install、sed -i 等）
- H 类文件保护：`evolclaw.json`、`agents/*/config.json`、证书密钥、快照目录等禁止通过 `Write`/`Edit`/`NotebookEdit` 直写；当前 Claude runner 已接入，Codex/Gemini 等 runner 的等价保护需要单独核查与补齐
- 三态权限决策：`allow` / `always`（记忆放行）/ `deny`

**5. 测试覆盖（80分）**
- 根目录已有 10 个 `*role*.test.ts`、2 个 `*permission*.test.ts`，`src/core/command/__tests__` 另有 command permission 与 operation registry 测试
- 覆盖核心场景：约束合并、模型白名单、命令权限、peer-role 解析
- 建议后续用脚本生成测试统计，避免“文件数/行数”随代码演进漂移

#### ⚠️ 存在不足或风险的部分

**1. 字段约束中的未知角色 fallback（风险等级：已修复）**

```typescript
// src/config/role-constraints.ts:28-34
if (!roleDef) {
  console.warn(`[role-constraints] Unknown role: ${role}, fallback to anonymous`);
  const result = mergeWithRoleConstraints('anonymous', relationConfig);
  return result;
}
```

**当前实现**：字段/行为配置合并路径中，未定义角色已降级到 `anonymous`；`isModelAllowedForRole()` 对未知角色同样按 `anonymous` 的模型白名单判定，避免拼写错误或竞态导致意外获得 `member` 级字段覆盖能力。

**边界说明**：命令执行鉴权路径中，`authorizeCommand()` 对未知角色是直接拒绝；角色分配写入路径也会校验目标 role 是否存在。因此这个风险主要存在于 `mergeWithRoleConstraints()` / `isModelAllowedForRole()` 这类字段约束辅助函数，而不是所有权限入口。

**验证**：`tests/role-constraints.test.ts` 已覆盖 unknown role fallback 与模型白名单判定。

---

**2. 进程级 owners 仅 warn 而非 fail-fast（风险等级：中-高）**

`ROLE_ACCESS_CONTROL.md` 明确写到：v3.2 起，`/system`、`/agent` 生命周期管理的鉴权迁移到 `evolclaw.json` 顶层 `owners` 字段，**未配置则一律 FORBIDDEN**（daemon 启动时仅 warn 提示）。

**当前实现**：
- daemon 启动阶段会对空 `owners` 打 warn
- 如设置 `EVOLCLAW_REQUIRE_OWNERS=1|true|yes`，daemon 启动时遇到空 `owners` 会 fail-fast
- `isProcessLevelOwner(peerId, owners)` 对空数组返回 `false`
- ECWeb/control channel 的进程级入口也会在空 `owners` 时拒绝

**残余问题**：warn 仍可能被忽略。云端/远程管理部署应显式设置 `EVOLCLAW_REQUIRE_OWNERS=1`，否则空 `owners` 会导致进程级运维不可用但 daemon 仍可启动。

**建议**：在生产/云部署模板中默认启用 `EVOLCLAW_REQUIRE_OWNERS=1`；本地开发、首次初始化和恢复场景可保持默认 warn-only。

---

**3. 角色分配未纳入统一 operation 与审计（风险等级：已修复 ECWeb 写入口）**

底层 `setPrivateRoleAssignment()` / `setGroupRoleAssignment()` / `setGroupMemberRoleAssignment()` 仍只校验目标 role 是否存在，供初始化、绑定和内部迁移流程使用。外部写入口（ECWeb role assignment API）已通过 `role.assign` / `role.revoke` 纳入 `authorizeCommand()`，并接入 `auditCommandAuthorization()`。

当前策略矩阵：
- `owner` 可分配/撤销任意已存在角色（包括 `owner`、`admin`、`member`、`guest`、`anonymous` 和自定义角色）
- `admin` 只能分配/撤销 `member`、`guest`、`anonymous`
- `member`、`guest`、`anonymous` 不能分配/撤销角色

实现位置：
- `src/core/command/operation-registry.ts`：注册 `role.assign` / `role.revoke`
- `src/config/builtin-roles.ts`：内置角色显式授权/拒绝 role operations
- `ecweb/src/sources/role-assignments.ts`：ECWeb 写入口执行 operation 授权、目标角色矩阵和审计

**残余边界**：内部调用底层 helper 的流程仍必须由调用方保证上下文可信；如果后续新增非 ECWeb 外部写入口，应复用同一套 `role.assign` / `role.revoke` 授权。

---

**4. 命令约束声明与执行不完全一致（风险等级：中）**

`CommandPermissionConstraints` 类型和 roles schema 中声明了较多约束字段，其中已执行的主要包括：
- `ownPeerOnly` / `ownAgentOnly`
- `privateOnly` / `groupOnly`
- `requireDaemonOwner` / `requireControlChannel`
- `forbiddenFlags` / `allowedArgs` / `deniedArgs`
- `requireExplicitDangerousGrant`
- `allowedConfigKeys` / `allowedPrefixes`
- `requireFieldOverride`

但 `timeoutMs`、`outputLimitBytes`、`cwdPolicy`、`envAllowlist` 等字段目前更像预留/声明字段，未在 `checkConstraints()` 中真正执行。

**建议**：
- 文档和 UI 区分“已执行约束”和“预留约束”
- 对已执行约束补充“正向通过 + 反向绕过尝试”成对测试（`command-permission.test.ts` 已覆盖 `allowedConfigKeys` / `allowedPrefixes` / `requireExplicitDangerousGrant`）
- 对预留约束要么实现，要么在 schema/UI 标记为 reserved，避免误配置后产生安全错觉

---

**5. 群组策略层仍偏薄（风险等级：中）**

```typescript
defaultRoles: {
  private: 'anonymous',
  group: 'guest',  // 所有群成员默认 guest，粒度较粗
}
```

**已有能力**：当前已经支持 `group` 和 `group-member` 粒度的 role assignment，群聊解析顺序为 `group-member assignment → private-inherited → group assignment → group default`。

**缺失能力**：
- 独立于 role assignment 的群组策略层
- 基于群组的操作配额/限流
- 群组级别的功能开关（禁止某个群使用某些命令）

**建议**：增加群组级权限配置层，例如：

```typescript
groupPolicies: {
  [groupId]: {
    defaultRole: 'guest',
    allowedCommands: ['session.*', 'model.list'],
    maxDailyRequests: 100,
  }
}
```

---

**6. 权限审计日志不完整（风险等级：中）**

已有零散的拒绝日志（如 `[ReadonlyCheck]`、`[H-Class Protection]`），但缺少：
- 集中的审计事件总线（当前 `auditCommandAuthorization` 只记录 deny、dangerous allow 和 `cli.exec.raw`，普通 allow 默认不落盘）
- 角色分配/撤销的变更历史
- 异常行为检测（如短时间内高频权限拒绝的告警）

**建议**：统一到一个审计事件总线，所有权限判定（角色访问、字段约束、命令鉴权、工具审批）都发布标准化事件，便于集中检索与异常检测。

---

**7. 跨渠道权限一致性（风险等级：低-中）**

不同 Channel（Feishu/WeChat/DingTalk...）可能有各自的 `debounce`/`flushDelay` 等覆盖配置，需要明确声明"角色权限边界跨渠道不可被渠道级配置绕过"的设计原则，并在代码层面加以保证（避免渠道适配层引入隐式旁路）。

---

**8. 权限模式切换的安全性（风险等级：中）**

```typescript
// src/core/permission.ts
clearAlwaysAllow(): void {
  this.alwaysAllow.clear();
}
```

切换权限模式（如 `bypass → readonly`）时会清空"始终允许"缓存，这是好的；但运行中的 runner 调用通常已经捕获了本次 `permissionMode`，不会自动重新评估：
- 新权限模式主要影响后续消息/后续任务
- 运行中任务是否需要中断，应由产品策略明确

**建议**：如果权限模式切换被定义为强安全边界，则切换时应主动中断当前会话内运行中的任务，并要求用户重新提交或重新走鉴权流程；否则文档应明确“仅对后续任务生效”。

### 三、安全边界检查

**✅ 已防护的攻击面**

| 攻击面 | 防护措施 |
|---|---|
| 命令注入 | 绝对禁止命令 + 危险命令检测 + Shell 控制字符过滤（`SHELL_CONTROL_RE`） |
| 文件系统破坏 | Claude 写文件路径的 H 类文件保护 + 只读模式拦截；其他 runner 需补 parity 检查 |
| 权限提升 | 角色约束（`allowOverride`）+ 命令权限白名单 |
| 模型/成本滥用 | 模型白名单（guest 仅 haiku，member 仅 sonnet/haiku，admin+ 可用 opus） |

**⚠️ 潜在漏洞**

1. **TOCTOU（检查到使用的时间窗口）**：角色检查与实际执行之间存在窗口期，若用户在此期间被降级，理论上仍可能沿用旧的鉴权结果。
2. **配置文件竞争**：多进程/多协程同时修改 `roles.json` 时缺少显式加锁描述。
3. **runner 防护不一致**：Claude/Codex/Gemini 对 H 类文件保护、危险命令审批、只读模式的接入深度不完全一致，需要单独测试。
4. **会话劫持**：ECWeb/token、AUN 控制通道等入口的 token/身份轮换策略需要在对应文档中明确。

## 第二部分：新增模块权限的设计与实施指南

### 一、系统权限控制流程

```
用户操作 → 命令解析 → Operation 映射 → 权限鉴权 → 约束检查 → 执行/拒绝
   ↓            ↓             ↓            ↓            ↓
 /budget      intent      budget.*    authorizeCommand  constraints
  list        解析         操作注册      角色匹配         参数验证
```

新增一个模块的权限控制，本质是把该模块的每个操作纳入这条统一链路，而不是在业务代码里写 `if (role === 'owner')` 之类的硬编码判断。

---

### 二、新增模块权限的 6 个步骤

以新增 **预算管理模块（Budget）**（查询/设置/重置）为例：

#### 步骤 1：确认类型边界（`src/types.ts`）

```typescript
// 当前已有操作类别
export type OperationCategory =
  | 'read'
  | 'diagnose'
  | 'write-own'
  | 'write-agent'
  | 'process'
  | 'dangerous';

// 当前已有作用域
export type CommandScope =
  | 'relation'
  | 'role'
  | 'agent'
  | 'process'
  | 'filesystem'
  | 'control'
  | 'raw-cli';

// 当前已有来源
export type CommandSource = 'slash' | 'menu' | 'menu.cli' | 'ctl' | 'ipc' | 'ecweb' | 'control';
```

新增模块优先复用现有 category/scope/source。只有当现有语义无法表达时，才新增类型；新增时必须同步更新：
- `src/types.ts`
- `kits/schemas/roles.schema.*.json`
- ECWeb 角色权限编辑器的校验枚举
- operation registry 与单元测试

#### 步骤 2：注册操作元数据（`src/core/command/operation-registry.ts`）

- `defaultScopes`：默认允许的作用域
- `sources`：允许触发该操作的入口

#### 步骤 4：实现命令处理器（`src/core/command/slash-handler.ts`）

```typescript
if (normalized.startsWith('/budget')) {
  const parts = normalized.split(/\s+/);
  const subcommand = parts[1] || 'list';

  let intent: CommandIntent;
  if (subcommand === 'list') {
    intent = { operation: 'budget.list', scope: 'relation', source: 'slash', args: {} };
  } else if (subcommand === 'current') {
    intent = { operation: 'budget.current', scope: 'relation', source: 'slash', args: {} };
  } else if (subcommand === 'set') {
    const limit = parseInt(parts[2], 10);
    intent = { operation: 'budget.set', scope: 'relation', source: 'slash', args: { limit } };
  } else if (subcommand === 'reset') {
    intent = { operation: 'budget.reset', scope: 'agent', source: 'slash', args: {}, dangerous: true };
  } else {
    return { kind: 'command.error', text: `❌ 未知子命令: ${subcommand}` };
  }

  // 统一鉴权入口
  const authError = await authorizeSlashIntent({
    intent, identity: session.identity, session, channel, channelId, userId, selfAid, isDaemonOwner,
  });
  if (authError) return authError;

  // 鉴权通过后才执行业务逻辑
  switch (subcommand) {
    case 'list':    return { kind: 'command.result', text: await executeBudgetList(session, identity.role) };
    case 'current': return { kind: 'command.result', text: await executeBudgetCurrent(session) };
    case 'set':     return { kind: 'command.result', text: await executeBudgetSet(session, intent.args.limit as number, identity.role) };
    case 'reset':   return { kind: 'command.result', text: await executeBudgetReset(session) };
  }
}
```

业务函数内部仍需结合字段权限做二次校验（不要只依赖命令鉴权一层）：

```typescript
async function executeBudgetSet(session: Session, limit: number, role: string): Promise<string> {
  const fieldPerm = getFieldPermission(role, 'budget.daily_limit');
  if (!fieldPerm || !fieldPerm.allowOverride) {
    return '❌ 您的角色不允许修改预算限额';
  }
  if (fieldPerm.allowedValues && !fieldPerm.allowedValues.includes(limit)) {
    return `❌ 限额值必须是: ${fieldPerm.allowedValues.join(', ')}`;
  }
  await writeRelationConfig(session, 'budget.daily_limit', limit);
  return `✅ 预算限额已设置为 ${limit} tokens`;
}
```

#### 步骤 5：按需扩展约束检查（`src/core/command/command-permission.ts`）

优先复用现有约束，例如 `requireFieldOverride`、`allowedArgs`、`deniedArgs`、`forbiddenFlags`。如果确实需要新增模块专属约束，不能只改 `checkConstraints()`，还必须同步更新 `CommandPermissionConstraints` 类型、roles schema、ECWeb 校验枚举和测试。

```typescript
function checkConstraints(ctx: CommandAuthorizationContext, constraints: CommandPermissionConstraints): ConstraintCheckResult {
  // ... 已有约束 ...

  // 示例：新增 requireBudgetOverride 前，需要先把该字段加入类型/schema/UI 校验。
  if (constraints.requireBudgetOverride) {
    const budgetCheck = checkBudgetOverride(ctx);
    if (!budgetCheck.ok) return budgetCheck;
  }
  return { ok: true };
}

function checkBudgetOverride(ctx: CommandAuthorizationContext): ConstraintCheckResult {
  const limit = ctx.intent.args.limit;
  if (typeof limit !== 'number' || limit < 0) {
    return { ok: false, reason: 'Invalid budget limit value' };
  }
  const fieldPerm = getFieldPermission(ctx.role, 'budget.daily_limit');
  const maxAllowed = Math.max(...(fieldPerm?.allowedValues as number[] || [0]));
  if (limit > maxAllowed) {
    return { ok: false, reason: `Budget limit ${limit} exceeds role maximum ${maxAllowed}` };
  }
  return { ok: true };
}
```

### 三、权限控制的关键设计原则

**1. 职责分离**

```
Operation Registry   →  定义"有哪些操作"
Role Config          →  定义"谁能做什么"
Command Permission   →  执行"运行时鉴权"
Field Permission     →  约束"配置值范围"
```

**2. 白名单优先，默认拒绝**

```typescript
// ❌ 黑名单思路，容易遗漏
if (role !== 'guest') { allow(); }

// ✅ 白名单思路，未声明的操作默认拒绝
commandPermissions: {
  'budget.list': { allow: true },
  // 其余操作默认 deny
}
```

**3. 危险操作显式标记，不可通过通配符隐式获得**

```typescript
{ id: 'budget.reset', dangerous: true }

commandPermissions: {
  'budget.reset': {
    allow: true,
    dangerous: true,                              // 必须显式声明
    constraints: { requireDaemonOwner: true },     // 额外约束
  }
}
```

`isExplicitDangerousGrant()` 会校验：危险操作必须匹配一条**非通配符**或 `dangerous:*` 的显式规则，防止 `'*': { allow: true }` 意外放行危险操作。

**4. 约束层层收紧**

```
1. 命令权限：是否允许执行该 operation
2. 作用域限制：是否命中允许的 scope
3. 参数约束：ownPeerOnly / privateOnly / forbiddenFlags ...
4. 字段权限：allowedValues / allowedModels
5. 业务逻辑：模块内部的额外运行时检查（不要只信任鉴权层）
```

### 六、新增模块权限检查清单

- [ ] `types.ts`：如需新的 Category/Scope/Source，先补充类型定义
- [ ] schema/UI：如新增 Category/Scope/Source/Constraint，同步更新 `kits/schemas/roles.schema.*.json` 和 ECWeb 校验枚举
- [ ] `operation-registry.ts`：为模块的每个操作注册元数据（id/category/dangerous/defaultScopes/sources）
- [ ] `builtin-roles.ts`：为**全部**内置角色（owner/admin/member/guest/anonymous）配置该模块的 `permissions` 与 `commandPermissions`，不要遗漏 `anonymous` 的显式拒绝
- [ ] 危险操作匹配：namespace 通配符下若包含危险操作，必须为危险操作补充精确规则或 `dangerous:*`，避免被普通 `namespace.*` 抢先匹配后拒绝
- [ ] 命令处理器：新增入口统一走 `authorizeSlashIntent()` / `authorizeCommand()`；如沿用历史硬编码角色判断，必须标记为待迁移
- [ ] 业务逻辑层：对写操作做字段权限（`allowOverride`/`allowedValues`）二次校验，不要只信任上层鉴权
- [ ] 危险操作：显式标记 `dangerous: true`，并配置 `requireDaemonOwner`/`requireControlChannel` 等约束
- [ ] 自定义约束：如有模块特有的校验逻辑，在 `checkConstraints()` 中扩展
- [ ] 测试：至少覆盖"最高权限允许 + 最低权限拒绝 + 中间角色的约束边界"三类用例
- [ ] 审计：确认 deny、dangerous allow、raw CLI 等高价值事件会经过 `auditCommandAuthorization()`；普通 allow 如需落盘需扩展审计策略
- [ ] 文档：更新 README 的斜杠命令清单与本文档的模块列表（如适用）

---

### 七、总结

该机制的核心优势是**声明式、可审计、易扩展、类型安全**：新增模块应优先在 Operation Registry 和 Role Config 中声明操作与授权策略，并通过统一授权器执行运行时鉴权。业务代码仍需要保留必要的二次校验（字段范围、路径沙箱、业务归属等），但不应重复散落 `role === 'owner'` 这类权限边界判断。当前系统已具备统一模型基础，后续重点是把历史入口逐步迁移到同一套安全基线。
