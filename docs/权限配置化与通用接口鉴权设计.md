# 权限配置化与通用接口鉴权设计

> 文档类型：架构设计 / 实施方案  
> 版本：v1.0  
> 日期：2026-07-02  
> 适用范围：`src/core/command/*`、`src/config/roles*`、`ecweb/src/server.ts`、`ecweb/src/sources/*`

---

## 1. 背景

当前 EvolClaw 已经具备 operation-based 的命令授权模型：

- `src/core/command/operation-registry.ts` 定义 operation 元数据。
- `src/core/command/command-permission.ts` 通过 `authorizeCommand()` 执行统一授权。
- `kits/schemas/roles.schema.4.json` 与 `roles.json` 支持 `commandPermissions`。
- `src/config/builtin-roles.ts` 为内置角色提供默认命令权限策略。
- ECWeb 角色分配写入口已经接入 `role.assign` / `role.revoke`、目标角色矩阵和审计。

但系统仍有两个关键限制：

1. **新增 operation 仍需要改代码。**  
   `operation-registry.ts` 当前是硬编码数组。新增业务权限点必须修改代码、重新构建、重新发布。

2. **HTTP 接口鉴权没有统一抽象。**  
   ECWeb 目前在 `server.ts` 中重复做 token 校验；各业务 handler 自己决定是否调用 `authorizeCommand()`，例如 role assignment 已接入，但 `models`、`stats`、`role-definitions` 仍有各自的判断逻辑。

本设计的目标是把“新增权限点”和“接口鉴权接入”配置化、通用化，使新业务在已有业务逻辑的前提下，可以只通过配置新增权限控制。

---

## 2. 设计目标

### 2.1 核心目标

1. 支持通过配置新增 operation 元数据。
2. 支持通过配置把 HTTP route 映射到 operation。
3. ECWeb HTTP API 统一走 `authorizeCommand()`。
4. `roles.json` 继续作为角色授权真相源。
5. 所有未知 operation 默认拒绝。
6. 危险操作仍要求显式授权，不允许被普通 `*` 隐式放行。
7. 授权结果统一审计，至少覆盖 deny、dangerous allow、role operation。

### 2.2 非目标

1. 不把业务逻辑配置化。  
   配置只声明“谁能调用什么操作”，业务 handler 仍由代码实现。

2. 不允许配置执行任意脚本、表达式或动态 JS。  
   route 参数提取、scope、source、operation 映射必须是受限声明式配置。

3. 不用 route 权限替代业务约束。  
   例如角色分配里的“admin 只能分配 member/guest/anonymous”仍是业务策略，除非后续被抽象成通用 constraint。

4. 不一次性迁移全部历史入口。  
   V1 先支持新业务和部分低风险 ECWeb API，历史 slash/menu/CLI 迁移按后续阶段推进。

## 3. 当前代码事实

### 3.1 Operation Registry

现状：

```text
src/core/command/operation-registry.ts
  -> const OPERATIONS: OperationMeta[]
  -> operationMap
  -> getOperationMeta()
  -> listOperations()
```

问题：

- operation catalog 只能通过代码新增。
- ECWeb 角色权限编辑器读取的是后端 registry，因此自定义 operation 不进入 registry 就无法被 UI 配置。
- `authorizeCommand()` 对未知 operation fail-closed，这是正确的，但也意味着新增业务必须先注册 operation。

### 3.2 Command Permission

现状：

```text
authorizeCommand(ctx)
  -> getOperationMeta(operation)
  -> 检查 source
  -> getRoleDefinition(role)
  -> match commandPermissions
  -> dangerous 显式授权检查
  -> scope 检查
  -> constraints 检查
```

已经可复用：

- exact operation、namespace wildcard、category、dangerous wildcard、ordinary wildcard。
- `ownPeerOnly`、`ownAgentOnly`、`privateOnly`、`groupOnly`。
- `requireDaemonOwner`、`requireControlChannel`。
- `forbiddenFlags`、`allowedArgs`、`deniedArgs`。
- `allowedConfigKeys`、`allowedPrefixes`。
- `requireFieldOverride`。

### 3.3 Roles Config

现状：

```text
roles.json overlay
  -> resolveRoles()
  -> mergeRolesConfig()
  -> getRoleDefinition()
  -> authorizeCommand()
```

优点：

- `roles.json` 已经支持自定义 role。
- 内置角色变更可以作为 baseline，用户 overlay 只记录差异。
- `commandPermissions` 已经存在，不需要重新设计角色权限模型。

### 3.4 ECWeb HTTP API

现状：

```text
ecweb/src/server.ts
  -> /api/stats/*
  -> /api/models/*
  -> /api/roles/*
  -> /api/role-definitions*
  -> /api/assignments/peer/*
```

问题：

- token 校验逻辑在多个分支重复。
- handler 是否接入 `authorizeCommand()` 取决于各自实现。
- role assignment 已有统一授权，但 role definitions 仍是 `process owners` 直接判断。
- 新增 HTTP API 时容易再次散落鉴权逻辑。

## 4. 总体方案

V1 引入两个配置层：

1. **Operation Manifest**  
   负责声明系统有哪些 operation。

2. **HTTP Route Auth Manifest**  
   负责声明 ECWeb route 如何映射到 operation。

运行链路：

```text
HTTP Request
  -> token/authentication
  -> match route auth manifest
  -> build CommandAuthorizationContext
  -> authorizeCommand()
  -> auditCommandAuthorization()
  -> allow: call business handler
  -> deny: return 403
```

operation 来源：

```text
builtin operations
  + configured operations
  = runtime operation registry
```

权限来源：

```text
builtin roles
  + roles.json overlay
  = effective roles
  -> roles[role].commandPermissions
```

## 5. Operation Manifest 设计

### 5.1 配置文件

建议路径：

```text
$EVOLCLAW_HOME/operations.json
```

也可以后续扩展插件目录：

```text
$EVOLCLAW_HOME/operations.d/*.json
kits/operations/*.json
plugins/*/operations.json
```

V1 建议只支持单文件 `$EVOLCLAW_HOME/operations.json`，减少合并顺序和冲突复杂度。

### 5.2 配置示例

```json
{
  "$schema_version": 1,
  "operations": [
    {
      "id": "budget.current",
      "category": "read",
      "dangerous": false,
      "defaultScopes": ["relation"],
      "description": "查看当前预算使用情况",
      "sources": ["ecweb", "slash"]
    },
    {
      "id": "budget.set",
      "category": "write-own",
      "dangerous": false,
      "defaultScopes": ["relation"],
      "description": "设置当前关系的预算限制",
      "sources": ["ecweb"]
    },
    {
      "id": "budget.reset",
      "category": "write-agent",
      "dangerous": true,
      "defaultScopes": ["agent"],
      "description": "重置 agent 级预算统计",
      "sources": ["ecweb", "control"]
    }
  ]
}
```

### 5.3 Schema 草案

新增：

```text
kits/schemas/operation-manifest.schema.1.json
```

逻辑结构：

```ts
interface OperationManifest {
  $schema_version: 1;
  operations: OperationMeta[];
}
```

校验要求：

| 字段 | 要求 |
|---|---|
| `id` | 必须匹配 `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)+$` |
| `category` | 必须是现有 `OperationCategory` |
| `dangerous` | 必须是 boolean |
| `defaultScopes` | 非空数组，元素必须是现有 `CommandScope` |
| `description` | 非空字符串 |
| `sources` | 可选；存在时必须是现有 `CommandSource` 数组 |

### 5.4 合并规则

V1 推荐规则：

1. 内置 operation 先加载。
2. `operations.json` 后加载。
3. 外部配置不能覆盖内置 operation。
4. 外部配置内部不能有重复 id。
5. 任何 schema 错误或重复 id 都 fail-fast。

原因：

- 权限系统必须 fail-closed。
- 允许覆盖内置 operation 容易改变危险标记或 scope，风险过高。
- 如果未来确实需要覆盖，应单独设计 `overrideBuiltin: true`，并要求 daemon owner 显式开启。

### 5.5 模块改造

建议新增：

```text
src/core/command/builtin-operations.ts
src/config/operation-manifest.ts
```

职责：

```text
builtin-operations.ts
  -> export const BUILTIN_OPERATIONS: OperationMeta[]

operation-manifest.ts
  -> readOperationManifest()
  -> validateOperationManifest()
  -> listConfiguredOperations()

operation-registry.ts
  -> buildOperationRegistry()
  -> getOperationMeta()
  -> listOperations()
```

`operation-registry.ts` 对外 API 保持兼容：

```ts
export function getOperationMeta(id: string): OperationMeta | null;
export function listOperations(): OperationMeta[];
export function listOperationsByCategory(category: OperationCategory): OperationMeta[];
export function listDangerousOperations(): OperationMeta[];
export function hasOperation(id: string): boolean;
```

### 5.6 缓存策略

V1 可使用 mtime 缓存：

```text
operations.json mtime 未变 -> 使用缓存 registry
operations.json mtime 变化 -> 重新加载并校验
```

如果校验失败：

- daemon 启动阶段：fail-fast。
- 运行期热加载：保留上一份有效 registry，记录 error audit/warn。

V1 更简单的实现是启动时加载，不做热加载。ECWeb 改配置后提示需要 reload。

## 6. HTTP Route Auth Manifest 设计

### 6.1 配置文件

建议路径：

```text
$EVOLCLAW_HOME/ecweb-auth-routes.json
```

### 6.2 配置示例

```json
{
  "$schema_version": 1,
  "routes": [
    {
      "id": "budget.current",
      "method": "GET",
      "path": "/api/budget/:aid",
      "operation": "budget.current",
      "scope": "relation",
      "source": "ecweb",
      "selfAidFrom": "path.aid",
      "args": {
        "aid": "path.aid"
      }
    },
    {
      "id": "budget.set",
      "method": "PUT",
      "path": "/api/budget/:aid",
      "operation": "budget.set",
      "scope": "relation",
      "source": "ecweb",
      "selfAidFrom": "path.aid",
      "args": {
        "aid": "path.aid",
        "limit": "body.limit"
      }
    },
    {
      "id": "role.assign",
      "method": "PUT",
      "path": "/api/assignments/peer/:aid/:targetId",
      "operation": "role.assign",
      "scope": "agent",
      "source": "ecweb",
      "selfAidFrom": "path.aid",
      "args": {
        "targetId": "path.targetId",
        "targetRole": "body.role",
        "scope": "body.scope"
      }
    }
  ]
}
```

### 6.3 Route 匹配规则

支持：

```text
GET /api/budget/:aid
PUT /api/assignments/peer/:aid/:targetId
GET /api/stats/*
```

V1 建议支持两类：

1. `:param` 命名路径参数。
2. 末尾 `*` 前缀匹配。

不建议 V1 支持完整正则，避免配置难以审计。

### 6.4 参数提取语法

只允许固定来源：

```text
path.<name>
query.<name>
body.<name>
header.<name>
literal.<value>
```

示例：

```json
{
  "args": {
    "targetRole": "body.role",
    "peerId": "body.peerId",
    "groupId": "body.groupId",
    "from": "query.from"
  }
}
```

限制：

- 不允许表达式。
- 不允许函数调用。
- 不允许从任意对象路径读取原型字段。
- body 只解析 JSON。
- body 大小沿用现有限制，建议默认 1MB。

### 6.5 Context 字段映射

HTTP request 需要构造 `CommandAuthorizationContext`。

| Context 字段 | 来源 |
|---|---|
| `intent.operation` | route auth manifest |
| `intent.scope` | route auth manifest |
| `intent.source` | 固定 `ecweb`，或 route 配置 |
| `intent.args` | route auth manifest args 提取 |
| `actorId` | `trustedActorAid(req)`，本地直连为 `local-direct` |
| `selfAid` | `selfAidFrom` 提取 |
| `role` | localDirect -> `owner`；否则 `resolvePeerRoleDetail()` |
| `source` | `ecweb` |
| `isDaemonOwner` | actorAid 是否在 process owners |
| `fromControlChannel` | V1 可为 false；control route 后续补充 |

### 6.6 认证与授权边界

认证和授权分层：

```text
Authentication:
  token 是否有效
  localDirect 是否允许自动 token
  trustedActorAid 是否可信

Authorization:
  actor 是什么 role
  role 是否允许 operation
  scope 是否匹配
  constraints 是否通过
```

token 有效不代表有业务权限。token 只证明访问 ECWeb 的会话合法；operation 权限仍由 role 决定。

## 7. 通用 HTTP Authorizer 设计

### 7.1 模块位置

新增：

```text
ecweb/src/auth/http-authorizer.ts
ecweb/src/auth/http-route-auth-config.ts
```

### 7.2 核心 API

```ts
export interface HttpAuthResult {
  allow: boolean;
  status?: number;
  payload?: Record<string, unknown>;
  route?: HttpRouteAuthRule;
  actorRole?: string;
  decision?: CommandAuthorizationDecision;
}

export async function authorizeHttpRequest(
  req: http.IncomingMessage,
  options: {
    localDirect: boolean;
    actorAid: string | null;
    body?: unknown;
  }
): Promise<HttpAuthResult>;
```

业务侧使用方式：

```ts
const body = await readJsonBody(req);
const authz = await authorizeHttpRequest(req, {
  localDirect: isLocalDirect(req),
  actorAid: trustedActorAid(req),
  body,
});

if (!authz.allow) {
  sendJson(res, authz.status ?? 403, authz.payload ?? { error: 'forbidden' });
  return;
}

// 执行业务逻辑
```

### 7.3 中间层职责

`authorizeHttpRequest()` 做：

1. 匹配 route auth rule。
2. 如果 route 没有配置：
   - V1 对 `/api/*` 默认拒绝，或只对标记为 public 的 route 放行。
   - 为兼容现状，可先使用 shadow mode。
3. 解析 body/query/path/header 参数。
4. 解析 actor role。
5. 构造 `CommandAuthorizationContext`。
6. 调用 `authorizeCommand()`。
7. 调用 `auditCommandAuthorization()`。
8. 返回 allow/deny。

### 7.4 Shadow Mode

为降低迁移风险，V1 可以支持 shadow mode：

```json
{
  "$schema_version": 1,
  "mode": "shadow",
  "routes": []
}
```

模式：

| 模式 | 行为 |
|---|---|
| `off` | 不启用 route auth |
| `shadow` | 执行授权和审计，但不阻断请求 |
| `enforce` | 授权失败直接 403 |

建议上线顺序：

```text
shadow -> 观察 deny 日志 -> 修正配置 -> enforce
```

## 8. 角色权限配置方式

### 8.1 roles.json 示例

```json
{
  "$schema_version": 4,
  "roles": {
    "member": {
      "description": "Team member",
      "permissions": {},
      "commandPermissions": {
        "budget.current": {
          "allow": true,
          "scopes": ["relation"],
          "constraints": {
            "ownPeerOnly": true
          }
        },
        "budget.set": {
          "allow": true,
          "scopes": ["relation"],
          "constraints": {
            "ownPeerOnly": true,
            "ownAgentOnly": true,
            "allowedArgs": {
              "currency": ["CNY", "USD"]
            }
          }
        },
        "budget.reset": {
          "allow": false,
          "dangerous": true
        }
      }
    },
    "guest": {
      "description": "Guest",
      "permissions": {},
      "commandPermissions": {
        "budget.current": {
          "allow": true,
          "scopes": ["relation"],
          "constraints": {
            "ownPeerOnly": true,
            "privateOnly": true
          }
        },
        "budget.*": {
          "allow": false
        }
      }
    }
  }
}
```

### 8.2 推荐规则

1. 新业务 namespace 建议使用业务域名，例如 `budget.*`、`billing.*`、`workflow.*`。
2. 读操作优先使用 `category: read`，但敏感读操作应单独精确授权。
3. 写操作不要依赖 `*`，优先精确授权。
4. dangerous operation 必须单独列出。
5. `anonymous` 应显式拒绝新业务 namespace。

## 9. 业务代码边界

### 9.1 可以配置化的部分

以下场景可以做到新增权限不改代码：

- 新 operation 元数据。
- 某个 role 是否允许 operation。
- operation 允许哪些 scope。
- operation 是否 dangerous。
- route 到 operation 的映射。
- 常见参数白名单/黑名单。
- private/group 限制。
- own peer / own agent 限制。
- daemon owner / control channel 限制。

### 9.2 仍需要代码的部分

以下场景仍需要业务代码：

- 新业务 API handler 不存在。
- 新数据库读写逻辑。
- 新业务资源归属判断。
- 新 constraint 语义。
- 复杂授权矩阵，例如“admin 只能分配某些目标角色”。
- 文件路径沙箱、SQL 安全解析等领域专属校验。

### 9.3 原则

权限配置回答：

```text
这个角色能不能发起这个操作？
```

业务代码回答：

```text
这个操作在当前业务状态下是否成立？
```

两者不能互相替代。

## 10. ECWeb 迁移方案

### 10.1 第一阶段：基础能力

目标：

- 支持 configured operations。
- 支持 route auth manifest。
- 支持 authorizer shadow mode。

改动：

```text
src/core/command/builtin-operations.ts
src/config/operation-manifest.ts
src/core/command/operation-registry.ts
kits/schemas/operation-manifest.schema.1.json

ecweb/src/auth/http-authorizer.ts
ecweb/src/auth/http-route-auth-config.ts
kits/schemas/ecweb-auth-routes.schema.1.json
```

验收：

- 现有 `listOperations()` 行为不变。
- 配置新增 `budget.current` 后，`listOperations()` 可以看到。
- 未注册 operation 仍 deny。
- 配置错误 fail-fast。

### 10.2 第二阶段：低风险 API 接入

优先迁移：

```text
GET /api/models/catalog       -> model.list 或 model.info
GET /api/stats/dashboard      -> stats.summary
GET /api/stats/overview       -> stats.summary
GET /api/role-definitions/operations -> roleDefinition.read 或 config.read
```

说明：

- 这些接口以读为主，适合先用 shadow mode 观察。
- stats 里部分接口可能返回敏感统计，需要决定是否按 agent/peer 裁剪。

### 10.3 第三阶段：写 API 接入

迁移：

```text
PUT /api/assignments/peer/*     -> role.assign
DELETE /api/assignments/peer/*  -> role.revoke
PUT /api/role-definitions       -> roleDefinition.write 或 config.write
POST /api/role-definitions      -> roleDefinition.create
DELETE /api/role-definitions/*  -> roleDefinition.delete
```

注意：

- role assignment 的目标角色矩阵仍保留。
- role definitions 修改属于高敏感配置，建议 dangerous 或 `requireDaemonOwner`。
- 内置 role 删除仍必须业务层拒绝。

### 10.4 第四阶段：server.ts 去重

把重复 token 逻辑抽成：

```ts
authenticateEcwebRequest(req): EcwebAuthenticationResult
```

把重复分支改成：

```text
authenticate
authorize route
dispatch handler
```

## 11. 审计设计

### 11.1 当前策略

`auditCommandAuthorization()` 当前审计：

- deny。
- dangerous allow。
- `role.*` operation。
- `cli.exec.raw`。

V1 保持该策略。

### 11.2 HTTP 授权审计字段

HTTP authorizer 应填充：

```ts
{
  ts: Date.now(),
  source: 'ecweb',
  operation,
  scope,
  dangerous,
  actorId,
  selfAid,
  role,
  decision: decision.allow ? 'allow' : 'deny',
  code,
  reason,
  matchedRule,
  argsSummary
}
```

### 11.3 argsSummary 脱敏

不应记录：

- token。
- authorization header。
- password。
- secret。
- private key。
- 完整大 body。

建议只记录 route auth manifest 中声明的 args，并对敏感 key 做脱敏：

```text
token/password/secret/key/privateKey/authorization -> "***"
```

## 12. 安全策略

### 12.1 Fail-closed

以下情况默认拒绝：

- 找不到 route auth rule。
- 找不到 operation。
- operation source 不包含 `ecweb`。
- 找不到 role。
- role `allowAccess=false`。
- commandPermissions 无匹配规则。
- dangerous operation 没有显式 dangerous grant。
- scope 不匹配。
- constraints 不通过。

### 12.2 Builtin 不可覆盖

V1 不允许外部配置覆盖内置 operation，避免：

- 把 dangerous 改成 false。
- 扩大 defaultScopes。
- 增加 source。
- 修改 description 混淆 UI。

### 12.3 配置不执行代码

禁止：

```json
{
  "args": {
    "aid": "eval(...)"
  }
}
```

只允许：

```text
path.aid
query.aid
body.aid
header.x-aun-visitor-aid
literal.some-value
```

### 12.4 Shadow Mode 上线

生产迁移建议：

1. `mode=shadow`。
2. 收集 3-7 天授权日志。
3. 修正误拒配置。
4. 对低风险 API 开启 `enforce`。

  "$schema_version": 1,

      "id": "budget.current",

## 18. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 配置错误导致 API 不可用 | 中高 | shadow mode、启动校验、明确错误日志 |
| 外部 operation 改写内置安全语义 | 高 | V1 禁止覆盖 builtin |
| route 未配置导致绕过 | 高 | enforce 下 `/api/*` 未匹配默认拒绝 |
| 参数提取过强变成脚本执行 | 高 | 只允许固定 path/query/body/header/literal |
| token 被误认为业务授权 | 中高 | token 只做 authentication，operation 才做 authorization |
| 审计泄露敏感参数 | 中 | argsSummary 脱敏和白名单记录 |
| 历史接口行为变化 | 中 | shadow mode 先观测，再逐步 enforce |

## 19. 最终判断

这个版本可以实现：

```text
新增权限点：配置化
角色授权：配置化
HTTP 接口鉴权：通用化
业务逻辑：仍由代码实现
复杂业务规则：按需代码扩展 constraint 或保留业务 policy
```

因此答案是：**可以做到“不改核心权限代码新增权限配置，并让接口鉴权方式通用”；但不能承诺“任何新业务完全不改代码”。**

准确边界是：

- 如果新业务 handler 已存在，只是补权限控制，可以只改配置。
- 如果新业务 handler 不存在，业务实现仍要写代码。
- 如果新业务需要全新的授权语义，需要扩展 constraint 或业务 policy。

V1 的关键价值不是消灭所有代码改动，而是把权限边界从散落的 handler 判断收敛到：

```text
operation manifest
route auth manifest
roles.json commandPermissions
authorizeCommand()
auditCommandAuthorization()
```

这会让后续新增业务权限的成本和风险显著下降。
