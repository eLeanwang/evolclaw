● 已经把链路看全了。下面是完整分析。

  一、aun 消息收到后的两条路径

  对端发来的 aun 私聊/群聊消息,落到 AUNChannel → MessageBridge.handleMessage
  后,在最前面会先过一道 handleCustomPayload(message-bridge.ts:84):

  - 结构化路径(menu 协议):如果消息正文是一段 JSON,且含 type 字段为
  menu.*,就被当作菜单协议拦截处理,不会进 agent 对话,直接返回 JSON 响应。
  - slash 命令路径:如果不是 JSON,正文以 /model 之类的 slash 开头,走
  command-handler.ts 的快速命令路径,返回人类可读文本/卡片。
  - 其余才是普通消息,转发给 agent。

  也就是说,对端想"获取模型列表/切换模型/查当前模型",有两种发法。

  ---
  二、推荐:menu 协议(结构化,机器友好)

  对端把消息正文设成一段 JSON 文本发过来即可。id 用于把响应和请求对上,自己生成。

  1. 获取模型列表

  请求(menu.options,name=model):
  {"type":"menu.options","id":"req-1","name":"model"}
  我收到后调用 getSubMenuItems('/model')(command-handler.ts:702),响应:
  {"type":"menu.response","id":"req-1","name":"model",
   "data":[
     {"value":"opus","label":"opus (claude-opus-4-8)","selected":true},
     {"value":"sonnet","label":"sonnet (claude-sonnet-4-6)","selected":false}
   ]}
  label 是"短名 (完整ID)",selected:true 标的就是当前模型。

  2. 获取当前使用的模型

  请求(menu.query):
  {"type":"menu.query","id":"req-2","name":"model"}
  响应(command-handler.ts:860):
  {"type":"menu.response","id":"req-2","name":"model","data":{"model":"opus"}}

  3. 切换模型

  请求(menu.update,带 value):
  {"type":"menu.update","id":"req-3","name":"model","value":"sonnet"}
  响应(command-handler.ts:962,会先校验在列表里):
  {"type":"menu.response","id":"req-3","name":"model","data":{"model":"sonnet"}}
  无效模型时:
  {"type":"menu.response","id":"req-3","name":"model",
   "error":{"code":"INVALID_VALUE","message":"无效模型: xxx"}}

  ▎ 还有 {"type":"menu.list","id":"..."} 可一次性拿到整个命令菜单(按对端 role 
  ▎ 过滤,见 getMenuItems)。name 可用的还有 pwd/session/baseagent/effort/chatmode
  ▎ /dispatch/permission/activity/system(映射表见 message-bridge.ts:233)。

  结论:ec model 这套命令,目前不能直接通过 aun 消息控制

  需要先区分项目里两套并存但不互通的模型管理系统:

  系统 A:对话内 slash / menu(会话运行时)

  - 入口:/model slash 命令、menu.* JSON 协议
  - 改的是:runner 的运行时模型 + EvolAgent 的 config.json baseagent
  块(agent.setModel() + evolagent.setBaseagentModel(),见
  command-handler.ts:962-972)
  - 能通过 aun 消息控制(就是上一条回答讲的两条路径)

  系统 B:ec model(三级作用域 CLI)

  - 入口:命令行 ec model list/current/use/...
  - 改的是:defaults.json(全局)/ config.json(agent级)/ relations/<peer>/preferenc
  es.json(关系级)三个作用域文件,运行时在每条消息处理时按 关系 > agent > 全局
  解析(message-processor.ts:630)
  - 入口是 cmdModel(src/cli/model.ts),只接受 process.argv,没有任何 aun / menu /
  IPC 桥接

  为什么 B 收不到 aun 消息

  handleCustomPayload 的 menu 映射表(message-bridge.ts:233)里 model →
  /model,走的是系统 A。menu.options/query/update 调的是
  getSubMenuItems、execMenuQuery、execMenuUpdate,这些方法内部用的是
  agent.listModels() / agent.getModel() / agent.setModel(),完全没有调用
  getCatalog / resolveEffectiveModel / writeScope。

  也就是说 ec model 的 list/current/use/info/effort/reset、三级作用域、--peer
  关系级覆盖、模型 catalog 元数据(价格/上下文窗口/模态)这些能力,没有对应的 aun 
  消息接口。对端发任何消息都触达不到系统 B。

  间接可达的唯一途径

  如果对端发的是普通对话消息(不是 slash、不是 menu JSON),消息会进 agent。Agent
  如果有 Bash/shell 权限,可以自己执行 ec model use ...——但这是"让 agent
  跑命令",不是"协议级控制",依赖权限模式且不可靠。

  ---
  如果你想让 ec model 能被 aun 消息控制

  需要新增桥接。最自然的做法是在 menu
  协议里扩展(因为它已经是结构化的机器接口)。两个可选方向:

  1. 扩展 menu. 的 model 语义*:给 menu.query/options/update 的 model name
  增加作用域参数(scope: global|agent|relation、peer),内部改调
  getCatalog/resolveEffectiveModel/writeScope,并复用 ec model
  已有的错误码。改动集中在 command-handler.ts 的三个 /model 分支 +
  message-bridge.ts 解析。

  action:"use/current/list/info"),把 cli/model.ts 里的 dispatch
